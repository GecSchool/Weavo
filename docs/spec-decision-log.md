# 웹 데이터 통합 플랫폼 스펙 결정 로그

- 작성일: 2026-10-11
- 최근 수정일: 2026-10-30
- 상태: 논의 진행 중
- 목적: 설계제안서에 반영하기 전, 대화를 통해 확정한 제품 및 수집 동작을 보존한다.
- 원칙: 이 문서는 최종 명세가 아니다. `확정` 항목은 현재 합의이며, 후속 논의에서 변경할 수 있다. 서비스 간 메시지 형식과 전송 흐름이 충돌하면 `service-message-contracts.md`를 우선한다.

## 1. 현재 제품 방향

- 여러 웹사이트에서 같은 종류의 텍스트 기반 데이터를 수집한다.
- 프로젝트별 공통 스키마에 맞춰 데이터를 추출하고 통합한다.
- 이미지와 첨부파일을 포함한 범용 미디어 크롤러는 목표로 하지 않는다.
- 세부 스펙은 제안안을 묶어서 검토한 뒤 사용자가 승인한 내용만 확정한다.

## 2. 확정된 결정

### 2.1 페이지 탐색 범위

- 페이지 번호 방식의 페이지네이션을 지원한다.
- `다음` 버튼 방식의 페이지네이션을 지원한다.
- `더 보기` 버튼을 지원한다.
- 목록에서 상세 페이지로 이동해 수집하는 방식을 지원한다.
- 무한 스크롤은 조건부로 지원한다.
- 마지막 페이지 또는 더 이상 새로운 항목이 없는 상태를 정상 종료 조건으로 사용한다. 일반 반복 수집에서는 출처에 연결된 각 프로젝트의 최신 저장 데이터 확인 조건을 모두 만족하면 그 전에 종료할 수 있다.
- URL이 동일하다는 사실만으로 반복이라고 판단하지 않는다. 이동 전후의 항목 구간과 실제 진행 상태를 함께 확인하며, 확인 가능한 동일 구간으로 돌아오거나 실질적 진행 없이 반복하면 이동 실패로 처리한다. 실제 사이트에서 판단을 검증한다.

### 2.2 페이지 접근 방식

- 최초 분석은 브라우저에서 렌더링된 DOM을 확보해 수행한다.
- 후보 검증 후 목록에서만 HTTP 응답으로 동일 데이터 추출·탐색이 가능한지 내부 확인한다. 가능하면 목록은 HTTP, 그렇지 않으면 브라우저를 사용한다. 상세는 항상 브라우저로 이동·추출·복귀를 검증하고 수집한다. 별도 HTTP 결과 화면은 두지 않는다.
- 목록의 HTTP·브라우저 수집 가능성과 상세의 브라우저 이동·복귀를 각각 검증한다. 상세 URL 생성 템플릿 직접 입력은 MVP에 포함하지 않는다.
- 로그인 없이 접근 가능한 공개 페이지에만 수집을 수행한다.
- 사용자 계정, 비밀번호, 세션 및 쿠키가 필요한 사이트는 지원하지 않는다.
- 자동 접근 과정에서 `403`, 접속 차단 또는 캡차가 확인되면 우회하지 않고 해당 출처의 수집을 즉시 중단한다.
- 차단된 출처는 지원할 수 없는 출처로 표시한다.

### 2.3 이미지와 첨부파일

- 이미지 요소는 공통 스키마 추천과 데이터 추출 대상에서 제외한다.
- 이미지 URL, `alt` 텍스트, CSS 배경 이미지, 이미지 파일 다운로드 및 OCR을 지원하지 않는다.
- 이미지 주변에 별도로 표시된 일반 텍스트는 기존 방식으로 수집한다.
- PDF, HWP, Word, Excel 등 첨부파일을 수집 대상에서 제외한다.
- 첨부파일의 파일명, 다운로드 링크 및 파일 내용도 스키마 추천과 데이터 추출에 사용하지 않는다.

### 2.4 출처 등록과 자동 탐지

- 사용자는 목록 페이지 URL과 원하는 데이터를 입력한다.
- 입력 URL은 스킴·호스트 대소문자와 기본 포트를 정규화하고 fragment를 제거해 비교한다. path·query와 그 순서는 임의 변경하지 않는다. 상세는 메시지 명세 20.2를 따른다.
- `http`와 `https`는 처음부터 같은 URL로 간주하지 않으며, 실제 리다이렉트 결과가 같은 최종 URL일 때만 동일 출처로 판단할 수 있다.
- 정규화된 목록 URL·목록 범위·초기 조건·목록 이동 설정이 정확히 같을 때만 동일 공유 출처로 판단하고 애매하면 분리한다. Control이 비교와 생성을 직렬화한다. 물리 잠금 구현은 별도다.
- URL 등록 즉시 ProjectSource를 만들고 고유한 project_source_id를 발급한다. 공유 출처가 확정되기 전 source_id는 null이다. 분석·검증 후 동일한 공유 출처의 source_id를 연결하거나 새 공유 출처를 만든다. 등록 후보와 연결 완료 출처는 같은 project_source_id로 식별한다.
- 분석 서버는 첫 목록의 DOM과 사용자 요구를 바탕으로 AI에 임시 스키마, 목록 추출 규칙, 다음 목록 이동 후보와 상세 페이지 이동 후보를 함께 요청한다.
- 상세 이동 후보가 있으면 실제로 이동해 DOM에서 데이터 후보를 추출하고, AI가 선택한 목록 항목과의 연결 및 사용자 요구에 필요한 데이터인지 판단한다. 필요한 상세 필드와 추출 위치는 임시 스키마와 커넥터 후보에 반영한다. 링크뿐 아니라 클릭으로 열리는 상세 화면도 지원하며 분석 단계에서 이동·목록 복귀 방법을 정의하고 검증한다.
- 다음 목록 이동 후보를 실제 실행하고 이동 전후 DOM·URL·추출 결과를 검증한다. 필요하면 다른 목록 및 소수의 상세 페이지 샘플에도 후보를 적용한다.
- 후보가 부적합하면 관찰 결과를 전달해 후보를 수정·재생성하고 다시 검증한다. 제한 안에 후보를 확보하지 못하면 `확인 필요`로 처리한다.
- 초기 분석, 스키마 리비전, 탐색 복구와 커넥터 복구는 공통 편집·검증 화면을 사용한다. 사용자에게 스키마, 원천별 필드 위치와 CSS 선택자, 추출 샘플 및 탐색 결과를 보여준다.
- 필드별 원천 위치는 목록·상세 페이지·해당 원천에 없음으로 지정한다. 상세 필드에는 목록 항목에서 상세를 여는 링크·버튼 CSS 선택자와 상세 DOM에서 값을 추출하는 CSS 선택자를 각각 설정한다. 상세 위치에 승인된 이동 규칙이 없으면 이동 후보를 찾고 검증한다. 같은 이동 규칙을 사용하는 필드는 실행 시 공유할 수 있다.
- 사용자는 스키마·CSS 선택자·탐색 규칙 후보를 직접 수정할 수 있다. 스키마 리비전에서는 원천별 필드의 위치와 CSS 선택자를 사용자가 직접 연결한다. 자연어 수정은 MVP에서 지원하지 않는다.
- 사용자가 수정하면 영향을 받는 원천과 규칙을 다시 검증하고 결과를 보여준다. 승인 전에는 후보 설정만 변경한다.
- 선택자 검증 화면에는 일치 요소 수, 추출 텍스트 및 상세 URL 등 적용 가능한 샘플을 보여준다. 샘플 필드의 match_count는 선택자를 실행하지 못하면 null, 실행했으나 일치가 없으면 0이다.
- 최초 설정과 공통 스키마 변경은 사용자가 샘플을 확인하고 승인한 뒤 활성화한다. 스키마 변경 없이 탐색·커넥터 규칙만 복구되는 경우의 자동 적용은 §2.15를 따른다.
- CSS 선택자 직접 입력·편집을 제공한다. 드래그 매핑, XPath 직접 입력, 자연어 수정 및 비개발자를 위한 시각적 요소 선택 UI는 MVP에서 지원하지 않는다.
- 초기 자동 분석은 브라우저 탐색, AI 호출과 후보 검증을 포함해 최대 5분으로 제한한다. 사용자 승인 대기는 제외하며 승인 전 HTTP 검증의 시간 예산은 미정이다.
- 초기 상세 샘플은 첫 목록에서 최대 3개를 확인하며, 항목이 1~2개면 존재하는 항목만 확인한다.
- 다중 출처 초기 분석은 두 단계로 진행한다. Analysis는 출처마다 브라우저 DOM과 수집 목적을 바탕으로 LLM에 필드·추출·이동 후보를 요청하고 실제 이동 및 추출을 검증한다. 출처별 필드 후보·샘플값·선택자·이동 방식 후보는 S3에 임시 저장한다.
- Analysis는 대상 출처의 중간 분석 결과를 S3에서 읽어 LLM에 공동 추천을 요청한다. 공동 추천은 의미가 같은 필드를 연결하고 공통 스키마와 출처별 매핑 후보를 생성한다. 공동 추천 입력은 출처별 후보와 샘플을 사용하며 분석 DOM 원본을 S3에 저장하지 않는다.
- 출처별 중간 분석 결과는 공동 추천에 쓰는 임시 객체이며 후보 revision별 검증 샘플 및 Crawler의 수집 스냅샷과 구분한다. 분석이 승인·취소 등으로 종료되어 재시도에 더 이상 필요 없고 관련 작업이 끝나 참조하지 않으면 정리한다. Control은 출처별 intermediate_ref를 저장해 출처 재시도 시 Analysis에 전달한다. Analysis는 중간 파일의 `(intermediate_ref, candidate_key)`와 공통 `field_id`의 매핑을 후보 메타데이터에 유지해 사용자 수정과 재시도 결과를 구분한다. 비승인 고아 임시 객체는 생성 후 7일이 지난 뒤에도 작업·현재 후보·최종 결과에서 참조하지 않는지 확인한 다음 정리한다. 최초 분석에서 성공한 출처가 하나 이상이면 그 결과로 공동 스키마 후보를 추천하고 실패 출처는 재시도·제외할 수 있다. 모든 출처가 실패하면 후보를 승인할 수 없다. 재시도 결과는 사용자 수정을 보존하고 필요한 검증을 수행한다. 상세 형식·경로·정리 절차는 [S3 저장 명세](s3-storage-contract.md)를 따른다.
- 초기 분석의 브라우저 DOM 원본은 보관하지 않는다. Analysis가 사용자 승인 전에 후보 revision별 샘플값을 S3에 저장한다. Control DB는 분석 후보·revision·검증 상태와 샘플 식별정보를 관리한다. 승인 시 현재 검증된 revision을 확인하고 해당 설정과 샘플 식별정보를 지속 저장한다.
- 분석 샘플은 Crawler의 HTML·DOM 수집 스냅샷과 다른 객체다. S3 경로는 analysis_id와 후보 revision으로 결정하고 프로젝트·출처를 구분한다. Analysis는 샘플값을 메시지에 담지 않고 후보·검증 결과와 식별정보만 Control에 전달한다. Control은 S3에서 해당 샘플을 읽어 화면에 제공한다. 수정 후 재검증이 필요하면 새 revision을 검증하고 새 샘플을 저장한다. 추출에 영향 없는 수정은 기존 검증·샘플을 승계할 수 있다. Control은 검증 결과의 실제 sample_ref·sample_revision을 기록하며 복구에는 승인 설정에 연결된 샘플만 사용한다. 추출에 영향 없는 수정으로 검증을 승계하면 유효 검증 revision은 새 후보에 맞추고 샘플 생성 revision·참조와 승계 근거는 보존한다. 새 승인 샘플이 확정되고 기존 참조·사용 작업이 끝날 때까지 기존 승인 샘플을 유지한다. 샘플 저장 실패는 승인 가능한 성공 결과가 아니다. 비승인 샘플의 7일 고아 검사에도 현재 후보와 진행 작업의 참조를 우선 확인한다. 실패 재처리와 정리 구현은 S3 저장 명세를 따른다.

### 2.5 공유 출처 수집기와 필드 커넥터

- 페이지 이동·수집을 담당하는 출처 수집기와 프로젝트·출처별 스키마 필드의 값을 추출하는 필드 커넥터를 구분한다.
- 출처 수집기는 목록 URL, 페이지네이션, 더 보기, 무한 스크롤, 상세 페이지 방문, 목록의 HTTP·브라우저 방식, 수집 일정과 스냅샷 생성을 관리한다. 상세 방문은 브라우저로 고정한다.
- 출처 수집기는 목록 구간과 필요한 상세 페이지를 수집해 동일 출처의 프로젝트들이 공유하도록 한다.
- 동일 목록 항목에서 여러 프로젝트·필드의 상세 접근·이동·대기·복귀 규칙이 같으면 실행 중 묶어 한 번 수집하고 프로젝트 출처·필드에 연결한다. URL만 같다는 이유로 서로 다른 클릭 동작을 합치지 않는다.
- FieldConnector는 하나의 SchemaField와 같은 프로젝트에 속한 ProjectSource에 연결되며 목록·상세·없음 위치, 상세 이동·복귀 정보, CSS 선택자, 추출 대상과 순서 있는 파싱 규칙을 가진다.
- 프로젝트·출처별 활성 필드 커넥터는 동일 수집 스냅샷에서 필요한 필드를 독립적으로 추출한다. 목록 항목과 상세 객체의 연결은 스냅샷 manifest에 남긴다. 목록 항목 경계의 구체적인 탐지 방식은 미정이다.
- 추출 결과와 스키마는 프로젝트별 영역에 분리해 저장한다.
- 모든 커넥터를 실행하지 않고, 해당 출처에 연결된 활성 커넥터만 실행한다.
- 출처 수집기의 접속·탐색 실패는 해당 출처를 사용하는 모든 프로젝트에 영향을 준다.
- 프로젝트 커넥터의 필드 추출·변환 실패는 해당 프로젝트에만 영향을 준다.

이후 문맥에서 프로젝트 커넥터는 별도 클래스가 아니라 해당 프로젝트·출처의 필드 커넥터 규칙 집합을 뜻한다.

개념 흐름:

```text
크롤러가 목록 페이지 또는 스크롤 5개 묶음을 확인
  -> 상세 데이터가 필요한 연결 프로젝트를 위해 해당 상세 페이지를 한 번 열어 공유
  -> 수집 도중 추출한 필드값과 전달받은 프로젝트별 최신 데이터 최대 3개 비교
  -> 모든 프로젝트가 기준을 충족하거나 시간·종료 조건에 도달할 때까지 반복
  -> 최종 HTML 또는 DOM 스냅샷을 S3에 저장하고 작업 메시지 발행
  -> 인제스천이 최종 스냅샷을 가져와 데이터 추출·검증·저장
```

### 2.6 스냅샷 보관

- 출처 수집기의 한 번의 실행에서 방문한 목록 및 상세 페이지 묶음을 하나의 `스냅샷 세트`로 본다.
- 스냅샷 세트에는 방문한 URL과 수집 시각, HTTP로 받은 HTML 또는 브라우저가 렌더링한 DOM을 포함하고 S3에 저장한다.
- 스냅샷 세트는 현재 출처 수집기와 프로젝트 커넥터의 추출 결과를 검증하고 장애를 분석하기 위한 출처 단위 자료로 사용한다.
- 마지막 페이지 도달 또는 시간 제한으로 실행이 끝나고 반복 목록 항목이 한 건 이상 검증된 경우의 스냅샷 승격은 기존 정상 세트 정책을 따른다.
- 데이터 변경이 전혀 없이 조기 종료한 경우 기존 최신 정상 스냅샷 세트를 유지한다.
- 신규·변경 데이터를 수집한 뒤 변경 없음 조건으로 조기 종료한 정상 실행은 이번 부분 스냅샷 세트로 최신 세트를 교체한다. 이전보다 확인 범위가 좁아질 수 있다.
- 반복 목록 항목이 0건인 스냅샷 세트는 즉시 교체하지 않고 후속 수집에서 정상 항목이 다시 발견될 때까지 기존 최신 세트를 유지한다.
- 0건 감지 결과만으로 빈 스냅샷 세트를 공유 출처의 최신 정상 세트로 확정하거나 출처 상태를 정상으로 전환하지 않는다.
- 공유 출처는 후속 수집에서 항목이 다시 발견될 때까지 `확인 필요` 상태를 유지한다. 사용자는 재확인을 요청하거나 출처 삭제를 선택할 수 있다. 기존 정기 수집 일정은 유지한다.
- 네트워크 오류, 접근 차단, 렌더링 오류 또는 페이지 구조 검증 실패로 끝난 결과는 최신 스냅샷 세트를 덮어쓰지 않는다.
- 크롤러는 수집 도중 페이지 또는 묶음 단위로 프로젝트별 비교에 필요한 필드값을 추출해 최신 저장 데이터와 비교한다. 중간 구간 스냅샷은 인제스천에 전달하지 않는다.
- 크롤러는 최종 HTML 또는 렌더링 DOM 스냅샷을 S3에 저장하고 작업 식별자와 저장 위치가 담긴 메시지를 전송한다. 인제스천이 최종 스냅샷을 가져와 추출·검증·중복 확인·DB 저장을 담당하며, 크롤러는 프로젝트 레코드를 직접 DB에 저장하지 않는다.
- Control이 작업 발행 전에 Ingestion 내부 API에서 각 프로젝트·출처의 최신 저장 데이터 최대 3개를 조회하고, 반환된 컬럼값을 Crawler 작업 메시지에 포함한다. 조회 실패는 정상적인 0건과 구분한다. 임시 추출은 Crawler에서 공통 Java 파싱 모듈로 수행한다. 생성된 parser.code는 별도 격리 작업자 없이 각 서비스 JVM의 공통 파서 모듈에서 실행한다.
- 최신 정상 스냅샷 세트 하나를 유지한다. 교체된 이전 세트는 참조하는 적재·재처리 작업이 종료된 뒤 삭제한다. 시도별 불변 객체와 채택된 manifest, 작업 결과 확정·정리 규칙은 [S3 저장 명세](s3-storage-contract.md)를 따른다.

### 2.7 수집 일정과 실행 분산

- 수집 일정은 프로젝트가 아니라 출처 단위로 관리한다.
- 하나의 출처에는 한 번에 하나의 수집 작업만 실행한다.
- 이미 해당 출처를 수집 중일 때 요청 프로젝트가 포함되어 있으면 현재 작업에 연결하고, 포함되어 있지 않으면 현재 수집·적재가 끝난 뒤 후속 작업을 예약한다.
- 수동 수집 중 정기 실행 시각이 도래하는 등 실행이 겹치면 출처를 중복 실행하지 않는다. 요청 프로젝트가 실행 대상에 포함된 경우에만 현재 실행 결과를 사용한다.
- 프로젝트 전체 수동 수집은 프로젝트에 연결된 활성 출처별 수집을 한 번에 요청한다. Control은 요청을 대표 작업으로 관리하고 출처별 작업의 진행·성공·실패 결과를 연결한다. 출처별 수동 수집은 유지한다.
- 실제 수집은 공유 출처 단위로 실행하고 해당 출처의 모든 활성 프로젝트를 기존 기준에 따라 비교·적재한다. 이미 실행 중인 작업에 요청 프로젝트가 포함되어 있으면 해당 프로젝트 결과를 연결한다. 포함되어 있지 않으면 현재 실행이 끝난 뒤 해당 프로젝트를 포함한 후속 수집을 요청한다. 다른 프로젝트 데이터는 요청자에게 노출하지 않는다.
- 출처가 없는 프로젝트에서 전체 수집 요청은 409 NO_ACTIVE_SOURCES를 반환한다. 중복 수동 요청은 각 요청 job을 만들되 대상이 포함된 기존 실행에 연결한다. 취소는 MVP에서 지원하지 않는다. 각 출처의 수집과 필요한 적재가 종료된 뒤 모두 성공이면 SUCCEEDED, 일부 실패면 PARTIAL, 모두 실패면 FAILED다.
- 사용자 요청으로 시작한 수동 수집과 새 출처의 최초 수집은 정기 수집보다 높은 우선순위 큐에 넣는다.
- 워커가 새 작업을 가져올 때 수동·최초 수집 대기 작업이 있으면 이를 정기 수집보다 먼저 실행한다.
- 정기 수집이 무기한 밀리는 것을 막기 위해 수동·최초 수집을 연속 3건 시작한 뒤 정기 수집 대기 작업이 있으면 정기 수집 1건을 실행하고 다시 수동 우선순위를 적용한다.
- 이미 실행 중인 정기 수집을 중단해 수동 수집으로 교체하지 않으며, 우선순위는 아직 시작하지 않은 대기 작업에만 적용한다.
- 동일 출처 중복 실행 금지와 도메인별 동시 요청·간격 제한은 작업 우선순위보다 먼저 적용한다.
- Control이 활성 연결이 확정된 공유 출처마다 EventBridge Scheduler에 12시간 주기의 일정을 등록한다. Scheduler는 예정 시각마다 정기 요청 SQS로 신호를 보내고, 이를 받은 Control이 실제 수집 작업을 생성한다. 개별 프로젝트가 일시적으로 실패해도 다른 활성 프로젝트의 일정을 중단하지 않는다.
- 일정 Input에는 공유 source_id와 예정 실행 시각을 담는다. source_id는 등록 시 고정하며 예정 시각은 Scheduler의 scheduled-time 문맥 키로 치환한다. 프로젝트 목록·최신 데이터·승인 규칙은 Scheduler가 DB에서 읽지 않고 Control이 신호 수신 시 조회한다.
- 기존 공유 출처에 프로젝트가 추가되면 일정을 재사용한다. 정기 신호는 source_id와 예정 시각으로 중복을 확인하며, 실제 작업의 job_id는 Control이 생성한다.
- 출처별 실행 시작 시각은 크롤러 작업이 최대한 겹치지 않도록 분산 배치한다.
- 새 출처는 기존 작업과 가능한 한 겹치지 않는 시간 슬롯에 할당한다.
- 같은 도메인에는 동시에 하나의 요청만 보내고 요청 사이에 최소 1초 간격을 둔다.
- 연결된 활성 프로젝트의 커넥터 처리와 DB 저장은 인제스천이 크롤러의 스냅샷을 바탕으로 담당한다. 신규 연결 프로젝트는 기존 비교 기준이 없으므로 최초 수집을 진행한다.
- 새로운 출처가 등록되면 정기 시간까지 기다리지 않고 최초 수집을 즉시 실행한다.
- 최초 수집 요청과 별도로 해당 출처를 미래 첫 실행 시각이 있는 12시간 주기의 분산 스케줄에 배치한다. 최초 수집은 정기 신호를 기다리지 않는다.
- 사용자가 수동 수집을 실행해도 기존 12시간 정기 실행 시각은 변경하지 않는다.
- 주기·실행 시각·전송 대상 변경은 Control이 일정을 갱신한다. 마지막 활성 연결이 해제되면 일정을 중지·삭제하며, 이미 큐에 들어온 신호는 Control이 현재 활성 상태를 확인해 무시한다.
- 일정 등록·변경 응답이 누락되면 공유 출처별 고정 일정 이름으로 실제 설정을 조회해 재처리한다. 일정 관리와 실행 신호의 상세 형식은 service-message-contracts.md 7.1·15.20, 전달 순서는 service-message-flows.md 3.20을 따른다.
- HTTP 수집 워커, 브라우저 수집 워커 및 프로젝트 커넥터 워커의 수와 전체 동시 실행 상한은 배포 환경에 맞춰 변경할 수 있는 운영 설정으로 관리하며 제품 스펙에 고정된 숫자를 두지 않는다.

### 2.8 수집 실행 제한

- 최초 수집과 스키마 리비전 수집은 각 출처의 첫 페이지부터 필요한 목록·상세 데이터를 출처별 최대 5분 수집한다. 리비전 대상 프로젝트는 기존 최신값 일치로 조기 종료하지 않는다.
- 일반 반복 수집은 첫 페이지부터 출처에 연결된 모든 프로젝트의 최신 저장 데이터 최대 3개와 추출 필드값을 비교한다. 각 프로젝트의 기준 데이터가 모두 확인되면 해당 프로젝트는 추가 수집이 필요 없는 것으로 판단한다.
- 수집이 필요한 프로젝트의 필드가 상세 화면에 있으면 해당 데이터를 확인하기 위해 상세 화면을 연다. 같은 상세 화면이 여러 프로젝트에 필요하면 한 번 수집해 공유한다.
- 최신 데이터는 해당 프로젝트·출처에 우리 시스템이 신규 레코드를 저장한 순서로 정한다. 내부 순차 `record_id`가 큰 레코드부터 최대 3개를 선택하며, 사이트의 게시일이나 최근 재확인 시각으로 정렬하지 않는다.
- 프로젝트에 저장된 데이터가 3개 미만이면 실제 존재하는 데이터를 기준으로 비교한다. 출처에 연결된 모든 프로젝트가 추가 수집이 필요 없는 상태가 되거나 최대 1분에 도달하면 해당 출처의 실행을 종료한다.
- 무한 스크롤은 스크롤 횟수가 아닌 추출 순서로 항목 5개씩 묶어 비교하며, 프로젝트별 최신 저장 데이터 확인 상태는 묶음 경계를 넘어 유지한다.
- 최초 비교 기준이 없는 신규 프로젝트는 다른 프로젝트의 일치만으로 조기 종료하지 않는다. 기존 공유 출처가 수집 중에 새 프로젝트에 연결되면 현재 작업이 끝난 뒤 신규 프로젝트 최초 수집을 실행한다.
- 출처 수집의 기존 데이터 비교에는 해당 출처를 사용하는 모든 프로젝트의 데이터를 활용한다. Control이 작업 발행 전에 Ingestion에서 각 프로젝트·출처의 최신 최대 3개를 조회해 Crawler 작업 메시지로 전달한다.
- 페이지 수와 레코드 수에는 별도 상한을 두지 않는다.
- 마지막 페이지에 먼저 도달하면 실행 결과를 `completed`로 기록한다. 이 값은 화면용 종료 분류이며 메시지 `status`와 `stop_reason`은 아래 대응을 따른다.
- 실행 유형별 시간 제한에 도달하면 실행 결과를 `time_limit_reached`로 기록하고 해당 회차를 종료한다. 최신값 확인 조기 종료는 성공 상태 `completed`와 메시지 stop_reason `NO_CHANGE`로 구분한다.
- 동일 URL만으로 순환을 판단하지 않는다. 목록 이동의 전후 추출 항목과 진행 상태를 비교하고 확인 가능한 동일 구간으로 되돌아가거나 실질적 진행 없이 반복하면 이동 실패 `NAVIGATION_FAILED`로 처리한다. 반복 판단은 실제 사이트에서 검증하며 URL만 같은 정상 동적 화면은 순환으로 단정하지 않는다.
- 네트워크 오류, `408`, `429` 및 `5xx` 응답만 최대 2회 재시도하며 2초, 5초 간격을 사용한다. 재시도 시간도 해당 실행의 전체 시간 제한에 포함한다.
- `401`, `403`, 캡차 및 명시적 접근 차단은 재시도하거나 우회하지 않고 즉시 중단한다.
- 네트워크 또는 렌더링 오류로 중단하면 `failed`, `401`·`403`·캡차·접근 차단으로 중단하면 `blocked`, 출처 페이지 구조 검증 실패로 중단하면 `source_validation_failed`로 기록한다.
- HTTP 요청의 제한 시간은 15초, 브라우저 페이지 로딩 제한 시간은 30초로 한다. 각 제한 시간도 해당 실행의 전체 시간 제한에 포함한다.
- 브라우저 수집에서는 이미지, 영상 및 폰트 리소스를 기본적으로 차단한다. 해당 리소스를 차단했을 때 본문 텍스트 렌더링이나 페이지 탐색이 실패하는 사이트에 한해서 필요한 리소스만 허용한다.
- 리다이렉트는 요청당 최대 5회까지만 허용하고 HTML 응답 크기는 URL당 최대 10MB로 제한한다.
- `robots.txt`의 수집 금지 규칙을 준수하고 서비스임을 식별할 수 있는 크롤러 User-Agent를 사용한다.
- 매 수집은 항상 첫 페이지부터 시작한다.
- 중단 위치 저장과 이어서 수집은 MVP에서 지원하지 않고 향후 확장 범위로 둔다.

### 2.9 중단 전 수집 결과와 0건 처리

- 일반 수집에서 제한 시간 또는 조기 종료 전 정상 추출한 데이터는 저장된 프로젝트 데이터와 비교하고, 같은 데이터가 없으면 신규 레코드로 저장한다. 리비전 수집은 §2.16의 새 결과 준비 및 교체를 따른다.
- 일반 수집에서 아직 방문하지 못한 기존 레코드는 그대로 유지한다. 리비전 전환 시에는 최대 5분간 재수집한 결과로 교체하므로 재수집하지 못한 과거 레코드는 유지되지 않는다.
- 수집 메시지의 project_id·project_source_id·source_id 등 필수 식별값 검증에 실패한 결과는 정상 레코드로 간주하지 않는다. 레코드에는 project_id와 project_source_id를 저장하며 공유 source_id는 중복 저장하지 않는다.
- 실행 유형별 시간 제한 도달은 한 회차의 실행 종료 조건이며, 시간 제한만을 이유로 별도의 불완전 데이터 상태나 부분 활성화 상태를 만들지 않는다.
- 정상 목록을 확인했지만 새 데이터가 없는 결과와 목록 항목 자체를 0건 발견한 결과를 구분한다. 추출·비교 실패는 변경 없음으로 처리하지 않는다.
- 최초·반복 수집에서 이동 규칙 또는 커넥터 실패가 감지되면 발생 서버가 Control에 실패 지점과 영향 범위를 메시지로 전달하고, Control이 분석 서버에 복구를 요청한다. 스키마를 유지할 수 있는 경우 자동 복구 후 재실행하고, 스키마 변경이 불가피하거나 복구하지 못하면 사용자에게 확인 필요 상태를 알린다.
- 원격 서버 또는 브라우저의 일시적 실패는 규칙 오류와 구분한다. 네트워크 오류·408·429·5xx는 실행 예산 안에서 2초·5초 간격으로 최대 2회 재시도하고, 401·403·캡차·명시적 차단은 우회하거나 재시도하지 않는다. 최종 실패는 메시지 명세 15.7에 따라 처리한다.
- 다만 사이트의 마지막 페이지까지 확인하지 못했으므로 기존 레코드의 삭제 여부는 판단하지 않는다.
- 오래된 페이지가 반복적으로 방문되지 않을 수 있다는 점을 MVP의 제한사항으로 둔다.
- 출처 수집기가 반복 목록 항목을 하나도 발견하지 못하면 정상적인 빈 목록으로 자동 판정하지 않고 출처를 `확인 필요` 상태로 변경한다.
- 출처가 `확인 필요` 상태가 되면 연결된 모든 프로젝트의 갱신을 중단하고 기존 데이터와 API 응답을 유지한다.
- 출처 수집기는 항목을 발견했지만 특정 프로젝트 커넥터의 정상 레코드가 0건이면 해당 프로젝트 커넥터만 `확인 필요` 상태로 변경하며 다른 프로젝트에는 영향을 주지 않는다.
- 확인 화면에는 실제 페이지, 출처 수집 항목 수, 프로젝트 추출 결과, 최근 회차별 수집 건수 추이를 함께 보여준다.
- 최근 수집 건수 추이는 자동 판정 기준이 아니라 참고 정보로만 사용한다.
- 목록 항목 0건이나 특정 프로젝트의 정상 추출 0건은 실제 사이트가 비었더라도 문제로 기록하고 대시보드에 즉시 표시한다. 해당 프로젝트의 이메일 알림이 켜져 있으면 이메일로도 알린다. 신규 데이터가 없는 정상 결과, DB에 기존 데이터가 없는 경우, 기존 데이터와 일치 항목이 없는 경우는 이에 해당하지 않는다.
- 사용자는 문제를 확인한 뒤 출처의 재확인을 요청하거나 프로젝트 설정에서 해당 출처 삭제를 선택한다. 재확인은 기존 실패 출처 재시도·분석·검증 흐름을 재사용하되 운영 중인 프로젝트·출처를 대상으로 한다. 재확인 실패 또는 0건이면 문제와 기존 데이터를 유지한다.
- 출처 삭제는 프로젝트 설정에서 삭제 후보를 지정하고 최종 설정 화면에서 확인·저장한 뒤 해당 프로젝트의 출처 연결과 데이터를 정리한다. 다른 프로젝트의 데이터와 공유 연결은 삭제하지 않는다. `empty-confirmations`로 사용자가 빈 목록을 확정해 별도로 데이터를 삭제하는 흐름은 사용하지 않는다.
- 출처 목록 자체가 0건인 경우 출처 단위, 목록은 있으나 특정 프로젝트의 정상 추출만 0건인 경우 해당 프로젝트 단위로 상태와 영향을 구분한다. 리비전 중 0건이면 기존 API와 데이터를 유지하고 전체 전환을 보류한다.

### 2.10 내부 출처 식별자

- `source_id`는 외부 사이트가 제공하는 값이 아니라 서비스가 출처 등록 시 생성하는 내부 식별자다.
- 등록 직후에는 `project_source_id`가 필수이며 공유 출처 판정 전 `source_id`는 null이다. 공유 출처 확정 후에는 `source_id`를 기록한다.
- 동일 출처를 여러 프로젝트가 사용하더라도 프로젝트별로 새 `source_id`를 만들지 않고 공유 출처를 참조한다.

### 2.11 레코드 식별과 중복 처리

- 크롤링 범위 판단에는 각 프로젝트의 최신 저장 데이터 최대 3개와 현재 추출한 필드값을 사용한다. 인제스천은 최종 스냅샷을 받은 후 DB에서 기존 데이터와 신규 여부를 확인하고 중복을 걸러낸다.
- 저장된 데이터와 같은 내용이면 기존 데이터로 판단하고 중복 추가하지 않는다. 서로 다른 정보가 있으면 실제로 같은 게시물이어도 새 데이터로 판단해 신규 저장한다.
- 게시물 ID나 상세 URL을 신규·기존 데이터 판정의 필수 조건으로 사용하지 않는다. 상세 URL은 접근 대상과 `source_url` 등의 출처 정보로 사용할 수 있다.
- API에 노출하는 `record_id`는 프로젝트 안에서 순차 증가하는 내부 식별자이며 외부 게시물의 동일성을 추론하는 데 사용하지 않는다.
- 같은 게시물의 내용이 바뀌어도 기존 레코드를 덮어쓰지 않으므로 수정 전후 데이터가 별도의 레코드로 남을 수 있다. 서로 다른 게시물이라도 비교 대상 값이 같으면 같은 데이터로 판단될 수 있다.
- 프로젝트가 상세 필드를 요구하면 수집 중 상세 화면을 열어 해당 필드값을 확보한다. 상세 추출이 실패한 상태를 기존 데이터와 일치하거나 변경 없음으로 판단하지 않는다.
- 비교 대상은 추출된 사용자 필드값이다. 실제 `null`은 정상 값으로 비교하고 NOT NULL 조건에 해당하지 않는 한 null이라는 이유만으로 오류를 표시하지 않는다. 필드 추출이나 페이지 접근 자체의 실패는 실제 null과 구분해 기록한다. 사용자 정의 필드는 현재 모두 nullable이며 시스템 필수 필드는 NOT NULL이다.
- 최종 스냅샷에서 추출한 신규 데이터는 각 프로젝트·출처에서 목록의 뒤쪽부터 앞쪽 순서로 DB에 저장한다. 이에 따라 순차 `record_id`가 큰 데이터가 해당 실행에서 앞쪽에 있던 데이터를 가리키도록 한다. 기존 데이터와의 중복 확인은 인제스천이 수행한다.
- 비교값은 승인 parser.code와 공통 타입 변환 결과다. Control은 작업 발행 전에 기준을 조회하며 관련 적재가 끝날 때까지 동일 출처의 다음 논리 작업을 대기시킨다. 작업 기준은 발행 시점 값이다.

### 2.12 레코드 삭제

- 일반 수집에서는 마지막 페이지까지 확인하더라도 이번 결과에 없다는 이유로 기존 레코드를 자동 삭제하지 않는다.
- 변경 없음 조기 종료, 시간 제한, 수집 오류, 반복 감지 또는 검증 오류로 종료된 실행에서는 방문하지 않은 기존 레코드를 삭제하지 않는다.
- 마지막 출처 삭제를 허용한다. 공개 스키마·API와 프로젝트는 유지하고 해당 출처의 레코드만 삭제해 빈 데이터 목록을 제공한다. 삭제 자체는 수집 0건 경고가 아니며 이후 출처 추가가 가능하다. 공개 전에는 승인된 v1 정의만 유지하고 API는 첫 성공 전까지 공개하지 않는다.
- 삭제된 레코드와 삭제 이력은 보관하지 않는다.
- 이후 수집에서 같은 게시물이 다시 발견되면 신규 레코드로 저장한다.
- 시스템은 재발견된 레코드가 복구된 게시물인지 완전히 새로운 게시물인지 구분하지 않는다.
- 조기 종료·시간 제한·마지막 페이지 도달을 포함한 일반 수집은 누락 레코드를 자동 삭제하지 않는다. 사용자 승인 출처·프로젝트 삭제와 스키마 리비전 데이터 교체는 별도다.
- 프로젝트에서 출처 연결을 해제하면 삭제될 레코드 수와 복구 기능이 없다는 사실을 보여주고 확인을 받은 뒤, 해당 프로젝트에서 그 출처가 만든 레코드를 물리 삭제한다.
- 연결 해제는 다른 프로젝트의 레코드와 공유 출처 수집기에 영향을 주지 않는다.
- 마지막 프로젝트 연결이 해제되어 연결된 프로젝트가 0개가 되면 해당 공유 출처의 정기 일정을 중지하고 대기 중인 수집 작업을 제거한다.
- 더 이상 사용되지 않는 공유 출처 수집기와 최신 스냅샷 세트는 별도의 유예 기간 없이 삭제하며 복구 기능을 제공하지 않는다.
- 마지막 연결 해제 시 해당 출처 수집이 이미 실행 중이면 결과를 프로젝트에 반영하지 않고 실행 종료 후 공유 출처와 스냅샷을 정리한다.

### 2.13 레코드 값 갱신

- 일반 수집에서 기존 저장 데이터와 다른 내용은 같은 게시물 여부와 관계없이 새 데이터로 저장한다. 기존 레코드의 값을 변경된 값으로 덮어쓰지 않는다.
- 동일하게 비교된 데이터는 중복 추가하지 않는다. 비교 불가 또는 추출 실패를 신규 데이터나 변경 없음으로 확정하지 않는다.
- 승인된 스키마 구조 변경은 기존 레코드 마이그레이션이나 기존 레코드와의 매칭 없이 재수집 결과로 해당 프로젝트의 데이터 세트를 교체한다. 일반 수집의 신규 데이터 판정과 구분한다.

### 2.14 빈 값과 원본 문자열

- 원본 요소가 존재하고 값이 `없음`, `미정` 또는 빈 문자열이면 이를 명시적인 원본 값으로 인식한다.
- 대상 필드가 `string`이면 `없음`, `미정` 및 빈 문자열을 그대로 정규화 값으로 저장한다.
- 대상 필드가 `number`, `boolean`, `date`, `datetime` 또는 `url`이면 타입 변환을 시도하고, 변환할 수 없을 때 정규화 결과를 `null`로 표현하며 실패를 기록한다. 실패한 레코드는 부분 저장하지 않고 정상 추출 건수에서도 제외한다.
- 타입 변환에 실패한 원본 문자열과 실패 원인은 검증 정보에 기록한다.
- 요소 자체를 찾지 못했거나 추출 오류가 발생하면 비교 불가 또는 검증 오류로 기록하며 기존 저장 데이터를 변경하지 않는다.
- 신규 레코드에서 요소 추출에 실패한 nullable 필드는 정상 null이나 원래 없는 필드와 구분해 실패 정보를 남긴다. 실패한 레코드는 부분 저장하지 않고 정상 추출 건수에서도 제외한다.
- HTML 파서가 엔티티를 문자로 해석한 결과를 원문으로 취급한다. 문자열 공백 제거·축약은 승인된 필드 parser.code가 명시한 경우에만 수행하며 시스템이 별도로 자동 가공하지 않는다.
- `없음`, `미정` 및 빈 문자열은 실제 null과 구분한다. 값 가공은 승인된 parser.code가 명시한 경우에만 적용한다.

### 2.15 타입 변환과 검증

- 공통 스키마는 다음 단일값 타입만 지원한다.
  - `string`
  - `number`
  - `boolean`
  - `date`
  - `datetime`
  - `url`
- 배열, 중첩 객체 및 그 밖의 복합 타입은 MVP에서 지원하지 않는다.
- 각 공통 필드는 API에서 사용하는 `api_name`과 화면에 표시하는 `display_name`을 분리한다.
- `api_name`은 영문 소문자 `snake_case` 형식과 최대 64자 제한을 적용하고 시스템 예약어를 사용할 수 없다.
- `display_name`에는 한글 등 사용자가 이해하기 쉬운 이름을 사용할 수 있다.
- `record_id`, `source_id`, `project_id`, `collected_at` 등 시스템 식별 및 관리 필드는 NOT NULL로 관리한다.
- 사이트에서 추출해 생성한 사용자 정의 스키마 필드는 모두 nullable로 생성한다.
- MVP에서는 사용자 정의 필드를 NOT NULL로 변경하는 기능을 지원하지 않는다.
- 실제 null 또는 출처에 원래 없는 필드는 정상 값이다. 추출·변환 실패가 포함된 nullable 레코드는 부분 저장하지 않고 정상 추출 건수에서 제외하며 실패를 정상 결과로 숨기지 않는다.
- 여러 출처 중 한 출처에만 존재하는 필드도 공통 스키마에 포함한다.
- 일부 출처에만 존재하는 필드는 nullable 필드로 생성하며, 해당 필드가 없는 출처의 값은 `null`로 저장한다.
- 출처 수가 늘어나면서 빈 값이 많은 필드가 증가할 수 있다는 점을 허용한다.
- 출처마다 이름이 다르지만 의미가 같은 필드는 AI가 의미 기반 병합 후보로 추천한다.
- AI 추천은 자동 확정하지 않으며 사용자가 최종 승인하거나 거절한다.
- 최초 스키마 추천에는 정상 추출된 레코드를 최대 50건까지 사용한다. 정상 샘플이 10건 미만이어도 추천은 진행하되 표본 부족 경고를 표시한다.
- 추천 화면에는 필드명뿐 아니라 추천 근거와 출처별 샘플값을 함께 제공한다.
- 사용자는 추천되지 않은 필드도 수동으로 매칭할 수 있다.
- 원천별 필드 위치와 CSS 선택자를 공통 편집 화면에서 직접 지정한다. 드래그 매핑과 XPath 입력은 MVP에서 지원하지 않는다.
- 사용자는 기존 연결을 해제하거나 다른 공통 필드로 다시 연결할 수 있다.
- 기본 필드 매핑은 출처 필드 하나와 공통 스키마 필드 하나를 연결하는 1:1 방식이다.
- 하나의 출처 필드를 여러 공통 스키마 필드로 분리하는 1:N 매핑을 지원한다.
- 1:N 매핑에는 공통 필드별 파싱 및 변환 규칙을 적용한다.
- AI가 필드 분리와 변환 규칙을 추천하고, 사용자가 샘플 변환 결과를 확인한 뒤 승인한다.
- 여러 출처 필드를 하나의 공통 필드로 결합하는 N:1 매핑은 MVP에서 지원하지 않는다.
- AI는 최초 커넥터 및 매핑 설정 시점에 결정적인 값 가공 규칙을 생성·샘플 검증한다. 별도 가공이 필요하면 필드 커넥터의 `parser.code`에 Java 함수 본문만 넣고 필요 없으면 `parser`를 null로 둔다. 입력은 selector가 추출한 문자열 목록, 출력은 가공된 문자열 또는 실제 null이다. 반환 문자열은 이후 스키마 타입으로 변환한다.
- 정상 수집에서는 레코드마다 AI를 다시 호출하지 않고 승인된 변환 규칙을 반복 실행한다.
- 최초 설정 또는 스키마 변경을 동반하는 AI 규칙은 샘플 결과를 사용자에게 보여준 뒤 승인받는다. 스키마를 유지하는 규칙 복구는 §2.15의 자동 검증·적용을 따른다.
- MVP에서는 사용자가 Java 파싱 코드나 변환 규칙을 직접 작성·편집하는 기능은 지원하지 않는다. 코드 생성·검증은 Analysis가 담당한다.
- 사용자 정의 필드의 실제 null은 정상 값으로 처리한다. NOT NULL 필드에서 null이 발생하면 오류를 표시한다.
- 요소 누락·변환 실패 등 실제 추출 실패는 null 값 자체와 구분한다. 실패가 포함된 레코드는 저장하지 않으며 검증 정보에 실패를 기록한다.
- 검토를 위해 변환 실패 원인과 해당 필드의 원본 값을 함께 기록한다.
- Crawler는 수집 중 임시 추출·파서 실패를, Ingestion은 최종 추출·파싱·타입 변환 실패를 감지하고 관찰한 단계·프로젝트·출처·필드와 확인 가능한 오류 정보를 Control에 전달한다. 실패 현상만으로 CSS 선택자, 파서 또는 사이트 구조 중 원인을 확정하지 않는다.
- 정상 null과 해당 출처에 원래 없는 필드는 추출 실패로 판단하지 않는다. DB·S3·브라우저 등 기술 오류와 접근 차단은 규칙 복구 대상과 구분한다.
- Control은 영향 범위와 실패 정보를 확인하고, 필요한 최신 저장 데이터 또는 승인 샘플을 준비해 Analysis에 `REPAIR_CONNECTOR` 작업을 요청한다. Analysis는 기존 스키마·커넥터와 실패 정보를 참고해 선택자·파싱 후보를 생성하고 검증한다.
- 규칙 관련 실패로 해당 프로젝트·출처의 비교·수집을 계속할 수 없으면 Control은 관찰 정보와 영향 범위를 확인해 Analysis에 자동 복구를 요청한다. 근본 원인을 미리 확정하지 않는다. 반복 실패·검증 불가면 확인 필요로 전환한다. 기술 장애·접근 차단과 구별하며 복구 후보는 최초 시도 포함 최대 3회 검증한다. 비교에 필요한 필드를 확보하지 못해 해당 프로젝트 출처의 비교를 계속할 수 없으면 그 대상만 중단하고 복구를 요청한다. 별도 실패율 임계치는 두지 않는다. 10회·30%는 확정 기준으로 취급하지 않는다.
- Crawler의 임시 추출 실패 시 해당 프로젝트·출처의 비교는 중단하고 다른 정상 프로젝트는 계속 처리한다. 실패 레코드는 저장하지 않는다. 반복 수집은 정상 결과를 적용할 수 있고 출처 추가 실패는 해당 추가를 적용하지 않으며 스키마 리비전은 모든 출처 준비 성공 전 기존 버전을 유지한다.
- 복구 중 또는 `확인 필요` 상태의 해당 프로젝트 추출은 복구·확인이 끝날 때까지 실행하지 않는다.
- 출처 수집기의 탐색 규칙이 실패하면 AI가 복구용 출처 수집기 후보를 생성하고, 프로젝트 필드 추출 규칙이 실패하면 AI가 해당 프로젝트의 복구용 커넥터 후보를 생성한다.
- 문제가 감지되면 사용자에게 즉시 판단을 요구하기 전에 시스템이 복구 후보 생성과 샘플 검증을 먼저 시도한다.
- 공통 스키마가 유지되고 탐색 규칙 또는 커넥터만 변경되는 경우, AI 복구 후보가 검증을 통과하면 사용자 확인 없이 규칙을 자동 교체하고 수집을 다시 실행한다. 탐색 규칙과 커넥터의 리비전은 구분해 기록한다.
- 자동 복구는 프로젝트·출처별 DB 최신 저장 데이터가 3건 이상이면 저장 순서상 최신 3건의 사용자 필드값을 모두 확인한다. 저장 데이터가 0건이면 S3의 승인 분석 샘플을 이용한다. 기준이 없거나 검증할 수 없으면 자동 적용하지 않고 사용자 확인을 요청한다. DB 1~2건이면 존재하는 데이터를 모두 비교해 전부 일치해야 자동 적용한다. 승인 샘플이 부족해 기준을 모두 확인할 수 없으면 자동 적용하지 않는다. 최초 시도 포함 최대 3회 검증 후 실패하면 확인 필요다.
- 사이트 구조와 내용 변화로 공통 스키마 변경이 필요한 경우 사용자가 후보를 확인·승인한 뒤 스키마 전환을 진행한다.
- 공유 탐색 규칙 오류가 확인되면 해당 출처의 모든 프로젝트 수집을 중단한다. Analysis는 영향 프로젝트별로 DB 최신값 또는 DB 0건 시 S3 승인 샘플을 사용해 검증한다. 모두 통과한 규칙만 자동 적용하며 한 프로젝트라도 실패하거나 검증할 수 없으면 공유 규칙 전체 적용을 보류하고 확인 필요로 처리한다.
- 스키마 변경을 요구하는 복구 후보가 샘플 검증을 통과하면 관련 설정을 `승인 대기`로 전환한다. 규칙만 복구되는 경우 승인 대기 없이 검증 후 자동 적용한다.
- 유효한 복구 후보를 생성하지 못했거나 후보가 샘플 검증을 통과하지 못하면 `확인 필요` 상태를 유지한다.
- 공유 출처 이동 규칙은 분석 중 연결된 프로젝트를 검증한 후 교체한다. 분석 단계에서 기준을 통과하지 못한 규칙은 크롤러에 전달하지 않는다.
- 스키마 변경 승인 화면에는 전체 결과의 필드별 추출 성공률, 이전 대비 값 변경률, 누락 필드 등 변화 요약을 제공한다.
- 스키마 변경 승인 화면은 후보 샘플을 보여준다. 안정적인 동일 레코드 식별을 가정해 기존값과 일대일 대응하지 않는다. 정상 샘플이 10건 미만이어도 실제 확보한 샘플로 추천하고 표본 부족을 표시한다.
- 타입 변환에 성공하면 변환된 값을 저장한다.
- 타입 변환에 실패한 nullable 필드는 정규화 결과를 `null`로 표현하고 변환 실패를 별도로 기록한다. 실패한 레코드는 부분 저장하지 않고 정상 추출 건수에서도 제외한다.
- `미정`, `없음` 등 원본 문자열은 검증 오류 정보 또는 원문 근거에서 확인할 수 있도록 한다.

### 2.16 커넥터 리비전 식별자와 API 스키마 버전

- 공개 및 적용 준비 중인 프로젝트 스키마·필드 정의의 원본은 Data DB에 둔다. Ingestion이 준비·변경·공개 전환을 수행하고 Data API는 같은 공개 버전의 스키마와 레코드를 읽는다. Control DB에는 분석·편집 중 후보와 필드 커넥터를 보관한다. 후보나 메시지에 임시로 포함된 스키마는 공개 원본이 아니다.
- 최초 승인 후 v1 스키마 정의를 프로젝트 최초 적용 작업 기준으로 Data DB에 준비한다. 출처별 최초 수집·적재 중 정상 적재된 출처의 데이터는 공개하고, 실패 또는 정상 추출 0건인 출처는 기존 문제·복구 정책에 따라 표시한다. 한 출처의 실패가 다른 성공 출처의 공개를 되돌리지 않는다. 최초 모든 출처가 실패하거나 정상 추출 0건이면 준비된 v1만으로 정상 운영 API를 공개하지 않고 확인 필요를 표시한다. 이후 한 출처라도 정상 적재되면 해당 성공 데이터를 공개한다. 공개 전 최초 복구는 공개 스키마 조회가 아니라 승인 v1 후보·커넥터와 승인 샘플을 적용 작업에서 확보한다.
- 구조 변경 시 승인된 v2 스키마를 변경 작업 기준으로 Data DB에 비공개 준비하고 출처별 새 데이터를 준비한다. 모든 최종 출처 성공 시에만 공개 스키마와 데이터를 v2로 전환한다. 하나라도 실패·0건이면 기존 v1을 유지한다.
- 같은 API 버전에서 공개 필드 정의의 표시 정보가 변경되면 Data DB의 해당 버전에 반영한다. 커넥터만 수정되는 경우 Control 규칙을 적용한다. 표시 정보 갱신은 메시지 명세 19.4, 공개 커넥터 revision 동기화는 10.6을 따른다.
- Control이 공개 스키마가 필요한 기존 출처 추가·수집·복구 작업을 만들 때 Data 측에서 현재 버전과 필드 정의를 조회한다. 실패를 빈 스키마로 바꾸지 않고 작업 발행을 보류·재시도한다. Data API는 Data DB의 공개 스키마를 읽는다. Ingestion의 POST /internal/v1/project-schemas:query로 프로젝트 목록을 묶어 조회한다.
- 리비전 중 Data 공개 버전 전환과 Control 커넥터 활성화가 서로 다른 DB에서 일어나므로 해당 프로젝트의 일반 작업이 서로 다른 버전을 섞지 않도록 조정한다. 전환 결과 중복·지연 시에도 버전·작업을 대조해 수렴시킨다. Control은 해당 프로젝트의 신규 일반 작업을 보류하고 진행 중 쓰기 종료를 확인한 뒤 Data 전환과 커넥터 활성화를 순서대로 마치고 재개한다. Ingestion은 저장 직전에 작업 버전·상태를 다시 검사한다.
- 최초 v1 또는 v2 스키마의 준비는 프로젝트 적용 작업 단위다. 여러 출처의 적재가 동일한 승인 정의를 참조하고, 중복·경합 시 다른 정의를 덮어쓰지 않는다. Control이 기존 Ingestion 큐로 schema.prepare를 보내고 schema.prepared 성공 후 수집한다.

- 프로젝트 커넥터의 현재 규칙을 식별하는 `connector_revision`과 외부 데이터 계약인 API 스키마 버전을 서로 분리한다.
- 프로젝트 커넥터가 교체될 때마다 출력 스키마 변경 여부와 관계없이 `connector_revision`을 1 증가시킨다.
- 출력 스키마가 유지되는 프로젝트 커넥터 교체는 API 버전을 변경하지 않는다.
- `connector_revision`과 변경 시각 및 변경 원인은 기록하지만 이전 커넥터 내용과 전체 변경 이력은 보관하지 않는다.
- nullable 여부와 관계없이 필드 추가·삭제·필드명 변경·타입 변경 등 데이터 API 필드 구조가 바뀌면 새 API 버전을 생성한다.
- 필드 설명 변경, 필드 순서 변경 및 동일한 응답 구조를 유지하는 매핑 변경은 현재 API 버전에 반영한다.
- API 버전 변경은 필드명과 타입 등 응답 구조를 기준으로 판정한다.
- 필드의 구조가 유지된다면 수집 대상의 의미나 매핑 규칙이 달라져도 같은 API 버전에 반영한다.
- 스키마 구조 변경이 감지되어도 새 API 버전을 자동 활성화하지 않는다.
- 필드 변경 내역과 이전·신규 응답 샘플을 사용자가 확인하고 명시적으로 승인해야 전환 절차를 시작한다. 승인 전에 기존 프로젝트 데이터가 재수집 결과로 교체되고, 재수집 범위 밖 과거 데이터와 기존 record_id가 사라짐을 안내한다.
- 새 API 버전의 승인을 기다리는 동안 해당 프로젝트의 데이터 갱신을 중단하고 기존 API는 마지막 정상 데이터를 계속 제공한다.
- 프로젝트 화면에는 스키마 승인 대기 상태와 마지막 정상 갱신 시각을 표시한다.
- 사용자가 새 API 버전을 승인하면 Control이 대상 프로젝트의 연결 출처마다 새 규칙으로 첫 페이지부터 최대 5분간 리비전 수집을 요청한다. Crawler는 기존 최신값 일치로 리비전 대상 프로젝트를 조기 종료하지 않는다.
- Ingestion은 출처별 최종 S3 스냅샷에서 승인된 스키마·커넥터로 데이터를 추출·검증하고 프로젝트의 새 데이터 세트를 준비한다. 기존 레코드를 마이그레이션하거나 재수집 결과와 기존 레코드를 매칭하지 않는다.
- 모든 대상 출처의 수집 및 새 데이터 준비가 성공하고 전환 조건을 만족할 때만 해당 프로젝트의 기존 데이터 세트와 API 활성 버전을 함께 교체한다. 다른 프로젝트의 데이터와 공유 출처 설정은 교체하지 않는다.
- 대상 출처 중 하나라도 수집·추출·준비에 실패하면 Control은 프로젝트 전체 교체를 즉시 보류하고 기존 데이터와 기존 API 응답을 유지한다. 복구 가능한 오류는 자동 복구를 먼저 시도하며 복구 실패·검증 불가, 접근 차단 또는 재시도 종료 등 사용자 조치가 필요할 때 알린다. 복구 중 상태는 화면에서 조회한다.
- 정상 결과 0건은 자동으로 빈 데이터 세트를 활성화하는 성공으로 처리하지 않는다. Control은 기존 0건 분류에 따라 출처 또는 프로젝트를 확인 필요로 표시하고 사용자에게 알리며 전체 교체를 보류한다.
- 레코드는 한 테이블에 프로젝트·프로젝트 출처·스키마 버전과 준비 작업 식별자를 구분해 저장한다. 새 버전이 준비되기 전 기존 API를 유지하며 Data DB의 공개 버전과 해당 스키마·데이터를 일관되게 전환한다. 미공개 준비 실패·취소 데이터는 작업 기준으로 정리한다.
- 각 출처의 마지막 페이지 도달 또는 5분 경과 자체는 정상적인 회차 종료 조건이다. 모든 출처의 유효한 결과와 전환 조건을 확인한 후 새 버전을 활성화하고 이전 버전을 종료한다.
- 새 데이터에는 새로운 record_id를 발급하고 기존 record_id를 재사용하지 않는다. 이전에 저장됐지만 재수집되지 않은 과거 레코드는 교체 후 제공되지 않는다.
- 프로젝트 데이터 교체 시 dataset_revision을 갱신한다. 이전 dataset_revision으로 발급한 커서는 기존 규칙에 따라 무효화되며 새 활성 버전에서 삭제된 기존 record_id의 단건 조회는 404를 반환한다. 종료된 이전 API 버전 경로 요청은 기존 정책대로 410을 반환한다.
- 여러 API 버전을 동시에 제공하지 않고 항상 최신 버전 하나만 운영한다.
- 종료된 이전 버전으로 요청하면 `410 Gone`과 현재 `latest_version` 및 최신 API 경로를 반환한다.
- 새 버전 전환에 영향을 준 출처의 최초 수집 또는 프로젝트 커넥터 추출에서 정상 레코드가 0건이면 새 API 버전을 활성화하지 않고 기존 API와 데이터를 유지하며 영향 범위에 따라 출처 수집기 또는 프로젝트 커넥터를 `확인 필요`로 전환한다.
- 5분 제한 도달을 이유로 새 API에 별도의 불완전 상태를 표시하지 않는다.
- 현재 활성 프로젝트 커넥터만 보관하며 교체된 이전 커넥터와 별도의 롤백 기능은 제공하지 않는다.
- 프로젝트 스키마 버전은 `v1`, `v2`처럼 1씩 증가시킨다.
- 레코드 API 경로는 `/api/projects/{project_id}/v{schema_version}/records` 형식을 사용한다.
- 경로의 `v{schema_version}`은 프로젝트 데이터 스키마 계약의 버전이며 서비스 자체 API의 전역 버전을 의미하지 않는다.
- 수동 수집은 `POST /control/v1/projects/{project_id}/sources/{project_source_id}/collect`로 요청하며, 프로젝트 소유권과 출처 연결을 확인한 뒤 출처 단위 작업을 생성하고 `202`와 `job_id`를 반환한다. 프로젝트 전체 수동 수집은 `POST /control/v1/projects/{project_id}/collect`로 요청하며 소유권을 확인하고 `202`와 대표 `job_id`를 반환한다.
- 사용자가 후보를 수정하면 Control은 변경 revision을 기록하고 필요 시 자동 재검증을 요청한다. 검증 결과는 analysis_id·후보 revision·출처별 상태에 연결하며 별도 검증 요청 API는 제공하지 않는다.
- 최초 설정과 사용자 승인 스키마 변경에서는 현재 후보와 각 출처의 검증 성공 revision이 같은지 확인한다. 스키마 유지 자동 복구는 사용자 승인 없이 검증 통과 결과를 적용한다.
- 스키마 활성화 요청은 현재 후보 revision과 출처별 검증 성공 revision을 확인한다. 출처별 최대 5분 재수집과 데이터 교체를 조정하며 `202`와 전환 job_id 또는 준비 실패 `422`를 반환한다.

### 2.17 API 목록 응답 구조

- 레코드 목록 API는 최상위에 `data`와 `meta`를 갖는 고정 응답 구조를 사용한다.
- `data`에는 레코드 배열을 담는다.
- 각 레코드는 시스템 필드와 사용자 정의 필드를 하나의 평평한 객체로 반환한다. 사용자 정의 필드의 `api_name`에는 시스템 예약어를 허용하지 않아 이름 충돌을 방지한다.
- `meta`에는 `schema_version`, `dataset_revision`, `returned_count`, `next_cursor` 및 `has_more`를 포함한다. 출처별 커넥터 revision과 마지막 수집 시각은 공개 Data API 응답에 반복 노출하지 않고 Control API의 운영 정보에서 제공한다.
- 목록 응답에서 전체 결과 수를 계산하는 `total_count`는 기본 제공하지 않는다.
- 수집이 5분 제한으로 종료되었다는 이유로 별도의 불완전 상태는 제공하지 않는다.
- 프로젝트 커넥터의 한 실행에서 나온 변경사항은 실행 종료 시 하나의 단위로 반영하고 `dataset_revision`을 1 증가시킨다.
- API는 한 실행의 데이터 반영이 끝나기 전까지 직전 `dataset_revision`의 데이터를 제공한다.
- 목록 페이지네이션은 `cursor`와 `limit` 방식을 사용한다.
- 응답의 `meta`에는 다음 조회를 위한 `next_cursor`와 다음 데이터 존재 여부인 `has_more`를 포함한다.
- `cursor`는 발급 당시의 `dataset_revision`, 정렬값 및 마지막 `record_id`를 포함하는 불투명 문자열이며, 클라이언트는 내부 내용을 해석하지 않고 다음 요청에 그대로 전달한다.
- 커서는 발급 당시의 정렬 및 필터 조건에 종속된다.
- 정렬 또는 필터 조건을 바꾼 요청에 기존 커서를 사용하면 메시지 명세에 따라 `409 Conflict`를 반환하고 첫 조회부터 다시 시작하게 한다.
- 다음 페이지 요청 전에 `dataset_revision`이 변경되었으면 `409 Dataset Changed`를 반환하고 첫 조회부터 다시 시작하게 한다.
- 클라이언트는 요청마다 `limit`을 원하는 값으로 지정할 수 있으며, 서버는 과도한 응답을 막기 위한 최대값을 적용한다.
- `limit`의 기본값은 100이고 허용 범위는 1~500이다.
- 허용 범위를 벗어난 `limit`에는 자동 보정하지 않고 `400 Bad Request`를 반환한다.
- 목록 조회는 요청당 하나의 정렬 필드와 `asc` 또는 `desc` 정렬 방향을 지정할 수 있다.
- 지정한 정렬 필드의 값이 같은 레코드 사이에서는 `record_id`를 보조 정렬 기준으로 사용해 순서를 고정한다.
- `record_id`는 레코드가 최초 저장될 때 순차적으로 증가하는 숫자 식별자를 부여한다.
- 발급된 `record_id`는 레코드가 삭제되어도 재사용하지 않는다.
- 정렬 조건을 생략하면 `record_id` 오름차순으로 반환하며, 이는 원문 게시일이 아니라 서비스에 레코드가 생성된 순서다.
- `record_id`는 Data DB 전역 시퀀스로 발급한다. 프로젝트별 번호는 1부터 시작하거나 연속될 필요가 없다. 프로젝트 내 동시 적재는 상태 행 잠금으로 직렬화하고 수집 결과는 뒤쪽부터 저장한다. 실패·삭제로 생긴 번호 공백은 재사용하지 않는다.
- 레코드의 내부 고유성은 `(project_id, record_id)` 조합으로 보장한다.
- 사용자 정의 필드에는 필드 타입별로 허용된 기본 필터 연산자만 지원한다.
- 공개 API의 필터 쿼리 문법은 `filter[field][operator]=value` 형식을 사용한다.
- `string`은 `eq`, `contains`를 지원한다.
- `contains`는 영문 대소문자를 구분하지 않는다.
- `number`, `date`, `datetime`은 `eq`, `gt`, `gte`, `lt`, `lte`를 지원한다.
- `boolean`과 `url`은 `eq`를 지원한다.
- 필드 타입에 허용되지 않은 연산자를 사용하면 `400 Bad Request`를 반환한다.
- 한 요청에 여러 필터 조건을 전달할 수 있으며 모든 조건은 `AND`로 결합한다.
- `OR`와 괄호를 이용한 조건 조합은 MVP에서 지원하지 않는다.
- 모든 필드 타입에 실제 `null` 여부를 조회하는 `is_null=true|false` 필터를 제공한다.
- 빈 문자열, `없음`, `미정` 등 원본 값은 실제 `null`과 합치지 않으며 `is_null` 대상이 아니다.
- 별도의 검색 필드 추천·선택 기능은 제공하지 않는다. 스키마의 사용자 필드는 지원하는 타입의 연산으로 필터·정렬할 수 있으며 시스템 필드도 사용할 수 있다. 인덱스는 서버의 내부 구현으로 관리한다.
- `GET /api/projects/{project_id}/v{schema_version}/records/{record_id}` 단건 조회를 제공하고 해당 레코드가 없으면 `404 Not Found`를 반환한다.
- 목록 및 단건 조회에는 선택적인 `fields` 파라미터를 제공해 반환할 사용자 정의 필드를 제한할 수 있다.
- `fields`를 사용해도 `record_id`, `source_id` 등 필수 시스템 식별 필드는 항상 반환한다.
- 존재하지 않거나 요청할 수 없는 필드를 `fields`에 지정하면 `400 Bad Request`를 반환한다.
- API 오류 응답은 `error.code`, `error.message`, `error.details`, `error.retryable`을 포함한다. 로그에는 job_id 등 작업 식별자를 사용한다.

### 2.18 상태, 프로젝트 소유권 및 알림

- MVP에서는 프로젝트마다 소유자 한 명만 존재한다.
- 프로젝트 멤버 초대, 공동 관리 및 `Owner`·`Editor`·`Viewer`와 같은 역할별 권한은 지원하지 않는다.
- 프로젝트 소유자가 출처, 스키마, 커넥터 및 API 키를 모두 관리한다.
- 출처 수집기 상태는 `정상`, `수집 중`, `확인 필요`, `지원 불가`로 구분한다.
- 프로젝트 커넥터 상태는 `정상`, `확인 필요`, `승인 대기`로 구분한다.
- 프로젝트 커넥터의 `승인 대기`는 최초 설정 또는 스키마 변경 후보가 샘플 검증을 통과해 프로젝트 소유자의 검토와 승인만 남은 상태를 뜻한다. 스키마를 유지하는 규칙 복구는 승인 대기 없이 자동 적용한다.
- `확인 필요`는 실제 빈 목록 여부를 판단해야 하거나, 자동 복구 후보 생성·검증에 실패했거나, 사용자가 후보를 거절해 수동 판단 또는 고급 설정이 필요한 상태를 뜻한다.
- 레코드 검증 상태는 `정상`, `검토 필요`로 구분한다.
- API 스키마 상태는 `활성`, `승인 대기`, `전환 중`으로 구분한다.
- 0건 감지 시에는 복구 여부와 무관하게 대시보드에 즉시 문제를 표시하고 이메일 알림 설정이 켜져 있으면 이메일을 발송한다. 리비전 중에는 전체 교체를 보류하고 기존 API를 유지한다. 사용자는 재확인 또는 출처 삭제를 선택한다. 0건 이외 오류는 기존 오류·복구 정책을 따른다.
- 자동 처리 결과 `승인 대기`로 전환되면 대시보드에 표시하고 이메일 설정에 따라 대상과 원인을 발송한다.
- 자동 복구에 실패해 `확인 필요`가 유지되거나 사용자 판단이 필요한 경우 대시보드에 표시하고 이메일 설정에 따라 발송한다. 서비스 내부 알림 목록·읽음 기능은 제공하지 않는다.
- 같은 문제의 중복 이메일은 반복 발송하지 않는다. 0건의 최초 감지는 즉시 알리며, 다른 오류는 사용자 조치가 필요한 상태를 기준으로 알린다.
- 정상 수집 완료, 실행 유형별 시간 제한에 따른 정상 종료와 변경 없음 조기 종료에는 이메일 알림을 발송하지 않는다. 결과는 대시보드에서 확인한다.
- 같은 문제 상태가 계속되는 동안 동일 이메일을 반복 발송하지 않는다.
- 문제가 해결된 뒤 같은 상태가 다시 발생하면 새로운 알림과 이메일을 발송한다.
- 사용자는 프로젝트별로 이메일 알림을 켜거나 끌 수 있다.

### 2.19 저장 데이터와 출처 간 중복

- 전체 페이지 본문을 담는 `raw_text`는 별도로 저장하지 않고 사용자가 승인한 스키마 필드만 정규화 데이터로 저장한다.
- 각 레코드에는 nullable `source_url`과 마지막 수집 시각을 저장한다. `source_url`은 해당 항목을 직접 열 수 있다고 확인한 절대 URL만 저장한다. 클릭·모달처럼 항목에 직접 접근 가능한 URL이 없거나 확인할 수 없다면 null이다. 여러 항목을 담는 목록 URL로 대체하지 않는다. 상세 화면 수집은 항상 브라우저로 수행하며 URL이 없더라도 클릭 규칙을 사용한다.
- 정상 추출된 필드의 원본 문자열, DOM 위치 및 선택자 일치 결과를 레코드마다 중복 저장하지 않는다.
- 정상 필드의 현재 원문은 출처의 최신 스냅샷 세트에서 확인하며, 이전 스냅샷이 교체된 뒤에는 오래된 레코드의 당시 원문을 복원하거나 증명하지 못할 수 있음을 MVP 제한사항으로 허용한다.
- 추출 또는 변환 실패가 발생한 필드에 한해서 원본 값과 실패 원인을 검증 정보로 보관한다.
- 서로 다른 출처에서 의미상 같은 게시물이 발견되더라도 출처 간 자동 병합이나 중복 제거를 수행하지 않는다.

### 2.20 API 키와 호출 제한

- API 키는 프로젝트 범위의 읽기 전용 키로만 제공하며 다른 프로젝트의 데이터에는 접근할 수 없다.
- 프로젝트별 API 키 발급 개수 제한은 두지 않으며 각 키에 용도를 구분하는 이름을 붙일 수 있다.
- API 키의 비밀값은 생성 시 한 번만 표시하고 서버에는 검증 가능한 해시만 저장한다.
- API 키에는 MVP 단계에서 자동 만료일을 두지 않는다. 프로젝트 소유자는 키를 즉시 폐기할 수 있고 화면에서 마지막 사용 시각을 확인할 수 있다.
- API 키 재발급과 자동 교체 기능은 제공하지 않는다. 키를 교체하려면 새 키를 발급해 클라이언트에 적용한 뒤 기존 키를 사용자가 직접 폐기한다.
- API 호출은 키당 분당 60회로 제한한다.
- 호출 제한을 초과하면 `429 Too Many Requests`와 재시도 가능 시각을 나타내는 `Retry-After` 헤더를 반환한다.

### 2.21 운영 정보, 로그 및 보안

- 출처 목록에는 마지막 실행 시각, 다음 실행 시각, 실행 시간, 수집 건수 및 실행 결과 상태를 표시한다.
- 수집 실행 요약과 오류 로그는 30일간 보관한다.
- 운영 로그에는 실행 시각, 단계, 상태, 건수 및 오류 요약만 기록하고 HTML 원문, 전체 필드값 및 API 키 원문은 기록하지 않는다.
- 추출 또는 변환 실패 필드의 원본 문자열은 해당 레코드와 필드의 검증 정보에 7일간 보관한다. Analysis 검증 샘플과 Crawler·Ingestion의 필드 실패 원본은 임시 S3 sidecar로 보관해 Control의 검증 정보에 기록하며 SQS에는 원문을 싣지 않는다. 참조와 만료 시각을 함께 저장해 만료 전 누락과 정상 만료를 구별한다. S3 저장 장애는 기술 재시도·DLQ 대상이다. sidecar도 실패 시각 기준 7일 후 제거하고 승인 샘플의 불변 참조가 그 기간을 연장하지 않는다.
- 동일 레코드의 동일 필드에서 실패가 반복되면 과거 원본 복사본을 쌓지 않고 최신 실패 원본과 발생 시각으로 교체한다.
- 최신 실패 원본은 마지막 실패 발생 시각부터 7일이 지나면 삭제한다.
- 원본 문자열을 제외한 필드명, 실패 원인, 발생 시각, `connector_revision` 및 오류 집계는 오류 로그 정책에 따라 30일간 보관한다.
- 실패 원본의 7일 보관 정책은 검증 정보에 복사한 원본 문자열에 적용하며, 출처 단위 최신 스냅샷 세트의 교체·삭제 정책과는 구분한다.
- 프로젝트·출처·스키마 설정 변경과 승인, API 키 발급·폐기 같은 운영 감사 이벤트는 30일간 보관한다.
- MVP에서는 별도의 사용자용 감사 로그 화면을 제공하지 않고 운영 문제 조사에 사용한다. 단일 소유자 구조이므로 사용자별 변경자 추적은 필수 범위로 두지 않는다.
- 수집 대상 URL은 공개 `http` 및 `https` 주소만 허용한다.
- DNS 확인 결과를 포함해 localhost, 루프백 주소, 사설 IP 대역, 링크 로컬 주소 및 클라우드 메타데이터 주소로 향하는 접근과 리다이렉트를 차단한다.
- 데이터베이스와 운영 백업은 저장 시 암호화한다. API 키 원문은 백업을 포함해 어디에도 저장하지 않는다.
- 운영 백업은 7일간 보관하며 전체 서비스의 장애 복구 목적으로만 사용한다. 사용자가 삭제한 개별 레코드, 커넥터 또는 과거 스냅샷을 복구하는 기능으로 제공하지 않는다.
- 프로젝트의 현재 레코드는 프로젝트가 유지되는 동안 보관하되 승인된 스키마 리비전의 데이터 전환 시 재수집 결과로 교체한다. 제품 기능으로 레코드 수나 저장 용량 상한을 두지 않는다.
- 프로젝트 또는 출처 연결 삭제처럼 물리 삭제가 확정된 데이터는 비동기 정리 작업으로 삭제할 수 있으며, 삭제 완료 전까지 외부 API와 일반 사용자 화면에는 노출하지 않는다.
- 레코드 변경 이력과 삭제 이력은 보관하지 않고, 출처별 스냅샷은 최신 세트 하나만 유지한다.
- API 성능 목표는 프로젝트당 레코드 최대 10만 건, 인덱싱된 검색용 사용자 정의 필드 최대 10개, 일반 운영 부하를 기준으로 측정한다.
- 위 10만 건은 성능 시험 조건이며 프로젝트 레코드 저장 한도가 아니다.
- 위 조건에서 목록 조회는 `limit=100`일 때 p95 500ms 이내, `limit=500`일 때 p95 2초 이내를 잠정 목표로 한다.
- 성능 수치는 초기 운영 결과와 인프라 규모를 바탕으로 다시 조정할 수 있는 목표이며 기능 보장값으로 간주하지 않는다.

### 2.22 API 사용 안내

- 프로젝트 화면에서 현재 활성 API 경로, 인증 방법, 스키마 필드와 타입을 확인할 수 있는 간단한 사용 안내를 제공한다.
- 사용 안내에는 필터, 정렬, 커서 페이지네이션, `limit`, `fields` 파라미터 설명과 대표 `curl` 요청 예시를 포함한다.
- 공통 오류 응답 형식과 주요 HTTP 상태 코드의 의미를 함께 안내한다.
- MVP에서는 Swagger UI, OpenAPI 파일 배포 및 언어별 SDK를 제공하지 않는다.

### 2.23 수집 허용 범위

- 로그인 없이 접근 가능한 공개 페이지와 `robots.txt`가 허용하는 범위만 수집한다.
- 로그인, 세션, 쿠키, 캡차 또는 접근 차단을 우회하지 않는다.
- 출처를 등록하는 사용자는 해당 공개 데이터를 수집하고 이용할 책임이 자신에게 있음을 확인한다.
- 서비스는 민감정보나 개인정보를 수집하기 위한 용도로 사용하지 않는 것을 기본 원칙으로 한다.
- MVP에서는 개인정보 자동 탐지, 사이트별 자동 허용 목록 및 별도의 삭제 요청 포털을 제공하지 않는다.

### 2.24 AWS 배포 아키텍처

전체 시스템은 역할이 분리된 마이크로서비스를 AWS ECS에 독립 서비스로 배포한다.

```text
사용자
  ├─ Vercel ─ 웹 프런트엔드
  └─ ALB ─ Auth Service / Control Service / Data Service

Control Service ─ Analysis Service (브라우저 분석·AI·샘플 검증)
EventBridge Scheduler ─ 정기 실행 요청 큐 ─ Control Service
                                              ├─ Ingestion 내부 API ─ RDS 최신값 조회
                                              └─ 수집 작업 큐 ─ Crawler Service ─ S3 스냅샷
Control Service ─ 적재 작업 큐 ─ Ingestion Service ─ RDS PostgreSQL

공통 운영 구성: ElastiCache Redis / SQS DLQ / ECR / Secrets Manager / CloudWatch
```

서비스 경계:

- `Auth Service`는 사용자 인증과 서비스 접근 토큰을 담당한다.
- `Control Service`는 프로젝트, 공유 출처, 스키마 후보, 매핑, 커넥터 리비전, 수집 작업 및 사용자 승인을 담당한다.
- `Data Service`는 프로젝트 API 키를 발급·조회·폐기·검증하고 활성 스키마 버전의 레코드 목록·단건 조회, 필터, 정렬 및 커서 페이지네이션을 제공한다.
- `Analysis Service`는 브라우저 기반 초기 분석, AI 후보 생성, 목록·상세 탐색 및 추출 샘플 검증, 후보 revision별 샘플의 S3 저장, 사용자 수정의 재검증과 복구 후보 생성을 담당한다. 정상 수집의 각 레코드마다 AI를 호출하지 않는다.
- `Crawler Service`는 승인된 규칙에 따른 HTTP·브라우저 목록과 브라우저 고정 상세 수집, 실행 시간 제한, 탐색 실패 관찰과 스냅샷 생성을 담당한다.
- `Ingestion Service`는 프로젝트 커넥터 실행, 타입 변환과 검증, 일반 수집 데이터 비교·저장, 리비전 데이터 세트 준비·교체 및 `dataset_revision` 갱신을 담당한다.
- Crawler가 페이지 또는 5개 항목 묶음별로 프로젝트 완료 여부를 판단한다. Control은 출처 단위 작업 원장, 결과 집계와 복구 요청을 관리한다. 구간별 스냅샷을 Ingestion에 전달하지 않는다.
- 각 서비스는 독립적으로 배포하고 장애 범위를 분리하되, 프로젝트와 수집 작업의 상태는 명시적인 식별자와 메시지로 연결한다.
- 외부 ALB는 `/auth/*`, `/control/*`, `/api/*`를 각각 Auth Service, Control Service, Data Service로 전달하며 `/internal/*`는 외부에 공개하지 않는다.

비동기 처리와 일정:

- `EventBridge Scheduler`가 출처 단위 정기 수집을 시작하고 실제 작업은 `SQS` 큐를 통해 전달한다.
- 수동·최초 수집 작업과 정기 수집 작업의 우선순위를 큐 소비 정책으로 적용한다.
- 처리에 반복적으로 실패한 메시지는 `DLQ`로 이동해 정상 작업과 분리한다.
- 메시지에는 작업·대상·규칙 revision과 필요한 참조를 넣는다. Crawler 수집 요청에는 예외적으로 Control이 조회한 프로젝트별 최신 데이터 최대 3개의 사용자 컬럼값을 포함한다. HTML 원문, API 키 및 비밀값은 포함하지 않는다.
- 작업 상태와 중복 실행 방지는 데이터베이스의 작업 기록을 기준으로 관리하며, 작업 생성과 메시지 발행 사이의 불일치는 outbox 방식으로 방지한다.

데이터 저장소:

- `RDS PostgreSQL`은 사용자·프로젝트·출처·스키마·커넥터·작업 메타데이터와 프로젝트별 정규화 레코드를 저장한다.
- S3는 출처별 임시 분석 결과, 출처별 최신 수집 스냅샷, 승인 전 후보 revision별 분석 샘플값을 서로 다른 객체로 보관한다. 분석 DOM 원본과 프런트엔드 정적 파일은 보관하지 않는다.
- `ElastiCache Redis`는 인증·권한·프로젝트·스키마 등 반복 조회 데이터의 캐시와 이메일 인증번호·인증 완료의 만료되는 임시 상태에 사용한다. 인증 임시 상태는 Redis에서 직접 관리하며 RDS 인증번호 테이블을 만들지 않는다. 계정 등 영구 데이터의 원본은 RDS에 둔다.
- Redis를 사용할 수 없을 때도 영구 데이터는 RDS를 기준으로 조회할 수 있어야 한다.

네트워크와 운영 구성:

- 프런트엔드는 Vercel에 배포하며 S3를 프런트엔드 원본으로 사용하지 않는다.
- 외부 API 요청은 하나의 ALB가 경로에 따라 외부 요청을 받는 서비스로 전달한다.
- ALB와 NAT Gateway는 퍼블릭 서브넷에, ECS 서비스는 프라이빗 애플리케이션 서브넷에, RDS와 Redis는 프라이빗 데이터 서브넷에 배치한다.
- 크롤링 대상 웹사이트와 외부 AI API로 나가는 통신은 NAT Gateway를 사용하고 S3 접근에는 VPC Gateway Endpoint를 사용한다.
- 컨테이너 이미지는 ECR에 저장하고 비밀값은 Secrets Manager로 관리하며 서비스 로그와 지표는 CloudWatch에 수집한다.
- 로컬 개발 환경은 Docker Compose로 구성하고 AWS 배포 환경은 동일한 서비스 경계를 유지한다.
- ECS 태스크 수, 워커 수, CPU·메모리와 전체 동시 실행 상한은 배포 환경에서 조정하는 운영 설정으로 두며 제품 스펙에 고정하지 않는다.

### 2.25 파싱과 커넥터 실행 경계

- 파싱은 `구조 파싱`, `값 파싱`, `타입 변환과 검증`의 세 단계로 구분한다.
- `Analysis Service`는 초기 설정과 복구에서 반복 목록·레코드 경계·상세 이동 및 다음 목록 이동 후보를 분석하고 selector·변환 규칙 후보를 검증한다.
- `Crawler Service`는 승인된 목록·상세 탐색 규칙을 실행하고 실행 중 관찰한 탐색 결과와 실패를 기록한다.
- 최초 설정·스키마 변경에서 사용자가 승인한 규칙과 자동 힐링 검증을 통과한 규칙은 프로젝트 커넥터 정의에 저장한다.
- Analysis·Crawler·Ingestion은 Java 21·Spring Boot를 사용한다. Analysis·Crawler의 현재 구현은 설정 및 리소스 연결 확인 골격이며 업무 기능과 공통 파서는 아직 구현하지 않았다.
- 세 서비스가 포함하는 공통 Java `ConnectorParser` 모듈은 최종 스냅샷에 승인된 selector와 `parser.code` 및 공통 타입 변환 규칙을 적용한다. 문자열을 자동으로 공백 정규화하지 않는다. 별도 값 가공이 없으면 `parser`는 null이다.
- `ConnectorParser`는 HTML 파서의 엔티티 해석, 승인된 parser.code에 따른 필드별 값 가공과 `number`·`boolean`·`date`·`datetime`·`url` 타입 변환 및 실패 정보 생성을 담당한다. Analysis의 샘플 검증과 Crawler의 최신값 비교도 같은 파싱 결과와 정규화 기준이 필요하며 공통 Java 모듈로 공유한다. 생성 코드는 별도 격리 작업자 없이 각 서비스 JVM에서 실행한다. 생성 Java 코드는 해당 서비스의 권한과 메모리를 공유하므로 파일·네트워크 접근, 무한 반복과 메모리 고갈이 서비스에 영향을 줄 수 있다. MVP에서 이를 별도 샌드박스로 차단하거나 강제 종료한다고 보장하지 않는다.
- 정상 수집에서는 레코드마다 AI를 호출하지 않고 승인된 결정적 규칙만 반복 실행한다.
- 별도의 Parser 마이크로서비스는 만들지 않고 공통 Java 모듈을 Analysis·Crawler·Ingestion에 포함하는 방향으로 구현한다. 생성 코드는 각 서비스 JVM에서 실행하며 공통 모듈의 입력·출력과 세 서비스의 결과 일치를 검증한다.
- 구조 파싱 실패는 공유 출처 문제로, 프로젝트별 값 파싱과 타입 변환 실패는 해당 프로젝트 커넥터 문제로 처리한다.

### 2.26 서비스 간 통신과 작업 메시지

- 사용자 요청과 즉시 확인이 필요한 최신 데이터 조회는 API로 처리한다. 분석·수집·적재·리비전 데이터 준비와 결과 전달은 SQS를 사용한다.
- 통신 경로: Scheduler → 정기 요청 큐 → Control → Ingestion 내부 최신 데이터 조회 → Control → Crawler 수집 큐 → Crawler → Control 결과 큐 → Ingestion 적재 큐 → Control 결과 큐.
- Control은 출처의 활성 프로젝트, 작업 원장 및 승인된 revision을 확인한다. Ingestion은 각 프로젝트·출처별 record_id가 큰 순서의 최신 데이터 최대 3건과 사용자 컬럼값을 반환한다. 1~2건은 존재하는 만큼, 0건은 빈 목록으로 반환하며 조회 실패는 0건과 구분한다.
- Control은 작업 발행 전에 최신 컬럼값과 규칙을 Crawler 메시지에 넣는다. 수동·최초 작업과 정기 작업은 별도 큐로 구분하고 기존 3:1 소비 정책을 적용한다. 비교 기준은 발행 시점 값이며 관련 적재가 끝날 때까지 동일 출처의 다음 논리 작업을 대기시킨다.
- 초기 분석, 수정 후 재검증, 탐색 복구 및 커넥터 복구는 Control이 Analysis 작업 큐로 요청하고 Analysis가 후보·검증 결과 또는 실패를 Control 결과 큐로 반환한다. 사용자 승인 대상과 자동 복구는 상태로 구분한다.
- Crawler 또는 Ingestion은 각자 감지한 추출·파싱·변환 실패의 현상·단계·영향 범위를 Control에 알린다. Control은 공유 탐색 실패와 프로젝트별 필드 처리 실패를 구분하고 필요한 기준을 준비해 Analysis에 복구를 요청한다. 근본 원인은 미리 확정하지 않으며 접근 차단과 일시 기술 오류는 별도로 처리한다.
- Crawler는 종료 사유와 해당하는 경우 최종 S3 스냅샷 참조를 Control에 전달한다. Control은 적재 가능한 프로젝트별로 Ingestion 작업을 발행한다. Ingestion은 S3의 최종 스냅샷을 읽어 프로젝트별 추출·검증·저장을 수행하고 결과를 Control에 반환한다. 목록 항목 선택자는 저장된 DOM에서 Crawler와 Ingestion 양쪽이 동일한 순서·결과로 해석할 수 있어야 하며 불일치하면 임의 매칭하지 않는다. 중간 구간 스냅샷은 전달하지 않는다.
- 사용자 승인 스키마 변경은 Control → Crawler 출처별 리비전 수집 → Ingestion 새 데이터 세트 준비·결과 → 전체 출처 조건 확인 및 데이터·API 버전 교체 순서로 조정한다. 일부 출처 실패 또는 0건이면 교체를 보류하고 기존 API를 유지한다. 0건은 즉시 문제 표시 및 이메일 설정에 따른 알림 대상이고, 그 외 복구 가능한 오류는 먼저 자동 복구를 시도한 뒤 사용자 조치가 필요하면 알린다.
- 결과 이벤트의 공통 정보는 event_id, event_type, job_id, occurred_at, format_version이다. 분석 결과에는 analysis_id와 후보 revision을 포함하고, source_id·project_id·snapshot_ref는 상황별로 포함한다. 동일 이벤트의 재발행은 같은 event_id를 유지한다. Scheduler 정기 신호에는 아직 job_id가 없을 수 있다.
- 결과 큐는 Control이 소비한다. SQS 표준 큐의 중복·순서 역전을 전제로 작업 원장, event_id와 적재 receipt로 중복 처리한다. 각 상황의 세부 필드와 내부 API 경로는 구현 계약으로 정한다.
- 초기 큐는 정기 실행 요청, Analysis 작업, 수동·최초 수집, 정기 수집, Ingestion 작업, Control 결과 큐로 구성한다. 기술적 재처리 실패를 격리하는 DLQ를 운영한다.
- 메시지 유형은 다음 상황을 모두 구분한다. 아래 이름은 구현을 위한 초안이며, 메시지 종류를 물리적으로 각각 별도 큐로 분리한다는 뜻은 아니다.
  - Scheduler → Control: 정기 수집 신호. 수동·최초 요청은 Control API 또는 내부 작업 생성으로 접수한다.
  - Control → Analysis 및 결과: 최초 분석, 사용자 수정 재검증, 승인 전 HTTP 비교, 탐색 복구, 커넥터 복구. Analysis는 출처별 중간 분석 결과와 후보 revision별 검증 샘플을 구분해 S3에 저장하고 후보·검증·실패 결과와 analysis_id·revision을 Control에 반환한다. 샘플값은 메시지로 전달하지 않는다.
  - Control ↔ Ingestion 내부 API: 프로젝트·출처별 최신 데이터 조회 요청과 정상 응답 또는 조회 실패. 정상 0건은 조회 실패가 아니다.
  - Control → Crawler: 최초·수동·정기·리비전 수집 요청. 최신 사용자 컬럼값과 규칙 revision을 포함한다.
  - Crawler → Control: 수집 중 오류 감지와 회차 종료 결과. 공유 탐색·프로젝트 커넥터·기술 오류·접근 차단의 영향 범위를 구분하고 필요한 경우 스냅샷 참조를 제공한다.
  - Control → Ingestion 및 결과: 프로젝트별 일반 스냅샷 적재 또는 사용자 승인 리비전 결과 준비·교체와 각각의 성공·실패 결과.
  - 사용자 ↔ Auth·Control·Data: 로그인, 설정·승인·작업 상태 조회, 저장 데이터 조회는 사용자 요청에 따른 API 통신이다. Control의 상태 알림·이메일은 승인 대기나 확인 필요 시 실행하며 이메일 설정을 따른다.
- 서비스 작업 메시지 예시에는 공통 envelope와 메시지별 payload를 구분한다. Scheduler의 정기 신호는 Control의 job_id 생성 전이므로 공통 작업 메시지와 동일하지 않을 수 있다. 전송 실패 시 작업을 실패로 처리하고 비교값을 임의로 잘라서 보내지 않는다.

#### 통신 상황별 송신·수신 목록

아래는 통신이 필요한 경우와 각 주체의 처리 내용을 정리한 것이다. SQS와 API는 송신 주체 옆에 표시하며, 여러 행은 순차 단계가 아니라 별도 상황일 수 있다.

**초기 분석과 사용자 수정**

| 발생 상황 | 송신 → 수신 | 전달 내용과 처리 |
|---|---|---|
| 프로젝트 생성 | 사용자 → Control (API) | 이름·목적·출처 URL·이메일 설정 접수; project_source_id 생성 |
| 초기 분석 시작·재요청 | 사용자 → Control (API) | 프로젝트별 분석 요청; 진행 중인 동일 분석은 기존 상태 반환 |
| 출처별 초기 분석 | Control → Analysis (SQS) | 프로젝트·출처·목적과 분석 작업 전달 |
| 출처별 중간 결과 저장·조회 | Analysis ↔ S3 | 필드 후보·샘플·선택자·이동 후보 저장 후 공동 추천에 사용 |
| 후보 샘플 저장 | Analysis → S3 | 검증한 analysis_id·revision·프로젝트·출처별 샘플 저장 |
| 초기 분석 결과 | Analysis → Control (SQS) | 후보·출처별 성공/실패와 revision 전달; 샘플값은 S3 참조 |
| 분석 상태·후보 조회 | 사용자 → Control (API) | 진행 상태·스키마·출처별 규칙·검증 결과·샘플 함께 조회 |
| 후보 샘플 조회 | Control → S3 | analysis_id·revision·프로젝트·출처에 맞는 샘플 조회 |
| 실패 출처 재시도 요청 | 사용자 → Control (API) | analysis_id·project_source_id로 실패 출처 지정 |
| 실패 출처 재분석 요청 | Control → Analysis (SQS) | 대상 출처와 기준 후보 revision을 전달해 재분석 |
| 재시도 결과 | Analysis → Control (SQS) | 출처별 성공/실패·후보 및 검증 정보 전달 |
| 성공 출처의 공동 후보 반영 | Control → Analysis (SQS) | 기존 사용자 수정을 보존하며 매핑·샘플 반영과 검증 요청 |
| 실패 출처 제외 | 사용자 → Control (API) | 출처를 후보에서 제외하고 남은 출처로 진행 |
| 설정 수정 | 사용자 → Control (API) | 필드·CSS·파싱·이동 규칙과 기준 revision 전달 |
| 재검증 필요 판단 | Control 내부 처리 | 변경 revision 기록; 변경 범위에 따라 검증 무효화·승계 판단 |
| 수정 재검증 요청 | Control → Analysis (SQS) | 필요할 때 새 revision과 대상 출처·규칙 전달 |
| 재검증 결과 | Analysis → Control (SQS) | S3 샘플 저장 후 revision·출처별 검증 결과 전달 |

### 2.27 API 계약 정리

- `{p}`는 project_id, `{s}`는 프로젝트 출처의 project_source_id, `{a}`는 analysis_id, `{j}`는 job_id, `{k}`는 key_id, `{v}`는 schema_version, `{r}`은 record_id다. 공유 출처 source_id는 수집·공유를 위한 별도 내부 식별자이며 `{s}`와 혼동하지 않는다.
- URL을 입력하면 ProjectSource의 project_source_id가 먼저 발급된다. 공유 출처 분석이 끝나면 기존 또는 신규 SharedSource의 source_id를 연결한다. 여러 프로젝트의 ProjectSource가 하나의 SharedSource를 참조할 수 있다.
- 웹은 Bearer access JWT를 사용하고 각 API가 공개키·서명·만료 등을 검증한 뒤 프로젝트 소유권을 확인한다. 외부 Data API는 프로젝트 범위의 X-API-Key를 사용한다. 로그인·갱신 시 access_token과 csrf_token, HttpOnly Secure refresh 쿠키를 발급·회전한다. refresh와 logout에는 X-CSRF-Token이 필요하다. 일반 로그아웃은 refresh 세션을 폐기하고 이미 발급된 access token은 짧은 잔여 유효시간을 허용한다. 탈퇴 진행 계정은 유효한 기발급 access token이 있어도 서버에서 접근을 차단한다. 계정·키 원본 상태를 확인할 수 없으면 접근을 거절한다. token 유효시간은 운영 설정이다.
- 회원가입과 비밀번호 초기화는 이메일로 보낸 6자리 인증번호를 사용한다. Auth는 인증번호와 검증 후 인증 완료의 임시 상태를 이메일·인증 목적에 따라 Redis에서 관리하며, 회원가입 전에도 확인할 수 있어야 한다. Redis 장애·상태 유실 시 인증 성공으로 처리하지 않는다. 가입·초기화 인증번호는 5분·최대 5회이며 일회용 인증 증명은 10분이다. 재발송 시 기존 번호와 증명은 무효화한다. DB 처리 실패 시 소비한 증명은 재사용하지 않고 재인증한다. 탈퇴하면 계정 및 소유 프로젝트·수집 데이터·API 키·출처 연결을 삭제한다. 다른 프로젝트가 사용하는 공유 출처는 유지한다. 프로젝트 정보가 들어간 공유 manifest·작업 결과와 대기/DLQ 메시지는 다른 프로젝트 처리 및 재전달 가능 기간 종료 후 정리하고, 필요한 공유 manifest는 삭제 대상 참조를 뺀 새 객체로 전환한다. 전체 정리 전에는 삭제 완료로 표시하지 않는다.
- 비동기 요청은 job_id를 반환한다. 분석 시작은 analysis_id도 반환하며, 프로젝트 생성 후 동일 프로젝트에서 초기 분석을 다시 요청할 수 있다. 진행 중 분석이 있다면 중복 실행을 만들지 않고 기존 분석을 반환한다. 이벤트 식별자 event_id는 내부 메시지용이다.

- 프로젝트 생성은 이름·수집 목적·출처 URL·이메일 알림 여부를 한 번에 받으며 분석은 별도 요청으로 시작한다. 분석 결과를 기다리는 동안 GET 분석 조회를 반복한다. 중단 후 재진입할 수 있도록 프론트엔드는 analysis_id를 보관하고 같은 프로젝트에서 분석을 다시 요청할 수 있다.
- 분석 생성 mode는 `initial`, `schema_revision`, `source_attachment`다. 신규 출처는 기존 프로젝트의 활성 스키마에 맞춰 분석한다. 기존 구조 변경이 필요하면 스키마 리비전과 사용자 확인을 거친다.
- 분석 조회가 상태, 후보 설정과 출처별 샘플을 함께 반환한다. 샘플은 Control이 S3에서 읽는다. 추출·이동 결과에 영향을 주는 후보 수정은 이전 검증을 무효화하고 서버가 자동 재검증한다. 표시 순서만 바꾸는 등 영향이 없는 수정은 기존 검증을 승계한다. 승인 시 요청 revision이 현재 후보 및 통과한 검증 revision과 같아야 한다. 클라이언트에서 별도 검증 요청을 보내지 않는다.
- 초기 분석에서 실패 출처는 해당 project_source_id로 재시도하거나 후보에서 제외할 수 있다. 재시도에 성공한 출처는 공통 추천 후보에 다시 반영하고 영향을 받은 후보를 재검증한다. 실패가 이어지면 사용자가 제외할 수 있다.
- 출처 추가는 등록 후보 생성과 기존 스키마 기준 분석·검증 후 최종 후보 승인으로 반영한다. 출처 삭제 요청은 편집 중인 analysis_id와 expected_revision을 지정해 삭제 후보만 표시하고 최종 승인 후 해당 프로젝트의 연결과 데이터를 정리한다. 삭제만 있고 스키마가 바뀌지 않으면 남은 출처를 재수집하지 않는다. 스키마 유지 상태에서 추가와 삭제가 함께 있으면 모든 추가 출처의 정상 적재·공개 후 삭제한다. 추가 실패·0건이면 삭제를 보류하고 이미 성공한 추가 출처는 유지한다. 삭제 실패는 추가를 되돌리지 않고 재시도·상태 표시한다. 처리 중 두 출처가 동시에 보일 수 있다. 취소·검증 실패 시 기존 적용 상태와 데이터를 유지한다. 다른 프로젝트의 공유 출처는 삭제하지 않는다.
- 수집 결과가 0건이면 실제 사이트가 빈 경우에도 대시보드에 즉시 문제를 표시하고 이메일 설정이 켜져 있으면 알린다. 사용자 조치가 필요해지면 현재 변경을 END_CHANGE로 닫고 결과가 확인될 때까지 후속 변경 승인을 대기시킨다. 사용자는 재확인 또는 출처 삭제를 선택한다. 0건은 새 데이터가 없거나 DB 기존 데이터가 없는 것과 구분한다. 리비전 중 0건이면 전체 전환을 보류하고 기존 API와 데이터를 유지한다.
- 출처별 상태는 준비 중·적용 보류·완료·확인 필요 등을 제공한다. 프로젝트 수동 수집은 대표 job_id에 각 출처의 성공·실패 상태를 연결한다. 공유 수집 결과는 요청자가 소유한 프로젝트 범위로만 반환한다.

#### Data API

키 관리 API는 사용자 access token을 요구한다. Data가 프로젝트 소유권과 상태를 Control에서 확인한다.

| 메서드 | 경로 | 요청 | 응답·처리 |
|---|---|---|---|
| GET | `/api/projects/{p}/keys` | 없음 | API 키 목록·nullable last_used_at; 비밀값 제외 |

- 같은 조회 경로에 웹 Access Token과 외부 프로젝트 API 키를 각각 허용한다. 로그인한 사용자는 소유 프로젝트를 access token으로 조회한다.

- 반환은 data와 meta(schema_version, dataset_revision, returned_count, next_cursor, has_more)다. 검색 필드 추천·선택·인덱스 상태 조회 API는 없다. 기존 사용자 정의 필드의 타입별 필터·정렬 기능은 유지한다.

## 3. 현재 명시된 MVP 제한사항

- 이미지와 첨부파일을 수집하지 않는다.
- 로그인, 세션, 쿠키, 캡차 및 차단 우회를 지원하지 않는다.
- 사용자 정의 필드의 NOT NULL 설정과 zero value 자동 대체를 지원하지 않는다.
- 비개발자를 위한 시각적 요소 선택 UI, 자연어 수정, XPath 직접 입력과 드래그 매핑은 지원하지 않는다. CSS 선택자 직접 입력·편집을 제공한다.
- 임의 HTML 속성과 스크립트에서 숨은 레코드 ID를 범용적으로 추론하지 않는다.
- URL이 변경된 동일 게시물의 자동 병합을 지원하지 않는다.
- DB에 저장된 데이터와 내용이 다르면 같은 게시물이어도 신규 레코드로 판단하므로 수정 전후 데이터가 함께 남을 수 있다.
- 일반 반복 수집에서 상세 필드를 요구하는 프로젝트는 확인하는 범위의 상세 페이지를 열어 필드값을 비교한다. 중단 조건이나 시간 제한 이후의 상세 페이지는 확인하지 못할 수 있다.
- 시간 제한 후 중단 위치부터 이어서 수집하지 않는다.
- 매 실행을 첫 페이지부터 시작하므로 오래된 페이지가 반복적으로 갱신되지 않을 수 있다.
- 레코드 변경 이력과 삭제 이력을 보관하지 않는다.
- 물리 삭제된 레코드가 다시 발견되면 신규 레코드로 취급한다.
- 이전 출처 수집기·프로젝트 커넥터·스냅샷 세트의 내용과 롤백 기능을 제공하지 않는다.
- 이전 스냅샷이 교체된 뒤 오래된 레코드의 당시 원문 근거를 복원하는 기능을 제공하지 않는다.
- API 키 자동 재발급, 자동 교체 및 자동 만료 기능을 제공하지 않는다.
- Swagger UI, OpenAPI 파일 및 언어별 SDK를 제공하지 않는다.
- 개인정보 자동 탐지와 별도의 삭제 요청 포털을 제공하지 않는다.
- 서로 다른 출처의 동일 게시물을 자동 병합하지 않는다.
- 팀원 초대와 역할별 권한을 제공하지 않는다.
- 웹훅, 문자 및 메신저 알림을 제공하지 않는다.
- CSV·Excel 내보내기와 API 쓰기 기능을 제공하지 않는다.
- 복잡한 `OR` 검색, 괄호 검색식 및 전문 검색을 제공하지 않는다.
- 요금제와 결제 기능은 MVP 범위에서 제외한다.
- 실시간 수집, 사용자별 수집 주기 및 사용자 정의 수집 주기는 제공하지 않는다.

## 4. 아직 결정하지 않은 주요 항목

- 무한 스크롤은 5개씩 비교하며 각 프로젝트의 최신 저장 데이터 최대 3개를 중단 기준으로 한다.
- 상세 필드를 요구하는 프로젝트를 위해 상세 페이지를 수집하는 중 접근 실패 시 비교 불가 항목과 재실행 범위.
- 승인 파서와 공통 타입 변환의 크롤러 비교·인제스천 판정 결과 일치 검증. 필드값이 실제 null인 경우 정상 값으로 취급한다.
- 이동 전후 항목과 진행 상태를 이용한 페이지네이션 순환 감지는 실제 사이트에서 검증한다. 정렬 변화나 고정글로 인한 누락은 MVP의 제한으로 둔다.
- 기존 데이터의 중복 확인은 Ingestion이 담당한다. 스케줄·SQS 중복은 발생할 수 있으며 Control 원장·시도 선점과 Ingestion receipt·Outbox로 처리한다. 각 기록의 보존 기간 수치는 운영 설정이다.
- 변경 없음 조기 종료 시 새 부분 스냅샷 교체와 과거 원문 확인 한계의 사용자 안내 및 상세 검증용 샘플 보관 범위.
- 기존 수집이 끝난 뒤 신규 프로젝트의 최초 수집을 시작하는 작업 예약과 중복 요청 처리 방식.
- 구조·커넥터 오류가 아닌 상대 서버·브라우저의 일시적 실패에 대한 재시도, 실패 스냅샷·미처리 항목 처리 및 사용자 알림 기준. 기존 네트워크 재시도 기준과의 관계를 구체화한다.
- 자동 복구에서 S3 승인 샘플 부족 또는 기준 불일치면 자동 적용하지 않는다. 후보는 최초 포함 최대 3회, 공유 규칙은 모든 영향 프로젝트 통과 시 적용한다. DB 1~2건은 존재하는 데이터 전부가 일치해야 한다.
- 비교·수집을 계속할 수 없는 규칙 관련 실패에서 자동 복구한다. 복구 후보는 최초 포함 최대 3회다. 별도 실패율 임계치는 두지 않으며 기존 오류 정보의 구체 매핑은 구현 시 검증한다.
- `parser.code`는 별도 격리 없이 각 서비스 JVM에서 공통 Java 모듈을 통해 실행한다. 공통 모듈 배포 방식과 세 서비스의 결과 일치는 구현 검증 대상이며 JVM 외부 격리·자원 강제 제한은 MVP에 두지 않는다.
- 스키마 변경 화면은 확보한 후보 샘플을 표시하며 안정적인 동일 레코드 대응을 가정하지 않는다.
- 첫 목록·상세 최대 3건을 전체 5분 내 검증한다. 후보 생성 예산과 HTTP 검증 비용은 실험한다.
- Control 주기 정리의 실행 주기·재발행 보장 기간 수치와 무한 스크롤 항목 경계의 구체적 탐지 방식을 운영 검증한다. 상세 이동 규칙은 필드 커넥터에 저장하며 객체 경로·본문·정리 조건은 S3 저장 명세를 따른다.
- 일반 반복 수집 1분에 인제스천 비교 대기 등 어떤 시간을 포함할지, 실제 출처에서의 성능 검증.
- 작업 발행 시점 최신값을 비교하고 동일 출처의 관련 적재 종료까지 다음 논리 작업을 대기시킨다. 일치 순서·중복값 처리의 구현 시험은 필요하다. 완료된 프로젝트의 뒤쪽 새 데이터는 놓치는 것으로 허용한다.
- CSS 선택자와 텍스트·속성 추출의 구체적 지원 범위.
- 실제 null과 실패 구분을 유지하며 실패 레코드는 저장·정상 추출 건수에서 제외한다. 비교에는 승인 parser.code와 공통 타입 변환 결과를 사용한다.
- 일반 수집의 누락 레코드는 마지막 페이지까지 확인해도 자동 삭제하지 않는다. 사용자 승인 출처·프로젝트 삭제 및 리비전 교체는 별도다.
- 신규 데이터 일부를 반영하고 조기 종료하거나 프로젝트 일부가 실패한 경우의 원자적 반영과 `dataset_revision` 정책.
- 리비전 준비 중 실패·취소된 작업 데이터 정리, 공개 버전·스키마 조회 일관성 및 중복 요청·부분 실패 복구의 세부 구현.
- 복구 후 수집의 시간 제한과 영향받지 않는 프로젝트의 처리.
- 동일 공유 출처는 정규화한 URL·범위·초기 동작·이동 규칙이 정확히 일치할 때만 공유한다. 직렬화 구현을 검증한다.
- 탐색 후보 평가에 Jev를 도입할지와 검증 방법.

## 7. 79개 흐름 점검 후 확정한 연결 계약

이 절은 이전 19개 선택과 후속 10개 연결 결정을 구체화한다. 기능은 구현 전이며 공통 파서 결과 일치·타입별 JSONB 쿼리·버전 전환은 통합 시험한다. 기존 2절의 관련 표와 메시지·ERD도 같은 계약을 따른다.

### 7.1 인증과 계정

- 가입·비밀번호 초기화는 서로 다른 purpose의 6자리 번호를 Redis에 5분 저장하며 확인은 최대 5회다. 성공하면 이메일·purpose에 묶인 무작위 일회용 증명(가입 verification_token 또는 초기화 reset_token)을 10분 발급한다. 저장소에는 검증 가능한 해시만 둔다. 증명은 각 요청에서 원자적으로 소비하며 DB 실패 또는 응답 유실로 결과를 확인할 수 없으면 재인증한다. 이미 생성된 이메일은 중복 가입을 거절한다. 사용자 display_name 기본값은 이메일의 @ 앞 문자열, account_status는 ACTIVE다.
- 재발송 시 동일 이메일·목적의 기존 번호와 증명을 원자적으로 무효화하고 새 번호를 저장해 발송한다. 공급자 접수 실패 시 해당 발송 시도 번호를 비교 후 무효화하며 이전 번호를 복원하지 않는다. 가입의 202는 공급자 접수를 확인한 결과이며 실제 메일 수신을 보장하지 않는다. 초기화는 계정 존재를 노출하지 않기 위해 존재하지 않는 계정에도 동일 202를 반환할 수 있으므로 202가 실제 발송을 보장하지 않는다. 공급자·발송 빈도 제한의 수치는 운영 설정이다.
- access token과 CSRF token은 웹 메모리에 보관한다. refresh token은 HttpOnly·Secure 쿠키이며 Auth DB의 REFRESH_SESSION에 해시·만료·폐기 상태를 저장하고 원자적으로 회전한다. 웹 재시작 시 자격 증명 포함 GET /auth/v1/csrf로 현재 refresh 세션에 결합된 CSRF 값을 받은 뒤 refresh한다. 해당 응답은 허용된 웹 Origin에만 CORS 허용하고 캐시하지 않는다. 교차 사이트 쿠키가 필요하면 SameSite=None; Secure를 사용한다. 프론트 요청은 단일 refresh를 공유하고 다중 탭 회전 실패나 응답 유실 시 재로그인한다. 세션 발급 기록 실패는 로그인 실패다. 정확한 토큰 TTL은 운영 설정이다.
- 탈퇴는 Auth가 탈퇴 진행 상태·refresh 폐기 후 Control 계정 정리 작업을 멱등 접수한다. 접수 응답 유실은 동일 owner_id로 재조회·재전송한다. 접수 전 확정 실패면 Auth는 진행 상태를 되돌리고 화면에 실패를 표시한다. 접수 여부가 불확실하면 접근 차단 상태를 유지하고 재확인하며 사용 가능하다고 표시하지 않는다. 소유 프로젝트 정리 완료 후 계정을 최종 삭제한다. 작업 상태·권한 확인에 필요한 비식별 최소 원장은 재처리 기간 동안 남긴다.
- 탈퇴 계정의 JWT는 Auth의 계정 원본 상태를, API 키는 Data DB의 키 원본 상태를 최종 확인한다. 캐시 무효화가 불확실하면 원본을 조회하고 원본도 확인할 수 없으면 503으로 거절한다. 완료 후 시작된 요청을 차단하며 이미 권한 검사를 마친 요청의 취소는 보장하지 않는다.

### 7.2 프로젝트·후보·화면 계약

- POST /projects는 Idempotency-Key UUID를 필수로 받는다. 같은 소유자·키·요청 본문 재요청은 같은 project_id를 반환하고 같은 키에 다른 본문이면 409다. 프로젝트와 출처 후보 생성은 같은 DB 트랜잭션이다. 응답 후 웹은 GET sources로 project_source_id를 조회하고 분석을 시작한다. 키·응답 기록은 최소 24시간 유지한다.
- 프로젝트 목록/상세의 current_analysis_id·current_job_id는 없으면 null이다. 서버는 현재 진행·검토 중인 분석을 우선 반환하므로 다른 기기에서도 재진입할 수 있다. 승인 전 후보는 expected_revision으로 취소하고 승인·적용 중은 409다.
- candidate PATCH는 expected_revision과 변경할 fields·source_rules·excluded_project_source_ids만 받는다. 생략 항목은 보존하고 명시된 목록은 각 항목의 field_id/project_source_id로 병합한다. 필드 삭제는 delete_field_ids, 제외 출처 목록은 명시된 전체 목록으로 교체한다. 예상 revision 불일치는 409와 current_revision을 반환하며 전체 후보는 GET으로 재조회한다. 필드·매핑·이동·추출·파싱의 변경은 영향 출처 재검증, 표시 순서만 바뀌면 유효 검증을 승계한다. 승인과 수정은 같은 revision 조건부 DB 갱신으로 직렬화한다.
- Analysis는 공통 필드별 recommendation_reason을 candidate에 담아 analysis.completed로 반환한다. Control은 현재 후보와 S3 샘플을 분석 조회로 제공하며 S3 중간 파일을 웹에 직접 노출하지 않는다. Figma는 상세 이동을 필드별로 설정하고 목록 URL 변경은 출처 삭제·추가를 안내한다. 상세는 브라우저 이동을 사용한다.
- 프로젝트·출처·작업 조회는 프로젝트 소유자 범위의 상태·last_success_at·next_scheduled_at·duration_ms·list_item_count·normal_extracted_record_count를 제공한다. 알 수 없는 수치는 null이며 0으로 바꾸지 않는다. Analysis가 별도 진행 이벤트를 보내지 않으므로 진행 중에는 실제 확인 가능한 상위 상태만 제공하고 출처별 상세 단계는 결과 수신 뒤 갱신한다. 오류는 job_id·출처·code로 묶어 같은 문제가 해결되기 전까지 이메일을 한 번만 보내고 해결 후 재발생 시 다시 알린다.

### 7.3 수집·데이터·API

- 공유 출처는 정규화 URL·목록 범위·초기 동작·목록 이동 설정이 정확히 같을 때만 공유하고 애매하면 별도 출처로 둔다. Control의 비교·생성을 직렬화한다. 최초 분석은 출처별 목록 첫 페이지와 필요한 상세 최대 3건을 검증하며 1~2건이면 존재하는 만큼 확인한다. 상세는 항상 브라우저다. 다음 이동의 예상 변화가 없으면 이동 종류별로 메시지 명세 20.2의 정상 종료·실패 기준을 적용한다. 가상화 DOM의 항목 재선택은 실제 사이트로 검증한다.
- 필드값은 JSONB(field_id→타입별 스칼라 또는 null)로 저장한다. 전역 record_id 시퀀스는 프로젝트별 연속을 보장하지 않으며 동일 프로젝트 쓰기는 상태 행을 잠근다. 각 수집 결과의 역순 저장은 유지한다. 선택된 parser.code만 공백 등의 값 가공을 하며 HTML 파서의 엔티티 해석과 공통 타입 변환은 세 서비스가 공유한다. 생성 코드는 별도 격리 없이 각 서비스 JVM에서 실행한다. 공통 모듈의 결과 일치와 배포 방식은 검증한다. 코드의 무한 반복·자원 고갈 및 서비스 권한 접근에 대한 격리 보장은 없다.
- DB 최신값 조회는 targets에 project_id·project_source_id 쌍을 넣어 Ingestion이 대상별 최대 3건을 조회한다. Data API의 source_id 표시는 Data가 Control의 내부 POST /internal/v1/project-sources:resolve에 project_source_id 목록을 보내 project_source_id·source_id 매핑을 확인한다. 확인 실패 시 503이며 다른 출처를 추정하지 않는다. 삭제 중 늦은 조회는 원본 연결 상태로 차단한다.
- Data는 API 키별 마지막 사용 시각을 Redis에 key_id 단위 최대 시각으로 기록하고 Data DB 키 목록과 함께 반환한다. Redis 실패 또는 사용 이력이 없으면 last_used_at=null이다. 키 원본 상태는 Data DB이며 원본 확인 실패 시 접근을 거절한다.
- 사용자 필드의 number/date/datetime은 스키마 타입으로 파싱해 비교·정렬하며 string contains는 대소문자를 구분하지 않는다. 정렬은 ASC NULLS LAST, DESC NULLS LAST, 동일 값은 record_id 같은 방향을 적용한다. 커서는 schema_version·dataset_revision·필터/정렬 해시·null 여부·정렬값·record_id를 포함한 위변조 방지 불투명 토큰이다. 조건·revision 불일치는 409, 잘못된 토큰은 400이다. 인덱스와 쿼리 성능은 실험해 확정한다.
- 일반 수집에서는 정상 레코드를 적재하고 실패 레코드만 제외한다. 실패로 최신 비교를 완료할 수 없는 프로젝트 출처는 복구 대상으로 둔다. 신규 승인 출처의 실패 시 부분 쓰기는 공개하지 않으며 구조 변경에서는 출처 하나라도 실패·0건이면 전체 전환을 보류한다. 자동 복구는 최초 포함 최대 3회이며 저장 최신값 또는 승인 샘플 기준을 모두 확인하지 못하면 자동 적용하지 않는다. 공유 이동 규칙은 모든 영향 프로젝트 통과 시에만 자동 적용한다.

### 7.4 비동기 작업·삭제·보관

- 최초·리비전 승인 스키마는 Control이 기존 Ingestion 큐로 schema.prepare를 보내 비공개 준비하고 schema.prepared 성공 후 수집한다. schema와 준비 결과는 change_job_id로 묶는다. 구조 변경 적용 시 Control은 프로젝트의 새 일반 수집·적재 발행을 보류하고 진행 중 쓰기 종료를 확인한다. Ingestion이 Data DB에서 공개 스키마·데이터 포인터를 트랜잭션으로 전환하고 Control이 결과를 확인해 새 커넥터를 활성화한 뒤 재개한다. 불확실하면 보류 상태로 결과를 재확인한다. 늦은 쓰기는 Data DB에서 작업·버전을 확인해 거절한다.
- Analysis·Crawler는 job_id·attempt_id로 Control 작업 원장을 선점하고 lease와 SQS visibility를 연장한다. 각 시도는 분리된 S3 경로에 결과를 보관하고 completed payload에 attempt_id를 넣는다. Control은 DB 시간 기준 유효 시도·lease·작업 상태·필요 revision 확인과 결과 채택·후속 Outbox를 한 트랜잭션으로 처리한다. 이전 시도는 채택하지 않는다. Ingestion은 receipt·쓰기·결과 Outbox를 동일 Data DB 트랜잭션에 기록한다.
- Control은 SQS DLQ를 전담 소비하고 command의 job_id로 작업 원장을 확인한다. 한 사본의 DLQ 도착만으로 유효한 다른 실행을 종료하지 않으며 실행이 없으면 재발행 또는 최종 실패·확인 필요를 판단한다. 시작 기한이 지나면 새 시도는 시작하지 않되 이미 시작한 시도는 유효 lease·작업 상태·별도 실행 종료 기한을 확인한다. SQS 재전달·DLQ 보존 기간은 환경 설정이며 결과·수신 기록은 해당 재처리 가능 기간보다 짧게 지우지 않는다. Control의 주기 정리 작업은 실제 실행·참조·재처리 종료를 확인하고 S3 삭제 대상 확정과 새 참조를 직렬화한다. 기존 7일 고아 검사와 승인 샘플·최신 스냅샷 유지 규칙을 따른다.
- 삭제 중 프로젝트는 새 작업과 늦은 쓰기를 차단한다. 데이터·키·연결·전용 S3 및 공유 참조 정리를 모두 끝낸 뒤 완료한다. 조회에 필요한 소유자·job_id·상태만 최소 작업 원장에 남기고 재처리 기간 이후 정리한다. 다른 프로젝트가 사용하는 공유 출처·객체는 유지한다.

- 출처 삭제 영향 건수 조회 실패는 0건이 아니라 확인 불가이며 재조회에 성공하기 전 승인을 보류한다. S3 객체 생성은 채택이 아니며 Control DB가 유효한 Analysis·Crawler 시도를 채택한다. 미완료 lease 만료 시 Control이 시작 기한 내 동일 job을 재발행하고 채택되지 않은 시도 객체는 참조·실행 종료를 확인해 정리한다. 중복 사이트·LLM 실행 가능성은 허용한다.

### 최근 확정: 인증·API 키·이동 규칙

- 비밀번호 초기화 성공 시 Auth는 비밀번호 변경과 해당 계정의 모든 refresh 세션 폐기를 Auth DB의 같은 트랜잭션에서 처리한다. Redis의 일회용 초기화 증명 소비는 별개다. 이미 발급된 access token은 만료까지 유효하며 이후 갱신에는 재로그인이 필요하다. 기기 ID는 요구하지 않는다. 로그인·refresh와 초기화가 동시에 실행될 때는 같은 계정 행 잠금으로 직렬화하고 변경된 비밀번호와 세션 상태를 확인한다. 탈퇴 계정 차단은 별개로 유지한다.
- Data가 프로젝트 키의 발급·목록·폐기·요청 검증과 키 원본을 소유한다. 관리 API는 access token과 Control의 프로젝트 소유권·상태 확인을 요구한다. 외부 호출에서 키 해시·대상 프로젝트·폐기 상태는 Data DB에서 확인한다. 폐기 성공 응답은 Data DB의 폐기 상태 반영 후 반환한다. 계정·프로젝트 삭제 상태 확인은 키 검증과 별도로 유지한다.
- 목록 `URL_TEMPLATE`는 Analysis가 실측·검증한 `url_template`, `start`, `step`으로 표현한다. 상세 형식과 검증·대체 규칙은 [메시지 명세 5.2](service-message-contracts.md#52-목록과-상세-이동)를 따른다. 목록만 정적 HTTP를 사용할 수 있으며 상세는 브라우저다.
- 출처 표시 이름은 별도 관리하지 않고 목록 URL로 표시한다. 레코드의 `source_url`과 출처 목록 URL은 서로 다른 값이다.

### 적용 상태와 지연 쓰기의 경계

승인된 동일 스키마 출처 추가는 정상 적재가 끝난 출처부터 공개한다. Control이 완료 이벤트를 아직 반영하지 않았더라도 Data는 이미 공개한 레코드의 승인된 적용 중 출처 매핑을 조회할 수 있어야 한다. 승인 전 후보를 공개한다는 뜻은 아니다.

출처 삭제·프로젝트 삭제·스키마 전환 후 늦은 작업의 재적재는 Data DB의 프로젝트별 쓰기 상태와 삭제된 출처 차단 정보를 실제 데이터 쓰기와 같은 트랜잭션에서 확인해 막는다. Control은 기존 dataset.apply에 BEGIN_CHANGE·END_CHANGE를 사용해 변경의 시작과 종료를 Data DB에 기록한다. Ingestion은 같은 프로젝트 상태 행을 잠가 OPEN 변경과 대상·버전을 확인하며 데이터 쓰기·종료·삭제 차단을 직렬화한다. 다음 변경은 종료 결과와 실제 커밋 결과를 확인한 뒤 시작한다. 지연 결과·부분 성공의 상세 계약은 메시지 명세 10.5를 따른다.

### 승인 변경 시작과 종료

Control은 프로젝트마다 승인 변경을 하나만 진행한다. 기존 dataset.apply로 BEGIN_CHANGE를 보내고 Data DB의 OPEN 기록과 dataset.applied 성공을 확인한 후 스키마 준비·수집·적재를 발행한다. 성공 또는 최종 실패 시 END_CHANGE로 닫고 Data의 실제 커밋 결과를 반영한 뒤 다음 변경을 허용한다. OPEN 여부·대상·버전과 출처 삭제 차단은 Data DB 쓰기 트랜잭션에서 확인한다. END 결과가 불확실하면 재전달하고 새 변경은 보류한다. 초기 일부 성공·추가 일부 성공은 유지하고 리비전 실패는 기존 버전을 유지한다. 상세는 [메시지 명세 10.5](service-message-contracts.md#105-승인-변경의-시작과-종료-기존-datasetapply-확장)를 따른다.

### 변경 재확인과 커넥터 동기화

- 지연 schema.prepare도 Data DB에서 OPEN change_job_id·프로젝트·목표 버전과 삭제 상태를 확인한다. 종료된 변경은 스키마 정의를 쓰지 않는다.
- 0건으로 사용자 조치가 필요한 변경은 즉시 문제를 표시하고 END_CHANGE로 종료한다. 종료 확인 뒤 원래 승인 설정으로 재확인·새 변경을 진행하며 최초 부분 성공은 유지한다. 구조 변경 재시도는 최종 출처를 모두 다시 준비한다. 상세는 메시지 명세 10.7이다.
- 스키마 유지 커넥터 수정·자동 복구는 해당 출처 작업을 보류하고 기존 dataset.apply의 SET_CONNECTOR_REVISION으로 Data DB의 유효 (schema_version, connector_revision)을 먼저 조건부 갱신한다. 결과 확인 후 Control 규칙을 활성화하고 재수집한다. 일반 적재는 해당 tuple을 Data DB에서 쓰기와 함께 검사한다. 신규 출처 공개·REPLACE는 유효 revision을 데이터 공개와 함께 기록한다. 상세는 10.6이다.
- REPLACE 결과가 유실됐을 때 동일 job_id·payload를 재전달하고 Ingestion receipt가 원래 event_id 결과를 재발행한다. Control은 해당 change_job_id의 재조정임을 확인해 이미 수신된 결과도 한 번 검토하고 중복 반영은 막는다. 확인 후 END_CHANGE로 닫는다. 상세는 10.8이다.

### 최근 확정: 빈 프로젝트와 교차 서비스 적용

- 마지막 프로젝트 출처 삭제를 허용한다. 공개된 스키마·API 버전은 유지하며 제거 출처의 레코드와 연결을 정리한 뒤 데이터 목록은 빈 배열이다. 삭제 자체는 크롤링 0건이 아니므로 0건 문제·이메일을 만들지 않는다. 신규 출처는 같은 활성 스키마로 추가·분석·승인할 수 있다. 마지막 공유 연결의 일정은 중지한다.
- 최초 v1이 아직 공개되지 않은 경우 이전 변경의 END 확인 후 삭제를 새 SOURCE_CHANGE로 승인·반영한다. 활성 버전은 null, 준비된 v1 정의는 유지한다. 남은 승인 대상이 있으면 새 INITIAL로 수집하고, 없으면 빈 프로젝트로 대기한다. 이후 새 출처는 보관된 승인 v1 기준으로 분석하고 신규 INITIAL의 첫 성공 전까지 API를 공개하지 않는다. 전체 출처 삭제만 하는 후보는 성공 출처가 없어도 승인 가능하다.
- 커넥터 복구는 공개 출처의 활성 가드 또는 승인 변경 중 출처의 pending 가드에 SET_CONNECTOR_REVISION을 보내 Data 조건부 갱신 성공 후 Control 규칙을 활성화하고 새 작업을 실행한다. 승인 변경의 BEGIN이 pending revision을 등록하고 출처별 쓰기는 커밋 때 이를 검사한다. 최초 공개·출처 추가·리비전 전환은 해당 pending revision을 활성 가드로 원자 반영한다. 상세는 메시지 명세 19.8을 따른다. 구조 변경은 사용자 승인을 다시 받는다.
- CLOSED된 과거 변경의 준비 v2는 새 변경이 동일 버전과 정의를 재준비할 때 프로젝트 행 잠금 아래 기존 미공개 정의·필드를 폐기하고 새 change_job_id로 다시 준비한다. 이전 준비 레코드는 노출·재사용하지 않고 늦은 작업은 CLOSED로 차단한다. 공개된 v1과 데이터는 유지한다. 미공개 최초 v1의 같은 승인 정의는 기존 정의의 변경 소유권을 새 OPEN INITIAL로 이전해 참조할 수 있고 공개된 v1은 변경 소유권을 덮어쓰지 않는다.
- 공개 스키마의 표시명·설명·순서 변경은 같은 API 버전에서 기존 dataset.apply UPDATE_SCHEMA_METADATA로 조건부 적용한다. Data DB의 schema_metadata_revision과 PROJECT_SCHEMA/SCHEMA_FIELD를 갱신하고 결과 receipt·Outbox를 같은 트랜잭션에 남긴다. Data 결과 확인 후 Control이 반영하며 구조 변경·데이터 재수집은 하지 않는다.
- 탈퇴 계정 차단을 위해 Control·Data는 사용자 JWT 요청마다 서비스 인증된 Auth 내부 계정 상태 조회로 원본을 확인한다. API 키 요청은 Data가 Control의 프로젝트 상태 확인을 거치며 Control이 해당 소유자의 Auth 상태를 확인한다. ACTIVE만 허용하고 탈퇴 진행·삭제 계정은 차단한다. Auth 원본 조회 실패는 503이다. 비밀번호 초기화의 이미 발급된 access token은 탈퇴와 별개로 만료까지 유효하다.
- source_id 필터·정렬은 Data가 Control에서 프로젝트별 공개 출처 매핑을 조회해 project_source_id에 대응시켜 DB 조건·정렬에 적용한다. 매핑 revision을 커서에 묶고 변경 시 409, 확인 불가는 503이다. 출력용 resolve도 유지한다.
- 동일 프로젝트의 초기 분석 생성은 프로젝트 행 잠금으로 진행 분석 확인·생성·JOB·Outbox를 한 Control DB 트랜잭션으로 처리한다. 동일 요청 경합 시 기존 analysis_id·job_id를 반환한다.
- 동일 호스트의 사이트 요청은 Analysis와 Crawler가 기존 Redis의 호스트별 임대와 최근 요청 시각을 공유해 하나씩 최소 1초 간격으로 보낸다. 임대 유효성 확인 불가 시 새 요청을 멈춘다. 네트워크 요청의 강제 종료·임대 만료 유예를 구현·시험하며 장시간 정지된 프로세스의 물리적 종료가 확인되지 않은 동안 다른 요청을 허용하지 않는다. 브라우저의 대상 호스트 요청도 적용한다.
- AI 추천 필드는 recommendation_reason을 반환한다. 사용자 추가 필드는 null을 허용하고 화면은 추천 근거 없음을 표시한다. 공유 manifest 재작성 시 삭제 출처의 consumers, source_urls와 다른 프로젝트 전용 참조를 모두 제거한다. 상세 메시지·검증 기준은 service-message-contracts.md 19절이다.

- 탈퇴 상태 확인은 Control·Data가 JWT 검증 후 Auth의 `GET /internal/v1/accounts/{user_id}/access-status`를 호출한다. `ACTIVE`만 허용하며 `WITHDRAWING`·`DELETED`는 403, 원본 확인 실패는 503이다. 프로젝트 API 키의 소유자 상태는 Control이 같은 원본으로 확인한다. 이미 인증을 통과해 실행 중인 요청의 취소는 보장하지 않는다. 상세 요청·응답은 메시지 명세 19.5절을 따른다.
- 승인된 v1이 미공개일 때 새 출처를 추가하면 Control은 Ingestion의 내부 준비 스키마 조회로 Data DB의 승인 정의를 읽어 기준으로 사용한다. 공개 데이터 API에는 이 정의를 노출하지 않는다. 상세는 메시지 명세 19.3절을 따른다.


### 7.7 실행·수신 계약 보완

- HTTP 목록은 NONE·NEXT_LINK·URL_TEMPLATE만 사용한다. 클릭·스크롤이 필요한 목록은 BROWSER, 상세는 항상 BROWSER다. 초기 클릭·상세 열기·대기·복귀의 구체 형식은 메시지 5.2를 따른다.
- 공유 수집은 각 프로젝트가 완료한 페이지 또는 5개 묶음까지 manifest의 source_urls 참여 표시를 남긴다. 참여하지 않은 후속 항목은 Ingestion이 읽지 않는다. 실패와 범위 밖은 다르다.
- 여러 프로젝트 수동 요청이 동일 수집을 사용하면 Control은 요청과 공유 실행을 연결하고 프로젝트별 결과를 집계한다. 출처가 없으면 작업을 만들지 않고 409 NO_ACTIVE_SOURCES를 반환한다.
- DB 장애로 Ingestion이 receipt/Outbox를 기록할 수 없으면 요청을 성공 삭제하지 않고 재전달·기한/DLQ 점검으로 처리한다.
- 후보 조회·수정과 작업 조회의 구체 JSON, 기존 사용자 편집을 보존하는 출처 재시도 병합은 메시지 19.9를 따른다.


## 8. 재점검 후 실행 경계 확정

- 최초 공동 후보 채택 시 Control은 누락된 description을 null, display_order를 추천 배열 순서로 초기화하고 사용자 편집을 보존한다. 후보 GET은 이동 규칙·필드별 커넥터·제외 출처·검증과 샘플 revision을 모두 반환한다. 수정의 navigation은 출처별 전체 교체, 커넥터는 필드별 병합이다. 최초 분석 대상이 다른 중복 요청은 409다.
- 상세는 계속 브라우저만 사용하며 CURRENT_TAB/NEW_TAB/MODAL 대상과 그에 맞는 대기·복귀를 검증해 전달한다. NONE은 첫 화면만 검사한다. 스크롤·더 보기 완료 대기 후 신규 항목이 연속 2회 없으면 목록 끝, 대기 실패·순환은 탐색 오류, 예산 만료는 TIME_LIMIT이다.
- 공유 출처는 URL 스킴·호스트 대소문자/기본 포트와 fragment만 정규화하고 의미 있는 path/query를 보존한다. 초기 동작 순서와 기본값을 채운 이동 설정이 정확히 같을 때만 공유한다. 호스트 동시 요청 제한은 브라우저의 실제 네트워크 요청별로 적용해 중첩 대기를 방지한다.
- Control은 일반 수집 발행 전에 조회한 schema_version과 최신값 버전을 대조하고 전환 중이면 보류한다. 요청 job은 수집뿐 아니라 대상별 적재 결과까지 연결해 집계한다. 공개 전 복구는 Data 준비 정의와 S3 승인 샘플을, 공개 후는 공개 정의와 최신 DB 값을 사용한다.
- 공유 manifest의 참여 범위 유효성은 전체 collection 대상 기준이다. Ingestion은 그중 자기 project_source_id만 처리한다. 공유 manifest 정리본은 같은 수집 시도의 rewrites/{cleanup_job_id}/manifest.json으로 보관하고 승인된 원본 시도 HTML을 참조한다.
- Data는 키 발급과 프로젝트 삭제가 충돌하지 않도록 Data DB 프로젝트 쓰기 상태를 같은 트랜잭션에서 확인한다. API 키 개수 제한은 없으며 키 호출 제한 Redis 장애는 503이다. JWT에는 키별 제한을 적용하지 않는다. MVP의 공개 스키마·데이터는 Data DB 동일 읽기 스냅샷을 사용하고 공개 스키마 캐시는 두지 않는다. 내부 권한·계정 정리·삭제 영향 경로와 요청 형식은 메시지 명세 20절을 따른다.
- 로그아웃은 유효한 요청을 중복 전달해도 204다. 가입 인증번호 202는 공급자 접수, 비밀번호 초기화 번호 202는 계정 존재를 숨기는 요청 접수다. 회원 표시명은 trim 후 1~50자다. 실제 발송·구현 테스트·운영 기간은 별도로 확인한다.


### 8.1 추가 확정: 이동·복구·알림

- Analysis는 item_selector가 목록의 항목을 분리하고 필드·상세 이동을 각 항목에 연결하는지 실제 화면에서 검증한다. Crawler는 목록 및 스크롤을 확인하며 같은 누적 DOM의 이미 처리한 항목을 다시 처리하지 않는다. DOM 가상화·재사용 등으로 사라진 항목을 복원하거나 완전한 중복 판별을 구현하는 것은 MVP 범위에서 제외하며 누락 가능성을 허용한다. 다만 이미 확보한 스냅샷에서 목록 항목과 상세가 다른 항목에 잘못 매칭되도록 추측하지 않는다.
- 추출·선택자·파싱·타입 변환 실패 레코드는 부분 저장하지 않는다. 실제 null과 ABSENT는 정상이다. 비교에 필요한 값이 실패해 해당 프로젝트 출처의 비교를 계속할 수 없을 때 그 대상 비교를 중단하고 관찰 정보로 Control이 자동 복구를 요청한다. 다른 정상 프로젝트는 계속한다. 기술 장애와 접근 차단은 기존 별도 흐름을 따른다. 복구 후보 검증은 최대 3회다.
- HTTP 목록 검증은 초기 분석 전체 5분 안에서 수행한다. 검증 시간이 부족하거나 동일성을 확인하지 못하면 미확인 HTTP 규칙을 채택하지 않고 검증 가능한 브라우저 방식을 사용한다. 구체 시간 수치는 운영 설정이다.
- 이메일 문제 알림은 같은 문제가 해결되기 전 중복 발송하지 않도록 프로젝트·출처·문제 상태를 기준으로 발송 상태를 보관한다. 발송 실패는 수집·적재를 되돌리지 않고 제한된 재시도를 한다. 공급자 접수 결과가 불확실하면 중복 가능성을 기록하고 공급자의 멱등 기능이 있는 경우 재사용한다. 이메일의 정확히 한 번 전달을 보장하지 않는다. 가입 메일 발송 실패·초기화의 계정 비노출 규칙은 7.1을 따른다.
- SQS·DLQ 재처리 가능 기간 이상 관련 receipt·이벤트 수신 기록·Outbox와 재발행에 필요한 S3 결과를 보존한다. 삭제나 참조 정리는 기존 S3 명세의 실제 실행·공유 참조 종료 조건을 따른다. 구체 시간과 토큰 TTL·lease·heartbeat·visibility는 운영 설정이다.

### 7.5 79개 흐름 추가 확정

- 분석 중 화면은 전체 진행 상태만 표시하고 개별 출처 결과는 완료 이벤트를 받은 뒤 표시한다. 분석 GET의 HTTP status는 RUNNING·READY·FAILED·CANCELLED이며 완료 이벤트의 SUCCEEDED·PARTIAL은 성공 후보가 있으면 READY로 변환한다. 검증 진행 상태는 별도 validation_status다.
- 동일 후보·출처의 진행 중 재시도는 같은 job을 반환한다. Control은 결과 채택 시 요청 revision을 검사하고 변경된 출처 결과의 병합·revision 증가·검증 기록·중복 처리와 후속 Outbox를 원자적으로 수행한다. stale 결과는 반영하지 않으며 승인도 현재 revision과 검증을 검사한다.
- 기존 후보의 출처 추가는 list_url·analysis_id·expected_revision으로 해당 후보에 연결한다. Control이 출처 후보 생성, 후보 revision 증가, ADD_SOURCE job·Outbox를 한 트랜잭션에서 확정하고 revision 충돌이면 아무것도 생성하지 않는다. 요청·응답은 메시지 명세 20.9를 따른다.
- 프로젝트 생성 확인 전 웹은 생성 의도별 Idempotency-Key와 동일 본문을 브라우저 sessionStorage에 보관해 새로고침 시 복원하고, 성공 확인 또는 유효 보관 기간 종료 시 제거한다. 서버의 키 보관은 최소 24시간이다. 다른 기기의 분석 재진입은 서버 목록의 현재 ID를 사용한다. 분석 미시작 프로젝트는 목록·상세에서 시작할 수 있고, 종료된 실패를 다시 시작하면 새 analysis_id·job_id를 발급한다. 동일 분석이 진행 중이면 기존 ID를 반환한다.
- 초기화 메일 202는 계정 유무·개별 발송 결과를 구분하지 않는다. 공통 장애만 계정과 무관한 동일 503으로 응답할 수 있다. 가입 결과 불확실은 재인증·로그인을 안내한다. 초기화 증명 소비 후 결과 불확실이면 번호 인증부터 다시 시작한다. 이름 변경과 로그아웃의 실패는 기존 공통 안내와 재시도를 사용한다.
- 회원 탈퇴는 Control 접수 확인 뒤 사용자에게 202를 반환하고 정리는 비동기로 진행한다. 접수 불확실이면 차단을 유지하고 확인하며 사용 가능이라고 단정하지 않는다.
- 수집 상태와 종료 사유의 매핑은 메시지 명세 20.9를 따른다. 측정 전 추출 건수 null은 화면에서 미측정으로 표시하며 실제 측정한 0과 구별한다.

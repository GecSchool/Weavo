# Weavo 개발 일정 초안

- 기간: 2026년 11월 9일 ~ 12월 31일
- 기준: 최종 설계제안서의 역할 분담과 [스펙 결정 로그](spec-decision-log.md), [메시지 명세](service-message-contracts.md), [메시지 전달 흐름](service-message-flows.md)
- 목적: 도학규가 미리 정리한 계약과 DB·클래스 설계를 기준으로 각 담당자의 주차별 구현과 확인 대상을 정리한다. 예상 일정이며 실제 가용 시간과 개발 결과에 따라 팀이 조정한다.
- 설계 문서와 메시지 형식이 다르면 메시지 명세를 우선한다. 명세에 표시된 제안·미정 항목은 구현 전에 별도로 확인한다.

## 일정 운영 기준

- 도학규가 개발 전에 API·메시지·데이터 계약과 DB 테이블·클래스 다이어그램을 설계하고 공유한다. 도학규를 포함한 담당자들은 매주 구현할 항목의 계약과 테이블·클래스를 먼저 확인한다. 계약·설계가 아직 제공되지 않았거나 모순·미정인 경우 도학규에게 확인하고 임의로 확정하지 않는다.
- 현재 DB·클래스 설계는 작성 예정이며 아래 테이블·클래스명은 **확인할 개념적 대상**이다. 실제 테이블명·컬럼·클래스는 추후 공유되는 설계가 기준이다.
- 각 주차의 작업에는 구현뿐 아니라 해당 기능의 단위 테스트, 리뷰와 다른 담당자와의 연결 확인을 포함한다.
- 다른 서비스가 아직 준비되지 않았다면 도학규가 공유한 요청·응답 형식으로 테스트 대역이나 샘플 메시지를 사용한다. 준비된 서비스는 이후 실제 연결로 교체하고, 대역만으로 연결 완료라고 판단하지 않는다.
- W3의 최소 수직 연결은 **고정된 테스트 규칙을 사용하는 단일 출처 흐름**이다. AI 분석, 실제 사용자 승인과 다중 출처 처리가 그때 완성된다는 뜻은 아니다.
- 초기 분석과 최초 수집은 별도 작업이다. 최초 수집의 출처별 5분 제한, 일반 반복 수집의 1분 및 최신값 비교는 각 기능 구현 시 적용한다.
- W4는 단일 출처의 실제 후보 생성·검증·승인 연결을 먼저 확인한다. 다중 출처 공동 추천은 같은 주에 진행하되 지연되면 미완성 상태를 표시하고 W5에 이어서 진행한다.
- W5의 반복 수집과 필터·정렬 및 W6의 복구·데이터 교체는 각각 별도 통합 작업이다. 정상 수집·조회와 기존 데이터 보존을 먼저 확인하고, 지연 시 팀이 우선순위와 후속 일정을 조정한다. 미완성 기능을 완성된 것처럼 표시하지 않는다.
- 도학규는 계약·DB·클래스 설계를 미리 작성해 공유하고, 담당자는 확인한 설계에 따라 테스트 데이터와 구현을 준비한다. GitHub Actions와 외부 계정은 필요한 담당자가 협업해 준비한다. 로컬·CI의 토큰과 운영 자격 증명은 각 환경에서 별도 관리한다.

## 전체 마일스톤과 선행 관계

| 시점 | 팀 목표 | 완료를 확인할 내용 |
|---|---|---|
| **W1** | 프로젝트 이해·환경 준비 | 도학규가 미리 계약·DB·클래스 설계를 공유하고, 다른 팀원은 전체 흐름과 자신의 담당을 이해한 뒤 실행·테스트와 관련 설계를 확인 |
| **W2** | 단일 출처의 기초 기능 | 고정 규칙으로 화면을 수집하고 S3에 저장할 수 있는 기초와, 샘플 스냅샷을 읽어 적재하는 기초를 각각 검증 |
| **W3** | 최소 수직 연결 | 테스트용 설정 → Control 작업 → Crawler → S3 → Ingestion → DB → Data API의 단일 출처 성공 경로를 실제 연결 |
| **W4** | 실제 초기 분석·설정 연결 | 출처별 후보와 공통 스키마 후보를 생성·검증하고 사용자 수정·승인과 최초 수집을 연결 |
| **W5** | 반복 수집·조회 | 프로젝트별 최신값 조회·비교와 정기 수집, 데이터 조회·필터의 핵심 흐름을 연결 |
| **W6** | 복구·변경 적용 | 0건·실패 분기, 규칙 복구 및 승인된 스키마 변경 후 새 데이터 준비·교체를 단계적으로 연결 |
| **W7** | 통합·배포 | 실제 서비스와 최소 AWS 환경에서 주요 흐름을 실행하고 결함 수정 |
| **W8** | 안정화·시연 | 시연 시나리오 재실행, 남은 결함·문서·발표 정리 |

**중요한 선행 관계**

1. Crawler의 스냅샷 저장과 Ingestion의 스냅샷 읽기 → W3 실제 연결. 이때 필요한 메시지·스냅샷 형식은 아래 계약 C1·C2를 참고한다.
2. 초기 DB·Flyway SQL → 프로젝트·작업 저장과 수집 데이터 적재 → 프로젝트 생성 및 Data 조회.
3. Auth 로그인 구현 → 인증 화면 연결 → Control·Data의 권한 확인. 토큰·권한 형식은 계약 C3을 참고하고 준비 전에는 테스트 대역을 사용한다.
4. Analysis 후보 형식·샘플 제공 → 후보 표시·CSS 편집 → 재검증·승인 → 최초 수집.
5. 프로젝트별 최신 데이터 조회와 동일한 파싱·정규화 결과 → Crawler의 최신 3건 비교 → 반복 수집 조기 종료.
6. 정상 수집·적재와 S3 샘플 → 오류 감지·복구 후보 검증 → 자동 적용 또는 사용자 확인.
7. 기존 API와 데이터 유지 방법 → 출처별 리비전 수집·새 데이터 준비 → 모든 대상 성공 확인 → 데이터·API 버전 교체.

## 필요한 계약

계약은 도학규가 사전에 정리해 공유하는 **요청·응답, 메시지 또는 데이터 형식**이다. 다른 담당자는 각 주의 구현 전에 본인과 관련된 계약과 테이블·클래스 설계를 확인한다. 아래 확인 시점은 실제 기능이 그때 구현 완료된다는 뜻이 아니다. 구체적인 필드와 미정 사항은 [메시지 명세](service-message-contracts.md)와 [전달 흐름](service-message-flows.md)을 기준으로 확인하며, 이 표는 작업 순서를 위한 참조다.

| 번호 | 필요한 계약 | 확인할 담당자 | 확인 시점 | 확인할 내용 |
|---|---|---|---|---|
| **C1** | 공통 작업·결과 메시지 | 김어령 · 도학규 · 김다은 | W1 확인, W3 실제 연결 전 | SQS 대상, 작업·이벤트 ID, 결과·실패·중복 처리, `analysis.execute`·`collection.execute`·`ingestion.execute` |
| **C2** | 수집 규칙·S3 스냅샷 | 도학규 · 김다은 · 김어령 | W1 확인, W2 샘플 확인 | 고정 규칙, 객체 참조, 목록 항목과 상세 화면 연결, 출처·프로젝트 식별 정보 |
| **C3** | 인증·권한 | 김어령 · 서채원 · 박민서 · 김다은 | W1 확인, W2~W3 인증 연결 전 | 로그인·인증번호 요청·응답, 토큰 전달·갱신, 사용자 권한과 외부 API 키 확인 |
| **C4** | 프로젝트 생성·분석 시작 | 김어령 · 서채원 · 박민서 | W1 확인, W4 실제 연결 전 | 프로젝트 생성 입력·응답, 분석 시작, project_id·analysis_id와 화면 이동 |
| **C5** | 분석 후보·샘플·승인 | 도학규 · 김어령 · 박민서 | W1 확인, W4 실제 연결 전 | 후보 revision, 출처별 필드·선택자·이동 규칙, S3 샘플 참조, 수정·재검증·승인 결과 |
| **C6** | 파싱·저장·최신값 비교 | 도학규 · 김다은 · 김어령 | W1 실험 착수, W4~W5 반복 수집 연결 전 | parser.code의 동일 실행·정규화, 스키마와 타입, 실패·null, 최신 최대 3건 조회·비교. 실행 위치·격리 등은 미정 |
| **C7** | 데이터 조회 | 김다은 · 박민서 · 김어령 | W1 응답 예시, W5 실제 연결 전 | 목록·필터·정렬·커서, 오류와 인증·권한. 저장 구조와 인덱스는 Ingestion·Data가 함께 확인 |
| **C8** | 복구·0건·변경 적용 | 김어령 · 도학규 · 김다은 · 서채원 · 박민서 | W1 확인, W6 실제 연결 전 | 수동 수집 요청·작업 상태, 실패 현상·범위, 복구 요청·검증 기준, 0건 알림, 출처별 준비 결과와 기존 데이터 유지·교체 조건. 미정 임계값은 확정하지 않음 |
| **C9** | 프론트 공통 UI·화면 연결 | 도학규 · 서채원 · 박민서 | W1 최소 범위, 화면 통합 전 보완 | 기본 컴포넌트 props·상태, 프로젝트 생성 후 분석 화면 이동, 오류·로딩 표시 |

각 주차의 **선행 작업**은 실제 연결에 필요한 구현·결과물, **확인할 계약**은 위 표의 해당 항목, **확인할 테이블·클래스**는 도학규가 작성한 DB·클래스 설계에서 살펴볼 범위다. 계약이 준비되면 테스트 대역으로 병행할 수 있지만 실제 서비스의 선행 구현을 대신하지는 못한다.

## 도학규 — Analysis·Crawler·기술 총괄

### W1 · 11/9~11/15

- 로컬 환경과 테스트 명령을 확인하고, 두 프론트 담당자와 버튼·입력 등 당장 필요한 기본 컴포넌트의 범위와 전달 시점을 맞춘다.
- 구현 전에 API·메시지·수집 규칙·S3 스냅샷 계약과 서비스별 DB 테이블·클래스 다이어그램을 정리하고 각 담당자에게 공유한다. 미정인 파서 실행 방식 등은 확정된 내용과 구분한다.
- **선행 위험 확인:** `parser.code`를 Python 기반 분석·수집과 Java 기반 적재에서 같은 결과로 실행하는 가능한 방법을 작은 샘플로 조사·실험한다. 실행 위치·격리 방식은 실험 후 결정하며 이 주에 완성했다고 가정하지 않는다.
- 산출물: 담당자들이 확인할 계약 문서·테이블·클래스 다이어그램, 기본 컴포넌트 최소 범위와 파서 실험 결과. 기본 컴포넌트 제공이 늦어져도 프론트 담당자가 화면 구조와 테스트 대역으로 병행할 수 있게 한다.
- 확인할 계약: C1 · C2 · C5 · C6 · C9.
- 확인할 테이블·클래스: 전체 서비스의 계정·프로젝트·출처·작업·스키마·커넥터·수집 데이터 테이블과 클래스 다이어그램을 사전 설계·공유.

### W2 · 11/16~11/22

- 단일 목록 페이지에서 브라우저 DOM을 확보하고, 고정된 목록·필드 규칙으로 필요한 화면을 수집하는 Crawler 기초를 만든다.
- S3에 저장할 스냅샷 구조를 적용하고 김다은에게 실제 샘플을 전달한다. 목록과 상세 연결 정보도 샘플 계약에 포함한다.
- Analysis에서는 샘플 DOM과 사용자 요구를 AI 후보 입력으로 만드는 기초를 검증한다. 최초에는 선택한 제한된 테스트 사이트를 사용한다.
- 선행 작업: 통신이 준비되지 않아도 로컬 샘플로 독립 검증할 수 있다.
- 확인할 계약: C1 · C2 · C5 · C6.
- 확인할 테이블·클래스: 공유 출처·수집 규칙·목록/상세·스냅샷 및 필드 커넥터.

### W3 · 11/23~11/29

- 고정 규칙으로 목록·상세 접근과 스냅샷 저장을 연결하고, Control의 수집 요청과 완료 결과를 실제 SQS로 주고받는다.
- 김어령·김다은과 단일 출처의 수집 → S3 → 적재 → 조회를 연결한다. 이 마일스톤은 고정 규칙 기반이며 AI 자동 분석 완성을 요구하지 않는다.
- Analysis의 AI 후보 생성과 실제 탐색 후보 실행을 별도로 진행하고, 실패 사례와 관찰 정보를 남긴다.
- 선행 작업: W2 샘플 스냅샷, Control 작업 발행·결과 수신, Ingestion 적재 기초.
- 확인할 계약: C1 · C2.
- 확인할 테이블·클래스: 작업·공유 출처·스냅샷·프로젝트/출처 연결.

### W4 · 11/30~12/6

- 출처별 임시 스키마·선택자·목록·상세 이동 후보를 만들고 실제 화면에서 검증한다. 후보가 부적합하면 관찰 정보를 바탕으로 보완한다.
- 다중 출처는 출처별 후보를 먼저 만들고 중간 결과를 모아 공통 스키마·매핑을 추천한다. 분석 샘플을 revision별로 S3에 저장한다.
- 김어령·박민서와 후보 조회·수정·재검증·승인을 연결한다. 우선 확인 가능한 목록 이동 방식부터 연결하고 무한 스크롤 등은 검증된 범위를 표시한다.
- 선행 작업: 실제 연결에는 김어령의 revision·승인과 박민서의 후보 편집 화면이 필요하다.
- 확인할 계약: C1 · C5.
- 확인할 테이블·클래스: 분석 작업·후보 revision·공통 스키마·필드 커넥터·샘플 참조.

### W5 · 12/7~12/13

## 팀 공통 점검

- 매주 초 각 담당자는 도학규가 공유한 이번 주 구현 대상의 계약과 DB·클래스 설계를 확인하고, 선행 구현의 완료 시점을 점검한다. 준비가 되지 않은 구현은 대역으로 병행 가능한지 표시한다.
- 매주 말 정상 경로와 실패 경로, 테스트 결과, 다음 담당자에게 전달한 API·메시지·샘플과 남은 이슈를 짧게 공유한다.
- W3부터 실제 서비스 간 연결을 매주 확인한다. W7 배포 전에 LocalStack·테스트 DB에서 실패·재전달과 주요 API를 가능한 범위에서 검증한다.
- 개발 진도에 따라 W6 범위가 어려우면 팀이 핵심 시연 흐름과 후속 범위를 결정한다. 일정표의 미정 정책을 구현자가 임의 확정하지 않는다.

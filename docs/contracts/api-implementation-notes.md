# API 구현 시 필요한 처리 규칙

HTTP 요청·응답 형식, 인증, 상태 코드는 [OpenAPI](openapi/)를 따른다. 아래 항목은 여러 요청이나 서비스의 상태를 함께 판단해야 하는 규칙이다. 전체 흐름과 메시지는 [기능별 전달 흐름](../service-message-flows.md)과 [서비스 메시지 명세](../service-message-contracts.md)를 따른다.

## 수집과 작업 조회

- 수동 요청은 프로젝트 출처별 실제 공유 수집에 연결한다. 요청이 진행 중인 수집의 참여 대상이 아니면 후속 수집을 기다린다. 대상별 수집 결과와 필요한 적재가 모두 종료된 뒤 요청 성공·부분 실패·실패를 판단한다. 프로젝트별 결과는 요청한 소유 프로젝트 범위로만 제공한다.
- 출처별 최근 수집은 실제 collection 회차를 최신순 최대 5건으로 조회한다. 중복 수동 요청과 ingestion 작업은 별도 회차로 세지 않는다. 5건은 화면 조회 제한이며 작업 보존 기간은 아니다. 목록 항목 수와 정상 추출 수는 실제 측정값만 표시하고 미측정은 null이다.
- 전혀 변경 없는 정상 수집은 적재 없이 완료한다. `NO_CHANGE` 전에 새 데이터를 발견했고 해당 프로젝트가 적재 가능하다면 적재 결과를 기다린다. 자세한 연결·중복 처리와 건수 기준은 [메시지 명세 23절](../service-message-contracts.md#23-수집-회차-연결과-삭제-화면-계약)을 따른다.

## 후보 수정과 승인

- `expected_revision`을 확인해 수정하고 필요한 출처만 재검증한다. 승인에서는 현재 후보와 유효 검증 revision이 일치해야 한다. 지연된 결과는 새 후보를 덮어쓰지 않는다.
- Analysis가 보낸 `sample_ref`는 Control이 S3 본문의 소유 범위와 실제 생성 revision을 확인한다. 사용자 응답에는 내부 S3 참조를 노출하지 않는다. 조회 실패는 빈 샘플이 아닌 오류다. [분석 흐름](../analysis-server-workflows.md)

## 삭제와 재처리

- 프로젝트 삭제의 202는 접수다. 소유자 목록에는 삭제 중·확인 필요의 최소 상태만 표시하고 정리가 끝나면 제거한다. 삭제된 프로젝트의 늦은 쓰기는 차단하며 공유 출처의 다른 프로젝트는 유지한다.
- 삭제 후 사용자용 작업 상세는 제공하지 않는다. 삭제 작업 재처리와 지연 메시지 차단에 필요한 최소 기술 기록은 해당 재처리 기간에 유지한다. 회원 탈퇴의 서비스 간 정리 완료 통지는 이 사용자 화면과 별개다. [삭제 메시지 흐름](../service-message-flows.md#316-프로젝트-전체-삭제)

## 데이터 조회

- 프로젝트별 동적 필드와 타입에 따른 필터 허용 여부는 활성 스키마와 함께 검사한다. 여러 필터는 AND이며 정렬과 커서는 스키마·데이터·출처 매핑의 유효한 버전과 함께 확인한다. 상세 조건은 [Data OpenAPI](openapi/data.json)와 [데이터 조회 흐름](../service-message-flows.md)을 따른다.

구현 및 통합 시험은 [구현 확인 사항](implementation-checklist.md)을 따른다.

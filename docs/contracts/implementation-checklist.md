# 계약 구현과 통합 확인 사항

이 문서는 실행 코드와 서비스 간 연동을 확인할 항목이다. 필드 형식은 [OpenAPI](openapi/)와 [메시지 JSON Schema](schemas/)를 기준으로 한다.

1. **HTTP 응답과 오류:** 각 경로의 상태 코드·본문·인증과 실제 서비스 응답이 일치하는지 확인한다. 공통 오류와 후보 PATCH 409·422 및 프로젝트 전체 수집 409의 별도 형식을 구분한다. 발생 조건별 오류 코드와 운영 값은 구현 시 확인한다.
2. **서비스 인증:** 서비스 전용 자격증명의 발급·보관·회전, 전송 보호와 개발 환경 공급 방법을 검증한다. 사용자 access token, API 키와 혼용하지 않는다.
3. **추출과 파서:** CSS 선택자·HTML 속성·여러 요소의 순서가 브라우저와 파서에서 일관되는지, Analysis·Crawler·Ingestion의 변환 결과가 같은지 확인한다. TEXT는 텍스트, ATTRIBUTE는 지정 속성을 추출한다.
4. **메시지 상태:** 명세에 정의된 각 메시지의 상태·부분 성공·실패 조건을 송수신 코드와 대조한다. project-data.deleted는 SUCCEEDED 또는 FAILED다.
5. **동적 필드:** 프로젝트 스키마별 사용자 필드와 필터 연산자, 정렬·커서 조건이 실제 요청과 데이터에 적용되는지 검증한다.
6. **업무 및 동시성 검증:** 필드·타입·커넥터 대응, revision과 영향 대상, S3 객체 소유·범위, 동일 출처, 중복 event_id와 SQS 재전달을 통합 시험한다. JSON Schema 통과만으로 실제 동작을 보증하지 않는다.
7. **필드 순서:** schema.prepare의 description·0 이상 display_order, 중복 방지 및 승인 정의와의 일치를 검증한다. 최초 추천은 배열 순서로 번호를 부여하며, 수정 뒤 번호가 반드시 연속적이라고 가정하지 않는다.
8. **S3 본문:** 메시지의 참조 형식뿐 아니라 [S3 저장 명세](../s3-storage-contract.md)의 샘플·manifest 본문·소유·정리 조건을 검증한다. 본문용 별도 JSON Schema는 제공하지 않는다.
9. **샘플 revision:** `analysis.completed`의 `sample_ref`가 있는 경우 Control이 S3 본문의 분석·프로젝트·출처·시도와 실제 생성 revision을 확인한다. 결과 메시지의 별도 `sample_revision`을 기준으로 사용하지 않는다. 승계 샘플은 원래 참조와 승계 근거를 보존한다. 추천 표본 수는 현재 후보와 함께 채택하며 재검증만 했으면 기존 수치를 유지한다. 9건과 10건의 경고가 승인 샘플 수와 독립적으로 표시되는지 검증한다.
10. **스케줄러 신호:** 일정 등록 템플릿의 `<aws.scheduler.scheduled-time>`과 실제 수신되는 UTC 시각 형식을 구별한다. 등록 템플릿과 수신 메시지는 각 JSON Schema를 사용한다.
11. **취소와 삭제:** 수동 수집 취소는 지원하지 않으며 승인 전 분석 후보 취소는 별도 기능이다. 삭제 영향 조회 오류는 0건으로 처리하지 않는다. 프로젝트 삭제 중 지연 쓰기 차단과 작업 재처리를 검증한다.
12. **최근 수집과 부분 실패:** 실제 collection 기준 최신 최대 5건을 반환하고 같은 회차의 수동 요청·적재 작업을 중복 집계하지 않는지 검증한다. 프로젝트별 적재 결과와 `NO_CHANGE`의 신규 데이터 유무를 확인한다.
13. **인증 입력:** 신규 비밀번호 조건은 회원가입·비밀번호 초기화에만 적용하며 로그인 시 기존 비밀번호에 소급하지 않는다. 비밀번호 형식 오류로 증명을 소비하지 않는다.
14. **외부 공개 범위:** OpenAPI·AsyncAPI는 팀 내부 개발 계약이다. 사용자용 Swagger UI·명세 배포는 MVP 범위가 아니다.

15. **반복 수집 종료:** 기준 `[A,A,B]`와 관측 `[A,B]`의 2건 집계, 누적 DOM의 같은 항목 재등장, 추가 구간 중 3개째가 일치해도 해당 구간 전체 처리, 추가 구간의 신규 후보·상세 참여, 최신 기준에는 없지만 DB에 있는 값의 중복 제거, 다음 구간 없음·잔여 1~4건·시간 제한, FULL 혼합을 검증한다. 적재 후보가 있는 대상과 없는 대상이 섞이면 같은 결과에서 can_ingest를 대상별로 확인한다.
16. **격리 파서:** 호출 인증과 생성 코드 실행 권한의 분리, CPU·메모리·시간 강제 한도, 코드 실패와 실행기 장애 구별, 항목 키 대조, 묶음 전체 기한과 개별 실행 한도, 상위 작업 기한 및 세 서비스의 동일 결과를 검증한다. Crawler 최초·리비전 수집의 목록·상세 필드 호출과 세 서비스의 기술 실패 완료 이벤트를 확인한다. 건수를 확정하지 못한 기술 실패는 정상 추출 0건이나 필드 실패 sidecar를 만들지 않는다.

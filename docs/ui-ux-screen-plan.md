# Weavo 화면 및 사용자 경험 기획안

- 작성일: 2026-11-08
- 상태: 화면 기획 최종안. 세부 문구와 API 응답 연결은 구현 과정에서 조정할 수 있다.
- 목적: 프로젝트 생성부터 분석·승인·수집·데이터 활용과 운영 중 문제 해결까지 일관된 사용자 흐름을 제공한다.
- 기준 문서: [스펙 결정 로그](spec-decision-log.md), [분석 서버 작업 흐름](analysis-server-workflows.md), [기능별 메시지 전달 흐름](service-message-flows.md), [서비스 작업 메시지와 데이터 형식](service-message-contracts.md)
- 우선순위: 제품 동작은 결정 로그를 따르고 서비스 간 메시지의 형식과 전달이 충돌하면 메시지 계약을 우선한다. 이 문서는 화면 구성과 행동을 구체화한 기획으로, 미정인 서버 정책이나 미구현 기능을 확정하지 않는다.

## 1. 제품과 설계 원칙

Weavo는 사용자가 여러 공개 웹사이트의 텍스트 데이터를 하나의 프로젝트에 연결하고, 공통 스키마를 검토·승인한 뒤 수집 결과를 웹과 읽기 API로 활용하는 서비스다. 사용자는 한 프로젝트의 단일 소유자다.

1. **다음 행동을 먼저 보여준다.** 사용자가 조치해야 할 문제가 있다면 대시보드 상단에 이유와 다음 행동을 함께 배치한다.
2. **현재 적용 상태와 변경 후보를 구분한다.** 후보 저장·검증·승인·실제 적용 완료는 서로 다른 상태다.
3. **비동기 작업을 끝까지 추적한다.** 분석, 수집, 승인 후 적용, 삭제는 접수 직후 완료로 표시하지 않는다. 작업 상태는 프로젝트와 출처별로 보여준다.
4. **데이터에 대한 영향을 승인 전에 설명한다.** 출처 삭제, 스키마 변경, 프로젝트 삭제와 회원 탈퇴의 결과를 구체적으로 보여준다.
5. **AI 추천은 근거와 샘플을 함께 검토한다.** 필드와 매핑을 자동 확정하지 않고 사용자가 수정하고 승인한다.
6. **오류와 정상적인 빈 값을 구분한다.** 새 데이터 없음, 실제 null, 해당 출처에 없는 필드, 추출 실패, 목록 항목 0건을 같은 상태로 표현하지 않는다.
7. **서버가 제공한 사실만 표시한다.** 근거 없는 진행률·남은 시간·전체 건수를 만들지 않는다. 색과 함께 텍스트·아이콘을 사용한다.

### MVP 범위

공개 HTTP/HTTPS 사이트의 텍스트를 대상으로 한다. 로그인·세션이 필요한 사이트, 캡차와 차단 우회, 이미지·첨부파일 수집은 지원하지 않는다. CSS 선택자 직접 편집은 제공하되 시각적 요소 선택, 드래그 매핑, XPath 직접 입력, 자연어 수정과 사용자 파싱 코드 편집은 제공하지 않는다. 팀 초대, 데이터 내보내기, 쓰기 API, 웹훅, 사용자 정의 수집 주기도 범위 밖이다.

## 2. 정보 구조와 전체 흐름

```text
랜딩
 ├─ 로그인 / 회원가입 / 비밀번호 초기화
 └─ 프로젝트 목록
     ├─ 프로젝트 생성 → 초기 분석 → 후보 검토·수정 → 승인
     │                                          ↓
     └─ 프로젝트 대시보드 ← 최초 수집·적재 진행 및 결과
          ├─ 데이터 조회 → 레코드 상세
          ├─ API 연결·사용 안내 → API 키 관리
          ├─ 수집 설정 → 공통 편집기·변경 비교·승인
          ├─ 프로젝트 설정 → 출처 추가·삭제 / 프로젝트 삭제
          └─ 작업 및 문제 상세 → 재확인·설정 검토
계정 설정 → 이름 변경 / 로그아웃 / 회원 탈퇴
```

로그인 후 프로젝트 내부에는 대시보드, 데이터, API 연결, 수집 설정, 프로젝트 설정을 공통 탐색으로 제공한다. 프로젝트 이름과 프로젝트 목록으로 돌아가는 경로를 유지한다. 작업 및 문제 상세는 별도 최상위 메뉴가 아니라 대시보드에서 여는 상세 영역 또는 하위 화면이다. 분석 진행은 독립 메뉴가 아닌 작업 상태 화면이다. 초기 설정과 운영 중 수정은 같은 편집기를 재사용하되 진입 목적과 적용 영향을 다르게 안내한다.

### 대표 흐름

1. 프로젝트 이름·수집 목적·공개 목록 URL·알림 여부를 입력하고 프로젝트를 생성한다.
2. 초기 분석을 요청한다. 출처별 분석과 공동 추천이 비동기로 진행된다.
3. 사용자는 성공·실패 출처, 공통 필드, 출처별 위치·선택자·이동 규칙과 샘플을 검토한다. 실패 출처는 재시도하거나 후보에서 제외할 수 있다.
4. 수정된 후보의 필요한 검증과 샘플 저장이 끝나면 현재 후보를 승인한다.
5. 승인 접수 후 출처별 최초 수집과 적재가 진행된다. 대시보드에서 완료·실패·확인 필요를 확인한다.
6. 사용자는 데이터를 조회하거나 API를 연결하고, 필요 시 출처·설정을 변경한다.

## 3. 공통 화면 규칙

### 상태와 작업

- 현재 공개 스키마는 Data DB 기준이며 Control이 Data 측 조회를 통해 화면에 제공한다. 수정 중 후보는 Control 분석 상태에서 제공한다. 최초 수집은 정상 적재된 출처의 데이터부터 공개하고 실패·0건 출처를 함께 표시한다. 최초 모든 출처가 실패하거나 정상 추출 0건이면 준비된 v1만으로 정상 운영 API를 공개하지 않고 확인 필요를 표시한다. 이후 한 출처라도 정상 적재되면 해당 성공 데이터를 공개한다. 공개 전 최초 복구는 공개 스키마 조회가 아니라 승인 v1 후보·커넥터와 승인 샘플을 적용 작업에서 확보한다.

- 출처, 프로젝트 추출 규칙, API 스키마, 개별 작업은 서로 다른 대상이므로 하나의 상태로 뭉개지 않는다. 사용자에게는 이해하기 쉬운 요약과 해당 대상의 상세 상태를 함께 제공한다.
- 화면에 사용할 대표 표현은 `준비 중`, `분석 중`, `검증 중`, `수집 중`, `데이터 처리 중`, `자동 복구 중`, `승인 대기`, `확인 필요`, `지원 불가`, `적용 보류`, `완료`다. 실제 단계가 서버에서 제공되지 않으면 상위 작업 상태만 표시한다.
- 승인 대기는 검증된 후보에 사용자 승인이 필요한 상태다. 자동 복구 중과 확인 필요를 구별한다. 목록 항목 0건은 즉시 확인 필요로 표시한다.
- 모든 출처가 완료되지 않았는데 프로젝트 전체를 완료라고 표시하지 않는다. 부분 성공 시 성공·실패 출처와 다음 조치를 함께 보여준다.
- 수집 요청의 202는 접수다. 요청 프로젝트가 이미 실행 중인 작업에 포함되면 그 결과를 기다리고, 포함되지 않으면 현재 실행과 관련 적재가 끝난 뒤 후속 수집을 기다린다.
- 서버가 제공하는 작업 ID를 이용해 진행과 결과를 조회한다. 페이지를 떠나도 프로젝트 목록·대시보드에서 진행 중인 작업과 후보로 돌아갈 수 있게 한다.

### 저장과 오류

- 로컬 편집 내용, 서버에 저장된 후보, 현재 적용 중인 설정을 시각적으로 구분한다. 화면 이동 시 저장되지 않은 입력이 있다면 이탈 확인을 제공한다. 후보의 저장·재개·취소는 실제 API와 정책에 맞춰 연결하고, 미구현 취소 동작을 약속하지 않는다.
- 후보 수정은 expected revision으로 저장한다. 서버는 영향 범위만 재검증하거나 유효한 검증을 승계한다. 화면은 저장 중·검증 중·통과·실패를 보여준다.
- 승인 시 현재 후보와 검증 revision이 일치해야 한다. 409 충돌이면 기존 입력을 무조건 버리지 말고 변경 사실을 안내한 뒤 최신 후보와 비교·재적용할 수 있도록 한다. 422는 미충족 조건과 해당 위치로 연결한다.
- 로딩, 빈 상태, 일시 오류, 권한 오류, 재시도 가능 여부를 명확히 표시한다. 재시도는 서버가 허용하는 작업에만 제공한다. 키·비밀번호 등 비밀값은 알림이나 로그에 노출하지 않는다.
- 필수 입력에 label과 오류 설명을 연결하고, 키보드 탐색·포커스 표시·읽을 수 있는 상태 문구를 제공한다.

## 4. 서비스 및 계정 화면

### 4.1 랜딩

**역할:** 제품의 가치와 지원 범위를 설명하고 시작 경로를 제공한다.

- 첫 영역에 여러 사이트의 데이터를 공통 구조로 모아 활용한다는 핵심 가치와 시작 버튼을 배치한다.
- `사이트 등록 → 분석·검토 → 수집 → 데이터·API 활용`을 간단한 흐름으로 설명한다.
- 공개 페이지·텍스트 중심이라는 범위와 CSS 수정이 필요할 수 있음을 안내한다.
- 비로그인 사용자는 회원가입·로그인, 로그인 사용자는 프로젝트 목록으로 이동한다.

### 4.2 로그인

이메일과 비밀번호를 입력하고 로그인한다. 실패 시 입력란 근처에 이해 가능한 오류를 표시하며 회원가입과 비밀번호 초기화로 연결한다. 성공하면 프로젝트 목록으로 이동한다. 세션 갱신이 실패하면 재로그인을 안내하고 진행 중이던 서버 작업은 다시 조회할 수 있게 한다.

### 4.3 회원가입

이메일 입력·인증번호 발송 → 6자리 번호 확인 → 비밀번호 입력·가입 순서로 구성한다. 발송 접수와 실패를 구분하고, 인증 실패 시 재입력 또는 재발송을 안내한다. 가입 성공 후 로그인으로 이동한다. 인증번호는 5분, 시도 최대 5회이며 인증 성공 시 가입 전용 일회용 증명값을 발급한다. 재발송은 이전 번호와 증명을 무효화한다. 인증 임시 상태가 유실되거나 확인에 실패하면 성공처럼 처리하지 않고 다시 인증하도록 안내한다.

### 4.4 비밀번호 초기화

이메일로 인증번호를 요청하고 번호를 확인한 뒤 새 비밀번호를 설정한다. 인증번호 확인과 비밀번호 변경은 별도 요청이다. 인증 확인 후 초기화 전용 일회용 증명을 발급하며 인증번호는 5분·최대 5회, 증명은 10분이다. 인증번호 확인과 변경 API는 각각 `/auth/v1/password-reset-requests/confirm`, `/auth/v1/password-resets`다. 성공하면 로그인으로 연결하고 인증·변경 실패는 각각 구분한다. 발송 요청에서 계정 유무 또는 개별 메일 발송 결과는 드러내지 않고 공통 장애만 안내한다. 초기화 시 모든 refresh 세션이 폐기되며 기존 access token은 만료까지 유효하다.

### 4.5 계정 설정

일반 로그아웃은 refresh 세션을 폐기하고 이미 발급된 access token은 짧은 잔여 유효시간을 허용한다. 탈퇴 진행 계정은 유효한 기발급 access token이 있어도 서버에서 접근을 차단한다. 원본 계정 상태를 확인할 수 없으면 요청을 거절한다. token 정확한 유효시간은 운영 설정이다.

이메일을 확인하고 이름을 변경하며 로그아웃할 수 있다. 회원 탈퇴는 별도의 위험 영역에서 시작한다. 계정, 소유 프로젝트, 수집 데이터, API 키와 출처 연결이 정리됨을 안내하고 명시적 확인을 받는다. 다른 프로젝트가 사용하는 공유 출처는 유지된다.

탈퇴 요청이 접수되면 `탈퇴 요청이 접수되었습니다. 관련 데이터 정리는 순차적으로 진행됩니다.`라고 안내한 뒤 세션을 정리한다. 요청 접수를 최종 삭제 완료라고 표현하지 않는다. 탈퇴 후 진행 조회 화면이나 별도 통지 기능은 추가하지 않는다. 접수 실패는 현재 화면에서 재시도할 수 있도록 안내한다.

## 5. 프로젝트 화면

### 5.1 프로젝트 목록

**역할:** 프로젝트를 찾고 조치가 필요한 작업으로 재진입한다.

- 상단에 새 프로젝트 생성 버튼을 둔다. 각 카드 또는 행에는 프로젝트 이름, 수집 목적 요약, 제공 가능한 상태와 마지막 정상 갱신 정보를 표시한다.
- 분석 중, 승인 대기, 확인 필요, 삭제 중 등에는 해당 작업으로 가는 행동을 함께 제공한다. 상태는 색과 문구로 구분한다.
- 프로젝트가 없으면 시작 설명과 생성 버튼을 보여준다. 목록 조회 실패는 빈 목록과 구별한다.

### 5.2 프로젝트 생성

**역할:** 프로젝트와 출처 후보를 등록하고 초기 분석을 시작한다.

1. 프로젝트 이름과 수집 목적을 입력한다. 목적은 AI의 추천 기준이며 현재 생성 후 변경할 수 없음을 안내한다.
2. 공개 목록 페이지 URL을 한 개 이상 입력한다. 행을 추가·삭제할 수 있고 형식·중복·접근 제한 오류를 해당 행에 표시한다. 실제 콘텐츠에 영향을 주는 쿼리값을 임의로 지우지 않는다.
3. 프로젝트별 이메일 알림 여부를 선택한다.
4. `프로젝트 만들고 분석 시작`으로 생성 후 분석을 요청한다.

공개 텍스트 범위, 인증·차단 우회 및 이미지·첨부파일 미지원 안내를 입력 가까이에 둔다. 프로젝트 생성과 분석 요청은 별도 작업이므로 생성 성공 후 분석 요청이 실패하면 생성된 프로젝트를 유지하고 분석 재시작 경로를 제공한다. 이미 진행 중인 분석의 재요청은 기존 작업을 확인한다.

### 5.3 초기 분석 진행

분석 진행 화면에서는 전체 분석 중 상태만 보여주고 목록·상세 확인과 공통 필드 추천이 진행된다고 설명한다. 출처별 성공·실패는 완료 이벤트가 도착한 뒤 결과 화면에 표시한다. 퍼센트나 남은 시간을 임의로 계산하지 않는다. 사용자가 화면을 떠나도 프로젝트에서 돌아올 수 있다. 분석 결과가 일부 실패하면 실패 출처와 가능한 재시도·제외 행동을 결과 검토 화면에 표시한다. 성공한 출처가 하나 이상이면 해당 출처들로 공동 추천을 진행하고, 전부 실패하면 승인 가능한 후보를 표시하지 않는다.

### 5.4 프로젝트 대시보드

**역할:** 현재 상태를 파악하고 다음 행동을 결정하는 운영 중심 화면.

1. **조치 필요 영역:** 0건, 자동 복구 실패, 승인 대기 등 사용자 조치가 필요한 항목을 우선 표시한다. 문제 대상·영향·기존 데이터 제공 여부·행동을 함께 쓴다.
2. **프로젝트 요약:** 마지막 정상 갱신 시각, 현재 활성 API 버전, 최근 작업 결과와 전체 수동 수집 버튼을 제공한다. 서버에서 제공되지 않는 합계는 임의로 만들지 않는다.
3. **출처 목록:** 출처 URL, 상태, 마지막·다음 실행 시각, 실행 시간, 수집 건수와 결과, 출처별 수동 수집을 표시한다. 필요하면 행에서 작업 상세로 이동한다.
4. **작업 상세:** 요청 접수, 대기, 수집, 적재, 완료·실패와 출처별 결과를 제공 가능한 수준에서 표시한다. 공유 출처에 연결된 다른 사용자의 프로젝트 정보는 노출하지 않는다.

정기 수집은 공유 출처의 12시간 일정이며 수동 요청으로 기존 일정이 바뀌지 않는다. 실행 중 요청이 현재 실행에 포함되면 해당 결과를 기다리고, 포함되지 않으면 후속 수집을 기다리는 상태로 표시한다. 중복 수동 요청은 요청별 작업으로 기존 실행에 연결하고 취소 버튼은 제공하지 않는다.

### 5.5 문제 상세와 재확인

- `목록 항목 0건`과 `목록은 있으나 이 프로젝트의 정상 추출 0건`을 구분한다. 새 데이터가 없는 정상 결과와 혼동하지 않는다.
- 해당 출처, 실제 페이지로 가는 링크, 수집 항목 수·정상 추출 결과·최근 회차별 건수 추이, 마지막 정상 데이터 유지 여부를 제공 가능한 범위에서 표시한다. 추이는 참고 정보이며 실제로 사이트가 비었다는 자동 판정이 아니다. 내장 사이트 미리보기는 전제하지 않는다.
- `재확인`은 새 분석 작업을 접수하고 그 결과와 후속 수집·적재를 추적한다. 이전 변경 종료 결과 확인 전이면 대기 상태를 표시한다. 실패하거나 여전히 0건이면 확인 필요를 유지한다.
- `출처 삭제 검토`는 프로젝트 설정의 삭제 후보 흐름으로 연결한다. 빈 목록을 확정해 바로 데이터를 삭제하는 별도 행동은 두지 않는다.
- 자동 복구 중에는 진행 상태를, 스키마 변경이 필요한 경우 승인 대기를, 복구 실패·검증 불가는 확인 필요를 표시한다. 스키마가 유지되고 검증을 통과한 자동 복구는 사용자 승인 없이 적용할 수 있다.

### 5.6 프로젝트 설정

- **기본 정보:** 이름 변경, 수집 목적 읽기 전용 표시.
- **알림:** 프로젝트별 이메일 알림을 켜거나 끈다. 확인 필요·승인 대기 등 사용자 조치가 필요한 상황을 알린다는 설명을 둔다.
- **출처:** 추가와 삭제를 후보로 만들고 공통 편집기에서 검토·최종 승인한다. 현재 연결과 변경 후보를 구분한다.
- **프로젝트 삭제:** 데이터·API 키·연결 등 영향을 설명하고 확인한다. 삭제 접수와 완료를 구분하고 처리 중 상태를 보여준다. 삭제 작업 결과 조회는 프로젝트 자체 조회와 분리될 수 있도록 작업 조회를 활용한다. 실패하면 완료라고 표시하지 않고 상태와 재처리 안내를 제공한다.

## 6. 공통 분석·수집 설정 편집기

### 6.1 진입과 화면 구조

초기 분석, 기존 프로젝트의 출처 추가, 스키마 수정, 운영 중 확인 필요에 같은 편집기를 사용한다. 상단에는 프로젝트, 작업 목적, 현재 적용 상태와 수정 후보, 저장·검증 상태를 표시한다. 화면의 기본 검토 순서는 다음과 같다. 단계는 안내용이며 자유롭게 이동할 수 있다. 이전 단계의 수정으로 검증이 무효화되면 영향을 받은 항목을 다시 확인하도록 표시한다.

```text
출처 확인 → 공통 필드 → 출처별 수집 규칙 → 샘플 검토 → 변경 확인·승인
```

### 6.2 출처 확인

최초 분석에서 성공한 출처가 하나 이상이면 그 결과로 공동 스키마 후보를 추천하고 실패 출처는 재시도·제외할 수 있다. 모든 출처가 실패하면 후보를 승인할 수 없다. 재시도 결과는 사용자 수정을 보존하고 필요한 검증을 수행한다.

- 출처별 분석 결과와 포함·제외 상태를 표시한다. 실패 출처에는 재시도와 후보에서 제외 행동을 제공한다.
- 재시도가 진행되는 동안 기존 사용자 수정을 유지한다. 결과가 현재 revision과 다르면 이전 결과로 덮어쓰지 않고 최신 후보 기준 재검증이 필요함을 안내한다.
- 기존 프로젝트에 출처를 추가할 때는 활성 스키마의 필드에 먼저 매핑한다. 새로운 공통 필드가 필요하면 스키마 변경 흐름으로 연결한다.
- 공동 추천은 성공한 출처가 하나 이상이면 진행한다.

### 6.3 공통 필드

공통 필드를 표로 보여주고 화면 표시 이름, API 이름, 타입, 출처별 샘플, 추천 근거와 매핑 상태를 제공한다. 필드를 선택하면 출처별 값과 위치를 확인·수정할 수 있다.

- API 이름은 영문 소문자 snake_case, 최대 64자, 예약어 제외 조건을 적용한다.
- 지원 타입은 string, number, boolean, date, datetime, url이다. 사용자 정의 필드는 nullable이며 해당 출처에 원래 없는 필드는 null로 표현할 수 있다.
- 의미가 같은 필드의 추천 근거와 샘플을 보여주고 연결 해제·재연결 및 수동 매핑을 지원한다. 하나의 출처 필드를 여러 공통 필드로 분리하는 1:N은 지원하지만 N:1 결합은 지원하지 않는다.
- 정상 샘플이 10건 미만이면 표본 부족을 알린다. AI 추천은 사용자의 승인 전 자동 확정하지 않는다.

### 6.4 출처별 수집 규칙

출처와 필드를 선택해 목록·상세·해당 출처에 없음 중 위치를 지정하고 CSS 선택자를 편집한다. 상세 필드는 해당 목록 항목에서 링크를 따르거나 버튼을 클릭하는 이동 선택자와, 열린 상세 DOM에서 값을 추출하는 선택자를 별도 입력한다. 이동 대상·대기·복귀는 분석이 만든 해당 필드 규칙을 사용하며 수정된 후보를 재검증한다. 일치 요소 수와 추출 텍스트, 가능한 상세 URL 등 검증 샘플을 가까이에 보여준다.

목록 항목 구분, 다음 페이지·더 보기·스크롤 등 목록 이동, 상세 링크 또는 클릭, 상세 화면에서 돌아오는 방식을 확인한다. 기본 화면에는 이해하기 쉬운 방식과 검증 상태를 표시하고 상세 규칙은 펼쳐서 편집한다. 실제 편집 가능한 매개변수와 지원 CSS·텍스트·속성 범위는 API·검증 구현에 맞춰 확정한다. 목록 HTTP 가능 여부만 승인 전 내부 검증하며 상세는 브라우저로 고정한다. 사용자의 상세 URL 생성 템플릿 직접 입력과 별도 HTTP 선택 화면은 제공하지 않는다.

파싱이 필요하면 원본 문자열과 변환 결과를 나란히 보여준다. 생성된 Java 파싱 코드를 직접 수정하거나 자연어로 규칙을 지시하는 입력은 두지 않는다. 수정 후 서버의 필요한 재검증 결과를 표시하며 별도 검증 요청 API가 있다고 가정하지 않는다.

### 6.5 샘플 검토

출처별 샘플 표에서 공통 필드와 추출 결과를 확인한다. 정상 null, 해당 출처에 없는 필드와 확인 가능한 오류를 구분한다. 실패 항목에서 해당 필드·규칙으로 이동한다. 샘플 저장 실패 또는 검증 불가는 승인 가능한 성공으로 표시하지 않는다.

### 6.6 변경 비교와 최종 승인

승인 전에 포함·제외 출처, 필드·매핑 변경, 검증 상태, 승인 후 실행될 작업을 요약한다. 스키마 구조 변경이면 추가·삭제·이름·타입 변경, 기존과 후보 응답 예시, API 버전 변경과 데이터 교체 영향을 강조한다. 재수집되지 않은 과거 데이터와 기존 record_id가 전환 후 제공되지 않을 수 있고 이전 API 버전은 종료된다는 내용을 확인받는다.

**동일 레코드 비교 UI:** 서버가 신뢰할 수 있는 대응 정보나 동일성 근거를 제공하면 해당 샘플의 이전 값과 후보 값을 나란히 표시한다. 대응 정보가 없거나 신뢰할 수 없으면 프론트엔드가 URL이나 제목만으로 동일 게시물이라고 단정하지 않는다. 대신 이전·후보 샘플을 각각 보여주고 `자동 대응 불가`라고 표시하며, 필드별 추출 성공률·값 변경률·누락 등 제공 가능한 집계와 함께 사람이 비교하도록 한다. 표본 수가 적으면 실제 건수를 표시하고 부족을 알린다. 비교용 연결을 사용자가 일시적으로 선택하는 UI는 데이터 대응을 변경하거나 확정한 것처럼 저장하지 않으며, 필요한 데이터와 화면 복잡도를 확인해 구현한다.

현재 후보와 유효한 검증 결과가 일치해야 승인할 수 있다. 승인 접수는 적용 완료가 아니므로 이후 작업 상태를 대시보드에서 보여준다.

### 6.7 출처 추가·삭제 적용

- **출처 추가:** 기존 스키마 기준 분석·샘플 검토·승인 후 추가 출처의 최초 수집과 정상 적재를 거쳐 공개·활성화한다. 0건·실패한 출처의 부분 적재는 공개하지 않고 확인·복구한다.
- **출처 삭제만:** 삭제 후보와 해당 출처의 삭제 영향을 표시하고 승인 후 적용한다. 남은 출처는 재수집하지 않는다. 삭제 출처에만 있던 공통 필드는 자동 삭제하지 않는다. 필드 삭제를 선택하면 별도의 스키마 변경 영향을 검토한다.
- **구조 유지 + 추가·삭제:** 모든 추가가 정상 적재·공개된 뒤 삭제한다. 일부 추가 실패 시 성공한 추가 출처는 유지하고 기존 출처 삭제는 보류한다. 삭제 실패 시 추가 출처를 되돌리지 않고 삭제 상태·재처리를 표시한다. 처리 중 기존과 새 출처가 동시에 보일 수 있음을 안내한다.
- **스키마 구조 변경 포함:** 모든 최종 대상 출처의 새 데이터를 준비하고 조건을 충족하면 데이터와 API 버전을 함께 전환한다. 하나라도 실패하거나 0건이면 전환을 보류하고 기존 데이터와 API를 유지한다.
- 출처 삭제 영향 건수 조회가 실패하면 `확인 불가`로 표시하고 0건으로 취급하지 않는다. 영향을 확인할 수 없으면 승인을 보류하고 재조회한다.

## 7. 데이터 조회

**역할:** 공개된 프로젝트 데이터를 공통 스키마 기준으로 확인하고 필터·정렬한다.

- 스키마 기반 표, 타입에 맞는 필터 연산자, 단일 필드 정렬, 다음 결과 이동을 제공한다. 여러 조건은 AND로 결합된다. OR·괄호 검색·전문 검색은 제공하지 않는다.
- 행을 선택하면 공개된 필드, 출처 URL과 수집 시각 등 제공 가능한 정보를 상세 패널에 보여준다. 원본 URL이 없는 경우 그 사실을 표시한다.
- 실제 null과 빈 문자열을 구분한다. 추출 실패가 포함된 레코드는 부분 저장하지 않고 정상 추출 건수에서 제외하므로 데이터 목록·상세에 정상 레코드로 표시하지 않는다. 운영 오류는 작업·문제 상세에서 확인한다.
- 커서 기반 페이지 이동을 사용한다. 전체 건수·마지막 페이지는 제공되지 않으면 표시하지 않는다. 조건 변경 시 첫 결과부터 조회하고, 데이터 revision 변경으로 커서가 무효화되면 안내 후 첫 결과를 다시 불러온다.
- 최초 수집 전, 공개 데이터 없음, 필터 결과 없음, 로딩·오류를 각각 다른 빈 상태로 표현한다.
- 일반 수집에서 같은 게시물의 필드값이 달라지면 별도 레코드가 생길 수 있고, 출처 간 같은 게시물도 자동 병합하지 않음을 안내한다. record_id는 서비스 내부 식별자이며 원본 게시물 ID나 변경 이력이 아니다. CSV·Excel 내보내기는 제공하지 않는다.

## 8. API 연결·사용 안내

- 현재 활성 API 경로와 스키마 버전, 필드의 API 이름·타입을 보여주고 경로 복사를 제공한다.
- X-API-Key 인증, curl 예시, 필터·정렬·커서·limit·fields, 주요 오류와 410·429 대응을 설명한다. 전체 건수는 기본 제공되지 않는다.
- 키 이름을 입력해 프로젝트별 읽기 전용 키를 발급하며 발급 개수 제한은 두지 않는다. 비밀값은 생성 직후 한 번만 보여주고 복사할 수 있게 한다. 창을 닫으면 다시 볼 수 없음을 안내한다.
- 키 목록에는 이름과 제공 가능한 마지막 사용 시각을 표시하고 폐기를 제공한다. 키 관리는 Data의 `/api/projects/{p}/keys` API를 사용한다. 폐기 전 외부 연결에 미치는 영향을 설명한다. 교체는 새 키 발급·적용 후 기존 키 폐기 순서로 안내한다. 키당 분당 60회 제한을 안내한다.
- 스키마 변경 승인 대기·전환 중에는 기존 활성 경로를 보여준다. 전환 보류 시 기존 경로 유지, 전환 완료 시 새 경로 활성과 이전 경로 종료를 명확히 표시한다. 키 폐기 완료 시점은 서버의 실제 권한 무효화 완료 계약에 맞춘다.

## 10. 구현 시 연결 기준

이 기획은 화면 행동의 기준이며 다음 세부사항은 문서와 실제 API 구현에 맞춰 유연하게 연결한다.

- 작업 조회에 실제로 제공되는 단계·출처별 결과·오류·시간·건수에 따라 표시 수준을 정한다. 백엔드가 제공하지 않는 정보를 프론트엔드에서 확정 사실로 추정하지 않는다.
- 사용자 정의 CSS·속성 추출의 구체 지원 범위는 구현 계약과 검증 결과에 맞춘다. 최초 분석 일부 성공, 후보 취소·재진입, 작업 취소 미지원과 중복 수집 요청의 처리는 확정된 계약을 따른다.
- 0건 화면에 필요한 실제 사이트 링크·회차별 건수, 삭제 영향 건수, 스키마 변경 전후 집계·샘플의 조회 경로와 권한은 관련 API에 연결한다. 조회 실패와 실제 0을 구분한다.
- 동일 레코드 비교는 신뢰할 수 있는 대응 근거가 있을 때 나란히 보여주고, 없을 때는 독립 샘플 비교로 안전하게 내려간다. 프론트엔드 비교 방식은 추후 실제 데이터와 함께 개선한다.
- 실제 null·ABSENT와 추출 실패를 구분한다. 실패 레코드는 저장하지 않으며 복구 후보 검증은 최초 포함 최대 3회이며 실패 세부 판정은 구현 검증 대상이다.
- 이 문서는 API의 세부 필드명이나 디자인 시스템을 고정하지 않는다. 화면 구현 시 공통 컴포넌트, 문구, 반응형 배치와 실제 응답 모델을 구체화한다.

## 11. 최신 API·상태 연결

- 프로젝트 생성은 Idempotency-Key를 사용하고 생성 성공 후 출처 ID 목록을 조회해 분석을 시작한다. 목록·상세의 current_analysis_id로 기기를 바꿔도 분석에 재진입한다. 승인 전 후보 취소만 가능하다.
- Analysis 출처별 진행 단계를 서버가 알 수 없으면 상위 분석 중 상태만 표시한다. 출처별 목록·정상 추출 수, 시각과 API 키 last_used_at은 서버 응답이 null이면 알 수 없음으로 표시한다.
- 후보 편집은 수정한 필드만 PATCH하며 추천 근거와 S3 샘플을 Control 조회 응답으로 확인한다. 상세 이동은 필드별 브라우저 규칙을 사용하며 목록 URL은 직접 변경하지 않고 출처 삭제·추가로 처리한다.
- 최초 v1은 정상 적재된 출처부터 공개하고 모든 출처 실패·0건이면 공개 전이다. v2는 전부 준비 성공 후 전환하며 실패 시 기존 버전이 유지된다. 삭제 접수와 완료를 구분한다.
- access/CSRF는 웹 메모리에 두고 재시작 시 허용 Origin에서 Auth csrf를 조회해 refresh한다. 로그인 복원·토큰 갱신 실패와 Auth 서비스 일시 장애를 구분한다.

### 출처 및 원문 링크 표시

출처를 식별할 때는 별도 출처명을 입력하거나 표시하지 않고 목록 URL을 표시한다. 레코드의 `source_url`은 해당 항목을 직접 열 수 있는 주소가 확인된 경우에만 제공한다. null이면 원문 링크를 표시하지 않으며, 목록 URL을 항목 링크로 대신하지 않는다.

## 12. 마지막 출처와 동일 버전 설정

- 마지막 출처도 삭제할 수 있다. 삭제 영향을 보여주고 승인한 뒤 프로젝트와 공개 스키마·API는 남으며 데이터는 빈 목록이다. 삭제는 수집 0건 문제가 아니다. 새 출처를 기존 스키마로 추가할 수 있다.
- 최초 수집이 모두 실패해 공개 API가 없을 때 마지막 출처를 삭제하면 프로젝트와 승인된 v1 후보는 보관하고 API는 비공개다. 새 출처를 추가해 수집을 성공하면 v1을 공개한다. 출처가 0개인 삭제 전용 후보는 승인할 수 있다.
- 표시명·설명·순서 변경이 같은 버전에서 적용되는 동안 저장 중 상태를 표시하고 Data 반영 성공 후 완료를 표시한다. 추천 근거가 없는 사용자 추가 필드는 근거 없음을 표시한다.


수동 수집 대상 출처가 없으면 409 NO_ACTIVE_SOURCES를 받아 출처 추가를 안내한다. 후보 조회·수정 및 수집 작업의 HTTP 본문과 오류는 메시지 명세 19.9를 따른다. 실패 출처 재시도는 다른 출처와 사용자가 수정한 필드를 유지한다.


## 실행 계약과 표시

- 분석 후보 재진입은 GET의 전체 이동 규칙·제외 출처·검증과 샘플 revision을 읽어 복원한다. 서버가 현재 revision 충돌을 반환하면 재조회하며, 미저장 입력은 서버 결과로 가정하지 않는다.
- 결과 화면에서 별도 출처명 대신 원래 목록 URL을 표시하고 내부 식별은 project_source_id로 한다. Figma의 기존 예시 출처명은 URL 표시로 수정할 대상이다.
- 수동 수집은 출처별 적재까지 완료한 결과를 성공·부분 실패·실패로 표시한다. 최초 분석과 수집에서 일부 실패한 출처는 별도 문제로 표시하고 성공 결과는 유지한다.
- 비밀번호 초기화 인증번호는 별도 확인 API에서 확인하고 그 오류를 해당 화면에 표시한다. 발송 요청 202는 실제 발송 보장이 아니며 존재하지 않는 계정 여부를 노출하지 않는다. Figma의 기존 확인 시점 문구는 변경 대상이다.

### 공통 오류 상태

서버가 실제로 반환한 실패를 기존 공통 피드백 컴포넌트로 해당 화면에 표시한다. 재시도 가능한 경우에만 재시도 동작을 제공하며, 표시만으로 실패가 복구되었다고 간주하지 않는다.

| 상황 | 표시와 다음 행동 |
|---|---|
| 로그아웃·이름 저장 또는 프로젝트 설정 저장 실패 | 실패를 알리고 기존 화면과 입력을 유지하며 다시 시도한다. |
| 다른 출처 집합의 분석 요청이 진행 중인 409 | 진행 중인 분석이 있음을 표시하고 현재 분석으로 돌아간다. |
| 샘플 저장·조회 또는 검증 실패 | 샘플을 확인할 수 없음을 표시하고 재시도한다. 유효한 검증 전까지 승인을 차단한다. |
| 모든 출처의 분석 실패 | 각 실패 상태를 표시하고 재시도나 제외를 안내한다. 성공 출처가 없으면 승인하지 않는다. |
| 데이터 조회 커서가 무효화된 409 | 목록이 변경됐음을 알리고 첫 결과부터 다시 불러온다. |

## 79개 흐름 점검에 따른 화면 표시

- 초기 분석이 진행되는 동안 전체 `Analysis in progress`만 표시한다. 출처별 성공·실패와 재시도는 결과 이벤트가 접수된 뒤에 표시한다. 개별 출처의 처리 단계나 진행률을 추측해 표시하지 않는다.
- 프로젝트 생성 요청의 결과를 받지 못하면 같은 생성 시도의 본문과 Idempotency-Key를 sessionStorage에서 복원해 재요청한다. 서버 보관 기한이 끝났으면 자동 재전송하지 않고 프로젝트 목록을 확인하게 한다. 분석 미시작 프로젝트는 목록 또는 상세에서 `Start analysis`를 제공한다.
- 가입 응답이 불확실하면 인증 재시도와 로그인 경로를 안내한다. 초기화 메일의 접수 표시는 실제 수신 여부나 계정 유무를 밝히지 않는다. reset_token이 소비됐거나 결과가 불확실하면 인증번호부터 다시 확인하도록 안내한다.
- 이름 저장은 성공 피드백을 표시하고 실패 시 입력을 유지한다. 로그아웃 요청 실패 또는 결과 불확실은 공통 피드백으로 안내하고 재시도를 제공한다. 탈퇴의 확정 접수 실패와 접수 여부 확인 중을 구별하고 후자에서 계정이 사용 가능하다고 단정하지 않는다.
- 정상 추출 건수 null은 `Not measured` 또는 `—`로, 실제 측정한 0은 `0`으로 표시한다. 0건 문제는 기존 정책에 따라 표시한다.

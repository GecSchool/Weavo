# Git 협업 컨벤션

이 문서는 브랜치 이름, 커밋, Pull Request의 팀 기준이다. 코드 작성·테스트는 팀 코드 컨벤션 최종본을 따르며, 자동 검사 설정은 [컨벤션 환경 안내](conventions-setup.md)를 참고한다. 브랜치 이름은 기존 코드 컨벤션 PDF 9.1절의 `feat/` 예시 대신 이 문서의 `feature/` 형식을 사용한다. 그 외 기존 코드 컨벤션은 그대로 따른다.

## 브랜치

최신 `main`을 기준으로 작업별 브랜치를 만들고 Pull Request로 `main`에 병합한다. 이슈가 있는 작업은 다음 형식을 사용한다.

```text
<작업 종류>/<이슈 번호>-<작업 내용>
```

작업 내용은 영문 소문자와 하이픈으로 간결하게 작성한다. 이슈 번호에는 `#`을 붙이지 않는다.

| 작업 종류 | 용도 | 예시 |
|---|---|---|
| `feature` | 기능 구현 | `feature/2-message-contracts` |
| `fix` | 오류 수정 | `fix/12-crawler-timeout` |
| `refactor` | 동작을 유지하는 구조 개선 | `refactor/13-connector-parser` |
| `test` | 테스트 추가·개선 | `test/14-navigation-rules` |
| `docs` | 문서 수정 | `docs/15-update-architecture` |
| `chore` | 설정·의존성 등 유지보수 | `chore/18-update-dependencies` |

이슈가 없는 작업은 `<작업 종류>/<작업 내용>`을 사용한다. 위 형식은 팀 약속이며 현재 브랜치 이름을 검사하는 Git 훅은 없다.

## 커밋

한 커밋에는 하나의 설명 가능한 변경 목적을 담는다. 기본 형식은 다음과 같으며 범위는 선택 사항이다.

```text
<유형>: <변경 내용>
<유형>(<범위>): <변경 내용>
```

유형은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore`를 사용한다. 브랜치 접두사는 `feature`, 커밋 유형은 `feat`로 구분한다.

```text
feat: 수집 메시지 모델 추가
fix(crawler): 수집 시간 제한 검증
```

가능하면 포맷만 바꾼 변경과 기능 변경을 분리한다. 비밀값, 로컬 설정, 생성 파일과 대용량 실행 결과는 커밋하지 않는다. 기존 `commit-msg` 훅은 위 유형과 형식을 검사하며 Git의 merge·revert·fixup·squash 메시지도 허용한다.

## Pull Request

PR 본문에는 목적, 주요 변경, 실행한 검증과 결과, API·스키마 영향, 미해결 사항을 적는다. API 계약이나 DB 마이그레이션을 변경하면 영향받는 코드와 테스트를 함께 표시한다. 리뷰하기 좋은 크기로 나누고 관련 없는 변경을 섞지 않는다.

이슈를 완료하는 PR이라면 본문에 `Closes #2`처럼 이슈 종료 키워드를 적거나 GitHub에서 이슈를 연결한다. 이슈 번호를 브랜치 이름에 넣는 것만으로 GitHub 연결을 가정하지 않는다. PR이 이슈의 일부만 다룬다면 `#2`처럼 참조하고 종료 키워드는 이슈 완료 시점에 사용한다.

병합 전에는 CI 결과와 저장소에 적용된 리뷰 규칙을 확인한다. 자동 검사를 별도 합의 없이 우회하지 않는다.

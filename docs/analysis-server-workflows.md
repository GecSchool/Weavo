# 분석 서버 작업 흐름

- 상태: 구현 전 설계 정리. 제품 정책은 [스펙 결정 로그](spec-decision-log.md)를 참고하며, 서비스 간 메시지 형식과 흐름이 충돌하면 [메시지 명세](service-message-contracts.md)를 우선한다. 전달 순서는 [메시지 전달 흐름](service-message-flows.md)을 참고한다.
- Analysis는 브라우저 분석, AI 후보 생성, 탐색·추출 검증, 승인 샘플 저장과 규칙 복구를 담당한다. 작업 조정은 Control, 반복 수집은 Crawler, 최종 스냅샷 추출과 DB 적재는 Ingestion이 담당한다.
- 아래 공통 기능 표시는 논리적으로 반복되는 처리 단계다. 표시가 같다고 입력과 목적이 다른 모든 상황을 반드시 동일한 함수나 AI 호출로 구현한다는 뜻은 아니다.

## 공통 기능

현재 공개 스키마·필드 정의의 원본은 Data DB다. Control은 기존 프로젝트 분석·복구에서 Data 측 공개 스키마를 조회해 커넥터와 함께 전달하며 조회 실패를 빈 스키마로 바꾸지 않는다. 최초 수집이 모두 실패해 공개 전인 경우에는 승인된 v1 후보·커넥터를 사용한다. 초기·수정 중 후보는 Control에서 관리한다. 승인된 v1·v2는 Control이 기존 Ingestion 큐의 schema.prepare로 비공개 준비하고 schema.prepared 성공 후 출처 수집을 요청한다.

| 표시 | 기능 |
| --- | --- |
| **[A] 화면 확인** | 브라우저로 목록·상세 화면의 DOM과 URL 확인 |
| **[B] 탐색 실행** | 목록 이동·더 보기·스크롤·상세 링크 또는 클릭 후보 실행 |
| **[C] 추출** | 후보 선택자와 필드 규칙을 적용해 샘플값 추출 |
| **[D] 검증** | 필드값·타입·null·추출 실패와 탐색 결과 확인 |
| **[E] AI 판단** | DOM·이동 결과·필드 후보를 바탕으로 추천 또는 후보 보완 |
| **[F] 편집·재검증** | 사용자 수정 후보의 영향 범위를 검증하고 결과 표시 |
| **[G] HTTP 확인** | 사용자 승인 전 목록의 HTTP 추출·탐색 가능 여부를 내부 비교. 상세는 항상 브라우저 |
| **[H] 결과 전달** | Analysis가 후보·검증 결과와 샘플 식별정보를 Control에 전달 |

## 실행 시도와 결과 채택

Analysis는 Control의 job_id에 대해 attempt_id로 선점하고 lease를 갱신한다. 각 시도는 중간 후보·샘플과 결과 이벤트를 별도 S3 경로에 저장한 뒤 attempt_id를 담아 Control에 보낸다. Control은 유효 lease·현재 시도와 후보 revision 및 영향 프로젝트의 유효성을 DB 트랜잭션으로 검사해 결과·참조·후속 Outbox를 채택한다. 사용자 수정이나 취소로 revision이 바뀐 결과와 만료된 이전 시도는 후보를 덮어쓰지 않는다. RETRY_SOURCE의 기존 intermediate_ref·검증 승계 sample_ref는 기준 revision·출처·승계 근거를 확인한다. Control 점검은 유효 시도가 사라진 미완료 job을 시작 기한 안에서 같은 입력으로 재요청한다. 자세한 선점·중복·기한 계약은 메시지 명세 11.1과 S3 명세 1.2를 따른다.

## 1. 초기 분석과 다중 출처 공동 추천

1. 사용자가 프로젝트 이름, 수집 목적, 출처 URL과 이메일 알림 여부로 프로젝트를 생성한다. 웹은 반환된 project_id로 출처 목록을 조회해 project_source_id를 확보한 뒤 분석을 시작한다. Control은 분석 작업을 생성해 Analysis에 요청한다.
2. Analysis는 각 출처에서 **[A]** 첫 목록 화면을 브라우저로 확인한다. **[E]** AI에 필드·추출 규칙·목록 이동·상세 이동 후보를 요청한다.
3. 상세 후보가 있다면 **[B]** 실제로 이동해 **[C]** 내용을 추출하고, **[E]** 목록 항목과의 연결 및 필요한 필드를 판단한다. 상세 링크와 클릭 방식을 모두 지원한다.
4. 목록 이동 후보를 **[B]** 실행하고 이동 전후 화면과 추출 결과를 **[C] [D] [E]** 확인한다. 적합하지 않으면 제한 시간 안에서 후보를 보완하고 다시 검증한다.
5. 출처별 필드 후보·샘플값·선택자·이동 후보를 S3에 임시 저장한다. Analysis는 성공한 출처의 중간 결과를 읽어 **[E]** LLM에 공통 필드와 출처별 매핑을 추천받는다. 출처별 중간 결과와 검증 샘플은 별도 객체이며 분석 DOM 원본은 보관하지 않는다. 본문·경로·정리 조건은 [S3 저장 명세](s3-storage-contract.md)를 따른다. 최초 분석에서 성공한 출처가 하나 이상이면 그 결과로 공동 스키마 후보를 추천하고 실패 출처는 재시도·제외할 수 있다. 모든 출처가 실패하면 후보를 승인할 수 없다. 재시도 결과는 사용자 수정을 보존하고 필요한 검증을 수행한다.
6. 후보에 대해 **[G]** 목록의 HTTP 추출·탐색 가능 여부를 내부 확인한다. 목록은 가능하면 HTTP, 그렇지 않으면 브라우저를 사용하고 상세는 항상 브라우저로 처리한다. 별도의 HTTP 결과 화면은 두지 않는다.
7. Analysis는 사용자 승인 전에 analysis_id·후보 revision·프로젝트·출처로 구분되는 검증 샘플값을 S3에 저장하고 **[H]** 후보·검증 결과와 샘플 식별정보를 Control에 보낸다. 저장 실패는 승인 가능한 성공으로 처리하지 않는다.
8. Control은 후보·검증 상태를 관리하고 S3에서 샘플을 읽어 사용자에게 스키마·원천별 필드 위치·CSS·이동 결과와 함께 제공한다.
9. 사용자가 후보를 수정하면 Control이 새 revision에 반영하고 필요한 경우 **[F]** 영향 범위를 재검증한다. 재검증이 필요한 경우 승인 전 HTTP 확인과 해당 revision의 샘플 저장을 포함한다. 추출에 영향 없는 수정은 기존 검증과 실제 샘플 참조·생성 revision을 승계할 수 있다. 필요 없는 재검증의 처리 등 상세 기준은 메시지 계약을 확인한다.
10. Control은 승인 요청의 revision이 현재 후보 및 검증 성공 revision과 일치하는지 확인한다. 승인되면 공유 출처 연결을 확정하고 `schema.prepare`/`schema.prepared`로 Data DB에 v1 스키마를 준비한 뒤 출처별 최초 수집을 조정한다.

초기 자동 분석에는 브라우저 탐색·AI 호출·후보 검증을 포함해 최대 5분을 적용하고, 사용자 승인 대기는 제외한다. 출처별 첫 목록 1페이지와 상세 최대 3건을 검증하며 전체 5분을 넘기면 검증하지 못한 출처는 확인 필요다.

### 실패한 출처의 재시도

- 사용자는 실패한 출처를 지정해 재분석을 요청하거나 후보에서 제외할 수 있다.
- Control은 성공 출처별 intermediate_ref를 저장하고 재시도 요청의 intermediate_refs로 Analysis에 전달한다. 재시도가 성공하면 공동 후보에 반영하고 영향받는 부분을 재검증한다. 반복 실패하면 사용자가 제외할 수 있다. 기존 사용자 수정과 현재 revision을 보존해야 한다. 분석 후보의 `(intermediate_ref, candidate_key) → field_id` 매핑으로 출처별 후보를 구분하고, 재분석 결과와의 매핑이 불명확하면 추측하여 덮어쓰지 않는다.

## 2. 스키마 수정 및 승인 후 데이터 교체

승인된 새 스키마 정의는 출처별 준비 전에 Data DB에 해당 변경 작업 기준으로 비공개 준비한다. 모든 최종 출처 준비가 성공할 때만 스키마·데이터를 함께 공개 전환하며, Data 전환과 Control 커넥터 활성화 사이 일반 작업의 버전 혼합을 막는다.

1. 사용자가 공통 편집 화면에서 스키마, 출처별 필드 위치·CSS 선택자와 탐색 설정을 수정한다. 필드 위치는 목록·상세·해당 출처에 없음 중에서 정한다.
2. Control은 변경 후보를 기록하고 필요한 **[A] [B] [C] [D] [E] [F]** 검증을 요청한다. 상세 규칙이 있으면 실제 상세 이동과 목록 복귀도 확인한다. 승인 전 **[G]** HTTP 확인과 revision별 샘플 저장을 포함한다.
3. 사용자는 검증 결과를 확인하고 수정하거나 승인한다. Control은 현재 후보와 검증 revision을 대조한다. 승인 전에는 적용 중인 설정과 데이터를 유지한다.
4. 필드 추가·삭제·필드명 또는 타입 변경 등 데이터 API 구조가 바뀌면 nullable 여부와 관계없이 새 API 버전 대상이다. 필드 설명·순서 변경 등 응답 구조가 유지되는 변경은 같은 버전을 유지한다.
5. 구조 변경 승인을 받으면 Control은 각 대상 출처에 첫 페이지부터 최대 5분의 리비전 수집을 요청한다. 기존 최신값 일치로 리비전 대상 프로젝트를 조기 종료하지 않는다.
6. Crawler는 최종 스냅샷을 S3에 저장하고 Control에 결과를 전달한다. Ingestion은 해당 스냅샷과 승인된 규칙으로 같은 레코드 테이블에 새 스키마 버전 데이터를 미공개 준비한다. 기존 레코드를 마이그레이션하거나 새 결과와 기존 레코드를 매칭하지 않는다.
7. 모든 대상 출처의 준비가 성공하고 전환 조건을 충족할 때 데이터 세트와 활성 API 버전을 함께 교체한다. 기존 데이터와 API는 준비가 끝날 때까지 유지한다.
8. 일부 출처가 실패하거나 정상 결과가 0건이면 전체 교체를 보류한다. 0건은 확인 필요로 즉시 알리고, 복구 가능한 다른 오류는 자동 복구를 먼저 시도한다. 새 결과에 포함되지 않은 과거 데이터와 기존 record_id는 교체 후 제공되지 않음을 승인 전에 안내한다.

## 3. 공유 탐색 규칙 복구

1. Crawler가 공유 목록 이동 실패를 감지하면 Control에 실패 지점과 공유 출처를 알린다. Control은 연결 프로젝트별 스키마·커넥터와 비교 기준을 준비해 Analysis에 복구를 요청한다. 필드별 상세 이동 실패는 영향 프로젝트 출처를 구분해 처리한다.
2. Analysis는 **[A] [B] [C] [D] [E]** 현재 화면과 기존 규칙을 참고해 새 탐색 후보를 만들고 영향받는 연결 프로젝트별 추출 결과를 검증한다.
3. 프로젝트·출처별 DB 저장 데이터가 3건 이상이면 시스템 저장 순서상 최신 3건의 사용자 필드값을 확인한다. DB가 0건이면 S3에 저장된 승인 revision의 분석 샘플을 사용한다.
4. DB 1~2건이면 있는 데이터를 모두 비교해 전부 일치해야 자동 적용한다. 기준을 모두 확보·일치시키지 못하면 자동 적용하지 않는다. 복구 후보 검증은 최초 시도 포함 최대 3회다. 기준을 확보하지 못하거나 검증할 수 없으면 자동 적용하지 않고 사용자 확인을 요청한다.
5. 모든 영향 프로젝트가 기준을 통과하고 스키마 구조가 유지되면 Control이 승인 없이 공유 탐색 규칙을 적용하고 수집 재실행을 조정한다. 한 프로젝트라도 실패하면 공유 규칙 전체 적용을 보류하고 확인 필요로 처리한다.
6. 스키마 변경이 필요하면 사용자에게 후보를 보여주고 승인 흐름으로 연결한다. 후보 생성·검증 실패 또는 검증 불가라면 확인 필요 상태를 유지한다.

## 4. 필드 추출·파싱 실패와 커넥터 복구

1. Crawler 또는 Ingestion은 추출·파싱·타입 변환 실패의 관찰 내용과 프로젝트·출처·필드 등 영향 범위를 Control에 전달한다. 규칙 관련 실패로 해당 프로젝트·출처의 비교·수집을 계속할 수 없으면 Control은 근본 원인을 미리 확정하지 않고 기준 정보와 영향 범위를 준비해 Analysis에 자동 복구를 요청한다. 반복 실패·검증 불가면 확인 필요로 전환한다. 기술 장애·접근 차단과 구별하며 복구 후보 검증은 최초 시도 포함 최대 3회다. 비교에 필요한 필드의 추출·파싱·타입 변환에 실패해 해당 프로젝트 출처의 비교를 계속할 수 없으면 그 대상만 중단하고 관찰 정보로 복구를 요청한다. 별도 실패율 임계치는 두지 않는다.
2. Analysis는 **[A] [C] [D] [E]** 화면과 기존 스키마를 참고해 필드 선택자·파싱 규칙 후보를 만들고 추출 및 타입을 검증한다.
3. 검증 기준은 탐색 복구와 같이 DB 최신 3건 또는 DB 0건 시 S3 승인 샘플을 사용한다. DB 1~2건이면 있는 데이터를 모두 비교해 전부 일치해야 한다. 승인 샘플이 부족해 전체 기준을 확인할 수 없으면 자동 적용하지 않으며 복구 후보 검증은 최초 포함 최대 3회다.
4. 스키마가 유지되고 검증을 통과하면 Control이 해당 커넥터를 승인 없이 교체하고 후속 수집·적재를 조정한다. 스키마 변경이 필요하면 사용자 승인 흐름으로 전환한다.
5. 복구가 실패하거나 검증할 수 없으면 해당 대상은 확인 필요 상태가 되고 기존 정상 데이터를 유지한다. 다른 프로젝트는 각자의 결과와 적용 조건에 따라 처리한다.

## 5. 기존 프로젝트의 출처 추가

1. 사용자가 새 URL을 등록하고 출처 추가 분석을 요청하면 Control은 기존 활성 스키마와 변경 후보를 Analysis에 전달한다.
2. Analysis는 **[A] [B] [C] [D] [E]** 새 출처의 탐색·추출 규칙을 분석하고, 새 공통 스키마를 임의로 늘리지 않고 기존 필드에 맞춰 매핑·검증한다. 빈 값과 추출 실패를 구분한다.
3. 사용자는 후보와 샘플을 확인하고 필요하면 수정한다. **[F]** 영향받는 부분을 재검증하고 승인 전 **[G]** 목록의 HTTP 가능 여부를 확인하며 새 revision의 샘플을 저장한다.
4. Control은 사용자의 최종 승인 후 최초 수집과 정상 적재를 조정한다. 성공한 추가 출처의 데이터는 공개하고 출처를 활성화한다. 실패·0건은 문제를 표시한다. 스키마 구조 변경이 필요하면 별도의 스키마 변경·승인 흐름을 따른다.
5. 출처 삭제는 후보로 지정해 최종 승인 후 반영한다. 추가와 삭제를 함께 요청한 경우 모든 추가가 성공한 뒤 삭제한다. 추가 실패 시 기존 출처를 유지하고 이미 성공한 추가 출처는 공개한다. 삭제 실패 시 재시도하며 상태를 표시한다.

## 6. 반복 수집과 최종 적재 경계

최초 v1은 같은 승인 스키마를 기준으로 출처별 적재하며, 정상 적재된 출처를 공개하고 실패·0건 출처는 문제 표시한다. 최초 모든 출처가 실패하거나 정상 추출 0건이면 준비된 v1만으로 정상 운영 API를 공개하지 않고 확인 필요를 표시한다. 이후 한 출처라도 정상 적재되면 해당 성공 데이터를 공개한다. 공개 전 최초 복구는 공개 스키마 조회가 아니라 승인 v1 후보·커넥터와 승인 샘플을 적용 작업에서 확보한다. 최초 스키마는 schema.prepare/schema.prepared로 준비한다. 이는 v2 리비전의 모든 출처 성공 후 일괄 전환과 구분한다.

1. Control이 작업 발행 전 Ingestion 내부 API에서 연결된 프로젝트·출처별 최신 저장 데이터 최대 3건을 조회하고 승인 규칙과 함께 Crawler 메시지에 넣는다. DB 1~2건이면 존재하는 만큼, 0건이면 빈 목록이며 조회 실패와 구분한다.
2. Crawler는 각 목록 페이지 또는 무한 스크롤 항목 5개 묶음의 사용자 필드값을 비교한다. 필드 커넥터의 상세 이동·복귀 규칙을 비교해 같은 목록 항목의 동일 동작을 묶어 방문하고 프로젝트 출처·필드와 연결한다.
3. 모든 대상 프로젝트의 최신 기준이 확인되거나 일반 반복 수집 최대 1분에 도달하면 종료한다. 신규 프로젝트처럼 기준이 없는 대상은 다른 프로젝트의 일치만으로 최초 수집을 중단하지 않는다.
4. Crawler는 최종 HTML/DOM 스냅샷을 S3에 저장하고 Control에 결과를 전달한다. Control이 적재 가능한 대상에 대해 Ingestion 작업을 발행한다.
5. Ingestion은 최종 스냅샷에서 데이터를 추출·검증하고 DB와 비교해 중복을 걸러 신규 데이터를 목록 뒤쪽부터 저장한다. 일반 수집에서는 동일 게시물이어도 사용자 필드값이 다르면 새 데이터로 판단한다.
6. 목록 항목 자체가 0건이거나 특정 프로젝트에서 정상 추출 결과가 0건이면 해당 범위를 확인 필요로 표시한다. 사용자는 재확인 또는 출처 삭제를 선택한다. 신규 데이터가 없는 정상 결과와 DB 기준 데이터 0건은 구분한다.

## 7. 남은 세부 결정

- 자동 복구 기준은 DB 최신 최대 3건 또는 DB가 0건일 때 승인 샘플이다. DB 1~2건은 모두 일치해야 하며 기준 부족·불일치 시 자동 적용하지 않는다. 후보 검증은 최초 포함 최대 3회다. 실제 원본 내용이 바뀐 경우의 세부 판단은 구현 검증 대상이다.
- 출처별 중간 결과와 승인 샘플의 형식·참조·정리 조건은 [S3 저장 명세](s3-storage-contract.md)를 따른다. 정리 주체는 Control이며 주기 수치와 DB/S3 간 구체 구현은 운영 검증한다.
- 초기 상세 최대 3건과 HTTP 목록 동일성 확인을 전체 5분 안에 검증한다. HTTP 동일성을 확인하지 못하면 검증 가능한 브라우저 방식을 사용하며 HTTP 시간 수치는 운영 설정이다.
- 실제 null·ABSENT는 정상이고 실패가 포함된 레코드는 부분 저장 및 정상 추출 건수에서 제외한다. 비교에는 승인 parser.code와 공통 타입 변환 결과를 사용한다.
- 새 버전 준비 실패·취소 데이터 정리와 공개 스키마·버전 조회 일관성, 부분 실패 및 중복 요청 처리.
- 수집 오류의 상세 분류·장애 지속 시 후속 처리와 알림 조건. 네트워크 재시도의 명시된 기본 기준은 스펙을 따른다.
- 파서는 메시지 명세의 `parser.code` Java 함수 본문을 사용한다. Analysis·Crawler·Ingestion은 공통 Java 파서 모듈을 사용하고 생성 코드는 별도 격리 없이 각 서비스 JVM에서 실행한다. 파일·네트워크 접근, 무한 반복과 메모리 고갈이 해당 서비스에 영향을 줄 수 있으며 별도 샌드박스나 자원 강제 제한은 보장하지 않는다. 공통 모듈의 세 서비스 결과 일치는 구현 시 검증한다. 별도 가공이 필요 없으면 parser는 null이다.
- 비교·수집을 계속할 수 없는 규칙 관련 실패는 자동 복구한다. 복구 후보 검증은 최초 포함 최대 3회이며 세부 실패 판정은 구현 검증 대상이다.

## 8. 최신 연결 계약

- 공동 후보의 필드별 recommendation_reason을 analysis.completed에 포함한다. 웹에는 Control이 현재 후보·S3 샘플을 반환한다. Analysis가 Control의 후보를 직접 덮어쓰지 않는다.
- 상세 후보는 첫 목록에서 최대 3개를 브라우저로 검증한다. 선택한 규칙에 대한 변환은 각 서비스 JVM의 공통 Java 모듈에서 수행하며 추가적인 공백 가공은 승인 parser.code가 있는 경우에만 수행한다.
- 최초를 포함해 복구 후보를 최대 3회 검증하고 DB 최신값 또는 승인 샘플 기준이 부족하거나 모두 일치하지 않으면 사용자 확인으로 전환한다. 공유 규칙은 모든 영향 프로젝트 통과가 필요하다.

### 목록 URL 규칙과 원문 링크

Analysis는 목록 이동이 숫자 규칙일 때 `URL_TEMPLATE`과 `{value}` 자리표시자·시작값·증가값을 만들고 실제 첫 목록과 다음 화면에서 검증한다. 재현되지 않거나 숫자 규칙으로 나타낼 수 없으면 NEXT_LINK 또는 검증된 브라우저 이동을 사용한다. 정확한 형식은 [메시지 명세 5.2](service-message-contracts.md#52-목록과-상세-이동)를 따른다.

상세 수집은 항상 브라우저에서 링크 또는 클릭으로 수행한다. 분석 샘플의 `source_url`은 해당 항목의 직접 접근 URL을 확인한 경우에만 기록하고, 그 외에는 null이다. 목록 화면의 주소를 항목 URL로 대체하지 않는다.

### 승인 변경 시작과 종료

Control은 프로젝트마다 승인 변경을 하나만 진행한다. 기존 dataset.apply로 BEGIN_CHANGE를 보내고 Data DB의 OPEN 기록과 dataset.applied 성공을 확인한 후 스키마 준비·수집·적재를 발행한다. 성공 또는 최종 실패 시 END_CHANGE로 닫고 Data의 실제 커밋 결과를 반영한 뒤 다음 변경을 허용한다. OPEN 여부·대상·버전과 출처 삭제 차단은 Data DB 쓰기 트랜잭션에서 확인한다. END 결과가 불확실하면 재전달하고 새 변경은 보류한다. 초기 일부 성공·추가 일부 성공은 유지하고 리비전 실패는 기존 버전을 유지한다. 상세는 [메시지 명세 10.5](service-message-contracts.md#105-승인-변경의-시작과-종료-기존-datasetapply-확장)를 따른다.

### 커넥터 복구와 적재 revision

Analysis가 스키마 유지 커넥터를 검증하면 Control은 해당 출처의 새 작업을 보류하고 Ingestion의 dataset.apply SET_CONNECTOR_REVISION 결과를 확인한다. Data DB의 유효 revision 갱신 후에만 Control 커넥터를 활성화하고 재수집한다. 후보 스키마 변경 중에는 관련 PREPARE를 다시 검증한다. 사용자 조치가 필요한 0건은 END_CHANGE 완료를 확인한 뒤 재확인·삭제를 새 작업으로 연결한다. 자세한 순서는 메시지 명세 10.6~10.8이다.

## 9. 공개 전 복구와 빈 프로젝트

- 최초·추가·리비전의 승인 작업 출처는 활성 가드와 별도의 Data pending revision을 BEGIN에 등록한다. 복구 검증 후 Control은 SET_CONNECTOR_REVISION CHANGE의 Data 동기화 성공을 먼저 확인한 뒤 규칙을 활성화하고 새 자식 작업으로 실행한다. 각 출처 쓰기는 DB 커밋 때 pending revision을 재확인하므로 늦은 이전 적재를 차단한다. 성공 공개·전환은 pending을 활성 가드에 원자 반영한다. 공개된 일반 수집은 ACTIVE 범위 가드를 사용한다. 상세는 메시지 19.8이다.
- 마지막 출처 삭제 후 공개 스키마가 있으면 기존 스키마 기준 ADD_SOURCE를 사용한다. 공개 전 빈 프로젝트에는 보관된 승인 v1 후보를 기준으로 새 출처를 분석하고 승인 후 새 INITIAL로 수집한다. 사용자 정의 스키마 구조가 달라지면 다시 승인받는다.


## 실행 계약 추가 사항

최초 추천 결과는 Control이 description=null과 추천 배열 순서의 display_order를 한 번 초기화한다. Analysis 재시도는 대상 출처 매핑·샘플만 교체하며 공통 필드와 다른 출처의 사용자 편집은 보존한다. 목록 NONE은 첫 화면만 확인한다. 상세는 BROWSER이며 CURRENT_TAB/NEW_TAB/MODAL과 각각 HISTORY_BACK/CLOSE_TAB/CLOSE 복귀 및 대상 화면의 wait_selector를 실제 실행 검증한다. 예상과 다른 탭·모달이나 대기 실패는 성공이 아니다.

동일 출처 판단은 보수적 URL 정규화와 순서가 유지된 완전한 탐색 규칙 동등성을 이용한다. 공유 출처 복구에서는 각 대상의 공개 스키마 또는 미공개 승인 준비 v1과 기존 데이터 또는 S3 승인 샘플을 구분해 검증한다. 브라우저 요청에 호스트 임대를 적용할 때 전체 탐색을 잠근 채 하위 요청에 재진입하지 않는다. 메시지 명세 20절이 실행 필드의 기준이다.


### 8.2 항목과 이동 검증

Analysis는 item_selector로 각 목록 항목이 분리되고 필드별 상세 열기 선택자와 상세 DOM 추출 선택자가 올바른 항목·화면에 연결되는지 실제 목록·상세 화면에서 검증한다. 목록 이동은 URL뿐 아니라 전후 항목 구간과 진행 여부를 확인한다. MVP는 가상화 DOM에서 사라진 항목의 복원이나 완전한 중복 판별을 보장하지 않고 누락을 허용한다. 검증한 규칙과 실제 수집 manifest의 항목·상세가 다른 항목으로 잘못 매칭되도록 추측하지 않는다.

### 재시도·신규 출처의 후보 경계

Control은 동일 분석·출처의 진행 중 재시도에 기존 job을 반환한다. 유효 결과는 요청 revision이 현재와 같을 때만 대상 출처에 병합하고 후보 revision을 증가시킨다. 필요한 검증은 새 revision에 연결하며 나머지 출처의 유효 검증은 영향이 없는 경우에만 승계한다. 오래된 결과는 반영하지 않는다. 신규 출처는 list_url·analysis_id·expected_revision으로 기존 편집 후보에 원자 연결된 뒤 그 새 revision의 ADD_SOURCE로 실행한다. 상세 HTTP와 원자 처리 조건은 메시지 명세 20.9를 따른다.
